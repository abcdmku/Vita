BLOCKING

1. `runtime/permission-broker/src/decide.ts` validates `packageContract` but then grants using methods from the original untrusted object. The grant checks call `classes.includes`, `volumes.find`, `network.*.some`, and rule-array `includes`/`every` on data returned by `validatePackageContract`. The manifest validator returns the same object and does not reject array method shadowing, so a shape-valid contract can define `contract.network.egress.some = () => true` and make an undeclared egress capability appear declared. Same issue exists for data via `classes.includes`/`volumes.find`. This violates the core contract: grant only if explicitly declared by the package, default-deny, fail-closed, pure/deterministic.

2. The same trust-boundary pattern appears in the bespoke policy/request parsers: raw arrays are traversed with caller-controlled `.forEach` / `Symbol.iterator` behavior. For an R2 TCB component, guards over `unknown` input must not execute attacker-supplied methods while deciding whether to grant. Normalize to plain internal data using intrinsic-safe indexed reads, or reject non-plain/exotic arrays before any decision logic.

3. The tests do not cover this bypass. Current adversarial cases cover partial plain objects, missing fields, alias rejection, and cycles, but not method-shadowed arrays or hostile iterators that pass validation yet alter grant decisions. This needs a regression test proving a package/policy with shadowed array methods is all-denied and never grants undeclared capability.
