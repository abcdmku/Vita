## TOP-PRIORITY concern — the "442-deletion" SDK model rewrite: NOT a regression

The framing that the shared module was "gutted" does not hold up. The rewrite **removed a second, hand-rolled
copy** of capsule validation (regex ID/version patterns, a bespoke base64/SRI decoder, embedded-field/secret
scanners) and replaced it with a thin wrapper that delegates to the **already-canonical shared manifest validator**
`compileCapabilityValidator(CAPSULE_MANIFEST)` (`sdk/typescript/src/capsule-registry-model.ts:81-100`). That is the
same machinery the ADR-0007 manifest dialect and the cross-language conformance corpus already use. Net effect: the
TS model is now provably aligned with the shared `schema/capabilities/capsule.json` manifest (and therefore with
agentd), rather than maintaining a divergent duplicate. This is the *opposite* of drift.

### 1. Blast radius — no exports removed, no consumer broken
All public exports present on `main` are still exported on the branch (`validateCapsuleRegistry`, `CapsuleEntry`,
`CapsuleEntryState`, `CapsuleId`, `CapsuleIntegrity`, `CapsuleRegistry`, `CapsuleRegistryValidationError`,
`CapsuleRegistryValidationResult`), plus additive new ones (`CapsuleRegistryApplyRequest`, `CapsuleRegistryConfig`,
`validateCapsuleRegistryApplyRequest`, `buildCapsuleRegistryApplyRequest`, `buildCapsuleRegistryConfig`).

  `CapsuleRegistryValidationError` → **6/6 pass**.

### 2. Why the deletions — legit refactor, converges on agentd's shape
The new `CAPSULE_MANIFEST` (`sdk/.../generated/capability-manifests.generated.ts:188`) encodes the full
`{desired:{capsules:[{id,version,integrity,state}]}}` apply-request shape with constraints that mirror
`agent/capabilities/capsule/capsule.go` 1:1: `id` capsuleId/maxBytes 255/noInlineCapsuleMaterial/forbiddenSchemePrefix
(↔ `validCapsuleID`), `version` capsuleVersion/maxBytes 128 (↔ `maxVersionLength=128`), `integrity` sriIntegrity
(↔ `isValidSRI`), `state` enum [installed,disabled], `capsules` uniqueBy `id` (↔ duplicate-id rejection), unknown-field
rejection. The unchanged `capsule-conformance.test.ts` runs a ≥25-vector corpus from the shared
`schema/capabilities/capsule.json` through this exact validator — so accept/reject parity with agentd is enforced.

### 3. Two test files — odd placement noted, no coverage weakened (NON-BLOCKING)
`sdk/typescript/src/capsule-registry-model.test.ts` is the **only** `src/*.test.ts` in the entire repo (every other
test lives under `test/`). It is a strict *subset* of the extended `sdk/typescript/test/capsule-registry-model.test.ts`
(config-builder shape + bad-SRI/embedded-secret/unknown-field), so it does not weaken or duplicate-away coverage — it
is merely redundant and misplaced. The contract's own artifact list named that `src/` path, so the worker followed the
contract literally. The CI/host runner globs `os/x86_64/test/*.test.ts` only (`tools/wsl-verify.sh:31`) and the SDK
tests are run by the worker, so the placement does not orphan CI. **Cleanup nit, not a blocker.** The extended `test/`
file's assertion changes (`["2/id"]`→`["2"]`, id fixture `com..vita`→`com.vita/app`) reflect the new validator's
correct manifest-relative paths, not weakened assertions — verified against the passing conformance corpus.

## Standard axes

### 4. Apply correctness + fail-closed — correct
`os/.../main.ts`:
- Committed: `buildCapsuleRegistryConfig([TEST_CAPSULE_ENTRY])` (fixed id `local.test.capsule`, pinned `1.0.0`, valid
  empty-string sha256, state `installed` → idempotent) → `applyNodeConfig(config.config, ...)` over the **same S3
  transport** → `VITA-CAPSULE: id=… ver=… state=… outcome=committed status=OK` (`main.ts:418-428`).
- Rejected: `FORCED_INVALID_CAPSULE_PLAN` uses `integrity:"sha256-AAAA"` (un-decodable SRI) sent via `client.apply()`
  → on agentd `rejected` outcome OR 4xx → `VITA-CAPSULE: outcome=rejected reason=… status=OK` (`main.ts:461-489`). It
  deliberately bypasses the TS evaluator (same pattern as the existing `emitForcedRejectMarker`) precisely so the
  invalid entry reaches agentd, proving **agentd** fails closed — TS is untrusted at the boundary.
- Failsafe: build error, transport error, connect/state failure all emit `VITA-CAPSULE-ERROR: status=FAILSAFE`. All
  prior markers (TS, PDS, CONNECT, STATE, APPLY) preserved.
- Acceptance `capsule.test.ts`: **6/6 pass.** Asserts the exact `POST /apply` body
  `{operations:[{capability:"capsule.registry",request:{desired:{capsules:[…]}}}]}` (surface stays `/apply`),
  committed/rejected marker formatting, and transport-throw → FAILSAFE with exactly 1 call.

Surface preservation independently confirmed: `apply-node-config.ts`, `unix-socket-transport.ts`, `agent-client.ts`
are **untouched**; agent-client exposes only `/apply` (POST) + read-only GETs (`/healthz`, `/capabilities`,
`/operations`, `/state`). `capsule.registry` IS in the evaluator manifest registry — no manifest gap (the contract's
hypothetical gap does not apply).

Minor note (non-blocking): `capsule.test.ts`'s `formatCapsuleMarker` mirrors `main.ts`'s marker logic rather than
importing it (`main.ts`'s functions are unexported) — same convention the apply markers use. The strings match
`main.ts` exactly; the real `main.ts` output is confirmed by the orchestrator boot step.
