## Objective
Wire the host backend's **window-manager intents** into the **GPU compositor** so that
`launchApp` / `stopApp` / focus / snap move *real* windows on screen. Today the appshell host
backend (`sdk/typescript/src/appshell/index.ts`) collects `WindowManagerIntent`s
(`repositionTexture` / `setFocus` / `setTextureVisibility`, validated by `isWindowManagerIntentArray`
in `ui_kits/desktop/runtime/host-bridge.ts:773`) and *only* re-emits them to an opaque `wm` port
(`emitWindowManagerIntent(this.#ports.wm, intent)`); **nothing applies them to the compositor**.
`CompositorDriver.reconcile` (`sdk/typescript/src/compositor-bridge/index.ts`) already accepts
`windowIntents` and patches placement/visibility/z-order via `applyWindowIntent` reusing the
no-repaint delta path (`diffCommands` → empty `commands` when nothing changed), but no code feeds the
host's emitted intents into it.

Build a headless, deterministic **WM-intent applier** in
`sdk/typescript/src/compositor-bridge/applier.ts` that:
- Accepts a stream/batch of `WindowManagerIntent`s (the exact union from `sdk/typescript/src/wm/policy.ts`,
  re-exported in the compositor-bridge) plus the current shell `ShellComposedLayout`, and drives an
  injected `CompositorPort` through `CompositorDriver.reconcile({ shell, windowIntents })`.
- Reconciles a multi-window **WindowModel** into one `registerSurface` / `updatePlacement` /
  `removeSurface` per `windowId` (one compositor surface per window texture), folding launch
  (`repositionTexture` → register+place visible), stop (`setTextureVisibility:false` of a tracked
  texture → `removeSurface`), focus (`setFocus` → z-order restack, no register/remove), and snap
  (`repositionTexture` of an existing texture → `updatePlacement` only).
- Returns the resulting `CompositorReconcileResult` and surfaces fail-closed errors verbatim
  (`DUPLICATE_SURFACE` / `INVALID_SURFACE` / `UNKNOWN_WINDOW_SURFACE` / `PORT_COMMAND_FAILED`) — it
  must NOT swallow them, mutate the shell, or invent placements.
- Is pure of ambient I/O: the only effect is calling the injected `CompositorPort`. No DOM/CEF/native.

Put the applier under `sdk/typescript/src/compositor-bridge/applier.ts` (export from the
compositor-bridge `index.ts`) and the tests under
`sdk/typescript/test/ui-kits/wm-intent-applier.test.ts`. Import the SDK only via its public
compositor-bridge exports; reuse `CompositorDriver`, do NOT re-implement intent reconciliation.

## User value
App launch, stop, focus, and snap actions emitted by the host backend actually relocate, raise, and
remove on-screen windows on the GPU compositor — closing the loop between the desktop interaction
view-models and the live KMS surface, with the existing no-repaint delta path preserved (idle ticks
produce zero compositor commands).

## Non-goals
- NO DOM/CSS/CEF/rendering, NO native/Rust changes, NO new wire-protocol commands (the
  `registerSurface`/`updatePlacement`/`removeSurface`/`present` set is fixed by PSD-304).
- Do NOT re-implement `applyWindowIntent`/`diffCommands` — consume `CompositorDriver`.
- Do NOT change `isWindowManagerIntentArray`, the host-bridge transport, or any acceptance/eval suite.
- No new visual design; no shell mutation; no ambient I/O.

## Acceptance
`acceptance_command` passes. Deterministic unit tests in
`sdk/typescript/test/ui-kits/wm-intent-applier.test.ts` cover, against a fake `CompositorPort` that
records calls:
- A sequence of intents produces the expected `CompositorDriver` command deltas
  (`registerSurface` + `updatePlacement` on launch; `updatePlacement` only on snap; `removeSurface`
  on stop).
- A `setFocus` to a non-top window restacks z-order and emits only `updatePlacement` (no
  register/remove).
- Opening 3 windows yields exactly 3 window surfaces (one per `windowId`).
- An invalid intent (unknown texture / non-window surface / malformed rect) is rejected fail-closed
  with the matching `CompositorDriverError.code`, and no partial port effects leak past the failing
  command.
- An idle reconcile (no changed intents) emits zero commands (no-repaint delta path).
- The existing compositor cargo tests still pass: `cargo test --manifest-path packages/compositor-core/Cargo.toml`
  is green (run by the worker; record the output as an artifact).
typecheck clean; pure and headless.

## Security/constraints
- Injected `CompositorPort` only (no ambient I/O); capability-mediated; fail-closed on every
  malformed intent. Pure/deterministic — same intents → byte-identical command sequence.
- No remote imports; lockfile mandatory; no package lifecycle scripts; no FFI/native addons.
