## Objective
Add a **registration ceremony** to the `owner.identity` capability that mirrors the existing
assertion (login) challenge path. Today `agent/capabilities/owner/owner.go` `Challenge(action)` mints
challenge tickets that are implicitly only used to verify `webauthn.get` (login) assertions
(`verifyAssertion` enforces `clientData.Type != webauthnGetType` → `denyInvalidType`), and the enroll
path (`ApplyRequest` → `enroll`) trusts the client-supplied `OwnerCredential` blindly with **no**
challenge binding. This contract adds a `webauthn.create`-flavored **create-ceremony** challenge
variant so a future enrollment can be tied to a server-minted, action-bound, single-use, TTL-bounded
ticket — without changing any key handling.

Concretely (server-side state machine ONLY; no crypto/key work):
- Introduce a ceremony notion for challenges: `get` (existing assertion path, default) and `create`
  (new registration path). Carry it on the `challengeRecord` and surface it on `ChallengeTicket`
  (e.g. a `Ceremony string json:"ceremony"` field whose zero value behaves as `get` for backward
  compatibility — existing callers that don't set it must keep working).
- Mint a create-ceremony ticket via the **same** TTL/replay-protected challenge map
  (`c.challenges`, `defaultChallengeTTL`, `pruneExpiredChallengesLocked`, `consumeChallengeLocked`),
  scoped to a registration intent. Use the well-known action token `owner.enroll` for the create
  ceremony (it already satisfies `validateAction` / `actionPattern`).
- A create-ceremony ticket and a get-ceremony ticket are **distinct and non-interchangeable**: a
  challenge minted for `create` must NOT be consumable by the get/assertion path, and vice-versa
  (cross-ceremony replay must be rejected). Consumption must check the ceremony in addition to the
  existing action + TTL + single-use checks. Reuse a stable deny reason from the existing
  `deny*` constant set for the mismatch (e.g. `denyActionMismatch`) — do NOT invent a leaky reason
  string; keep `sanitizeReason` exhaustive over any constant you add.
- HTTP surface: the route that serves `/challenge/owner.identity` must accept a `ceremony=create`
  query selector and return a create-ceremony challenge distinct from the default
  (`ceremony` absent / `ceremony=get`) GET challenge. (Locate the existing handler that calls
  `Challenge(...)` for `/challenge/owner.identity` and extend it; do NOT duplicate the route.)

This is a pure server-side ceremony/state-machine change. It does NOT register a credential, parse
attestation objects, verify attestation statements, or touch any signing/recovery/TPM material —
those remain owner-held and out of scope (§16).

## User value
Closes a Phase-2 residual gap in the owner-identity trust path: enrollment can be bound to a
server-minted, replay-proof registration challenge instead of trusting an unauthenticated
client-supplied credential, and the create/get ceremonies cannot be confused for one another. This
is the foundation the later attestation-verification work hangs off.

## Non-goals
- NO attestation-object parsing, NO `webauthn.create` attestation-statement verification, NO COSE
  key extraction from attestation, NO change to `enroll`/`ApplyRequest` trust semantics in THIS
  slice (the create ticket is minted + consumable; wiring enrollment to require it is a follow-up).
- NO new persisted state / no on-disk format change (challenges stay in-memory).
- NO key, signing, recovery, or TPM handling of any kind (§16 — owner-held).
- Do NOT weaken or rename existing deny constants, the assertion (`get`) path, or `sanitizeReason`'s
  closed set; backward compatibility for existing `Challenge`/`Consume` callers is mandatory.

## Acceptance
`acceptance_command` passes deterministically. New table/unit tests in
`agent/capabilities/owner/*_test.go` (same package) must assert:
1. A `create`-ceremony ticket is **action-bound**: minting with the create ceremony yields a ticket
   carrying the create ceremony + `owner.enroll` action; consuming it with a mismatched
   ceremony/action is rejected.
2. **Single-use**: consuming the create ticket once succeeds; a second consume of the same challenge
   is rejected (`denyChallengeReplayed`).
3. **TTL-expired**: a create ticket consumed after `now()` advances past `challengeTTL` is rejected
   (`denyChallengeExpired`) — drive via the injectable `now func() time.Time` clock.
4. **Cross-ceremony replay rejected**: a challenge minted for `create` is NOT consumable by the
   get/assertion path, and a `get` challenge is NOT consumable by the create path.
5. **HTTP**: `GET /challenge/owner.identity?ceremony=create` returns a challenge distinct from the
   default GET challenge, and the create challenge is rejected by the get-ceremony consumer
   (and vice-versa). Existing `Challenge`/`Consume` tests still pass (back-compat).
The pre-existing `-run Challenge` tests MUST continue to pass; the filter
`-run 'Challenge|RegistrationCeremony'` selects both old and new cases.

## Security/constraints
- Deterministic, no-I/O state machine except the existing in-memory challenge map; clock injected
  via `now`. No network (`allowed_network: false`), no remote imports, no new deps, no lifecycle
  scripts; lockfile/module graph unchanged.
- Fail-closed: unknown/expired/replayed/cross-ceremony challenges deny via the existing closed
  deny-reason set; `sanitizeReason` stays exhaustive (no information leakage in deny reasons).
- §16: signing / recovery / TPM keys are **owner-held and unavailable to dev agents** — this slice
  is propose-only for any key-bearing behavior and MUST NOT touch key material.
