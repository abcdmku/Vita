## Objective
The first developer-facing surface of the Vita app platform: a small set of FIRST-PARTY SDK STARTER TEMPLATES a
developer can copy as the starting point for their own capsule. Each template is a minimal, complete, *valid*
`PackageContract` (the §9.2 package-contract / capsule manifest dialect already merged in
`sdk/manifests/src/package-contract.ts`), authored as a typed TS module, that VALIDATES against `validatePackageContract`.
Three templates covering the most common shapes:

1. **`ts-service.template.ts`** — a minimal `packageClass: "ts-service"` HTTP service: one private ingress rule, no
   egress, no accelerators, a single persistent `app-state` volume, an `http` health check, `strategy: "replace"`
   updates with NO schema migrations, `requireCleanVerification: true` restore, `vita-capsule` export. The canonical
   "write a small TypeScript backend" starting point.
2. **`static-site.template.ts`** — a minimal site/UI capsule (`packageClass: "ui-extension"`): one private `https`
   ingress, no egress, a single READ-ONLY `cache`-class ephemeral volume (the served assets), `lifecycle` health check,
   `none` backup strategy, no secrets. The "ship a static front-end" starting point.
3. **`data-app.template.ts`** — a minimal data-centric `ts-service`: a persistent `user-content` volume + a persistent
   `app-state` volume (both `backup: true`), `strategy: "application-consistent"` backup with quiesce hooks,
   `requireCleanVerification: true` restore, an `http` health check. The "build an app that owns user data and is
   backed up" starting point.

Plus `index.ts` re-exporting the three as named typed `PackageContract` constants (e.g. `tsServiceTemplate`,
`staticSiteTemplate`, `dataAppTemplate`) so the SDK and future tooling (catalog authoring, `vita init <template>` CLI)
can import them. Each template is annotated with brief comments explaining the copy-and-edit fields (id, name, version,
digest, signingKeyRef) a developer must change. Pure TS, deterministic, no I/O. NO on-device component — this is the
host-side SDK/authoring floor.

## User value
The §9.3 package-contract is the contract a developer fills in to ship an app on Vita; today there is a validator and a
single test fixture but NO starting point a developer can copy. These templates are the first concrete on-ramp to the
app platform: a developer copies the nearest template, edits identity/version/digest/signing-ref, and has a manifest
that already passes the platform validator and encodes the secure defaults (referenced-not-inline secrets, private
ingress, explicit volumes/health/backup). Foundation for a later `vita init` scaffold (CLI) and the signed catalog.

## Non-goals
NO new validator behavior, NO change to `package-contract.ts` or any schema/dialect (templates must satisfy the schema
AS MERGED — if a template can't be expressed validly, fix the template, never loosen the validator). NO real app code /
business logic / runtime entrypoint (these are *manifests* only). NO catalog entry, NO signing, NO CLI scaffold (later
slices). NO real digests/keys — use clearly-placeholder TEST values (e.g. a 64-hex zero/sample digest, a
`publisher-key://vita/first-party/...` ref) with comments saying "replace before publishing"; NEVER embed or generate
production signing/key material, and NEVER use an inline-secret field (`value`/`token`/`privateKey`/… are rejected by
the validator by design). NO on-device marker (pure host-side module — no boot involvement).

## Acceptance tests
`acceptance_command` (the existing manifests test glob, which the new `templates.test.ts` joins):
`node --experimental-strip-types --test "sdk/manifests/test/*.test.ts"`. The new `templates.test.ts` must assert, for
EACH of the three templates:
- `validatePackageContract(<template>)` returns `ok: true` (fail the test with the joined `path: message` errors if not).
- The expected `packageClass` (`ts-service` / `ui-extension` / `ts-service`) and that each is a distinct `identity.id`.
- The static-site template's served-assets volume is `access: "read-only"` and the data-app template has at least one
  `backup: true` persistent volume — i.e. the templates encode the intended secure shape, not just "any valid object".
- No template contains an inline-secret field (assert validation stays `ok: true` AND that no template object has own
  keys in {`value`,`plaintext`,`secret`,`token`,`password`,`privateKey`,`data`} at the secret-entry level) — proves the
  referenced-not-inline discipline.
Also: the existing `package-contract.test.ts` cases must still pass unchanged. `npm run typecheck` clean on the touched
files. Do NOT add hidden/rotating cases here.

## Performance & security constraints
Pure, deterministic, no I/O, no remote imports, no lifecycle scripts, no FFI. Secrets only ever REFERENCED (`ref:`),
never inline — the templates model the §13.1 secret-leak discipline. TEST/placeholder digests + signing refs only; no
production key material committed or generated. The TS authoring surface is unprivileged and produces only a manifest —
any later privileged action is the Go agentd re-validating this manifest, never raw runtime text (encode that intent in
the template comments: "this manifest is re-validated by the node before anything is applied"). R1 (isolated,
additive, non-privileged SDK modules + a test; no schema/TCB change) — orchestrator review + integrate.

## Hardware profiles
Host-side only (any); no on-device / hardware-specific component. The templates' `architectures` field SHOULD list both
`x86_64` and `arm64` (portable-first), but that is template content, not a build requirement.

## Allowed tools & network
Offline. Node ≥22 built-ins only (`node:test`, `node:assert/strict`). No network, no filesystem writes at runtime, no
package installs.
