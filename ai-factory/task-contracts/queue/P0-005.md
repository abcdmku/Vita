## Objective
Implement `validatePlan(state: DesiredState, caps: DeviceSnapshot): ValidationResult` that
type-/schema-validates a desired state and **rejects invalid or overprivileged plans** (spec §8.2
step 4; Phase-2 exit gate "Invalid or overprivileged plans are rejected"). Return a typed result:
`{ ok: true; plan: CanonicalPlan } | { ok: false; errors: ValidationError[] }` where each error has a
`path` and a `message`. Validate at least:
- Schema: required fields present, enums in range, no unknown app/backup fields.
- Resource sanity: e.g. an app requesting an accelerator the device snapshot does not have (and no
  CPU fallback) is rejected (spec §3.9, §14).
- Least privilege: an app requesting a capability/data-access not declared/allowed is rejected
  (overprivilege) — model a minimal `allowedCapabilities` notion to demonstrate the rejection.

Build on `DesiredState`/`normalize` (P0-001) and `DeviceSnapshot`/accelerator types (P0-003).

## User value
Rejecting invalid/overprivileged plans before they reach the Go agent is core to the trust model
(spec §7.1, §8.2). A plan must be proven safe before it can be applied.

## Non-goals
- No host enforcement (that's the Go agent later) — this is the *pure validation layer*.
- No network/policy-engine integration yet; model a minimal allow-list to prove the rejection path.

## Dependencies
P0-001 (`DesiredState`/`normalize`), P0-003 (`DeviceSnapshot`, accelerators).

## Acceptance tests
`acceptance_command`. `sdk/typescript/test/validate.test.ts` must prove:
1. A valid, least-privilege plan validates and yields a `CanonicalPlan`.
2. A schema-invalid plan (bad enum / missing required / unknown field) is rejected with a precise
   `path`.
3. An overprivileged plan (undeclared capability or unavailable accelerator without CPU fallback) is
   rejected.

## Performance & security constraints
Pure/deterministic, no I/O. Fail closed — ambiguous/unknown → reject, never silently allow.

## Hardware profiles
Exercises no-accelerator and x86_64/arm64 snapshots.
