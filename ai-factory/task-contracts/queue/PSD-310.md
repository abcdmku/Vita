## Objective
Harden the **production libinput device backend** on the real KMS open() path so input availability
is actually *verified*, not perpetually `Unverified`. Today the live KMS backend reports
`InputAvailability::Unverified` (`lib.rs:340-341`) while the real device path
(`LibinputState::open` / `add_default_input_devices` / `poll_events` — `platform/linux.rs:2086-2250`)
opens devices from `/dev/input` once and never reflects seat ownership or hotplug. This slice makes
the device backend production-grade and the **real input source feeding PSD-300's routing core**:
- **Seat management.** The backend must acquire input through a seat session (seatd/logind) rather
  than raw `open(2)` on `/dev/input/event*`. Model the seat acquisition behind a small injectable
  seat-provider trait so it is testable without root or a live seat: a `SeatSession`-style abstraction
  whose `open_restricted`/`close_restricted` go through the seat (replacing the direct `libc_open` in
  `libinput_open_restricted` — `platform/linux.rs:2258-2271`). **Fail closed**: if no seat can be
  acquired (no seatd socket / no logind session / `take_control` denied), `open()` returns the
  existing `input_unavailable(..)` error and the backend stays `Unavailable`/`Unverified` — it must
  NOT fall back to privileged raw device opens.
- **Device discovery + hotplug.** Replace the one-shot enumeration with a discovery/refresh routine
  that can add devices on hotplug-add and drop them on remove, keyed by the `/dev/input/eventN`
  selection already in `add_selected_input_devices` (`platform/linux.rs:2216-2250`). Surface a
  pure, testable hotplug-reconciliation function (add/remove set diffing over device paths) plus a
  device-count accessor; the FFI dispatch loop stays as-is for event draining.
- **Verified availability transition.** Add an `InputAvailability::Verified` state and the transition
  rule: the KMS backend reports `Unverified` until the seat is held AND at least one input device has
  been successfully added AND at least one real libinput event has been observed via `poll_events`,
  at which point it becomes `Verified`; loss of the seat or removal of the last device returns it to
  `Unverified` (never silently `Available`). Keep `Available`/`Unavailable`/`Unverified` semantics
  for the existing stub/path backends unchanged; update `marker_token()` (`lib.rs:317-325`) to cover
  the new variant.
- **Marker.** Define `pub const VITA_INPUT_DEVICE_MARKER: &str = "VITA-INPUT-DEVICE";` and a
  `marker_line()` on a small device-backend self-test report emitting a stable asserted line, e.g.
  `VITA-INPUT-DEVICE: seat=<held|absent> devices=<n> availability=<token> status=OK`, so a later
  boot self-test can assert it.
- Keep the crate self-consistent: every new public item is exercised by `#[cfg(test)]` tests in a
  new `input_device_backend` module; `cargo test --locked` and `rust-in-docker.mjs` stay green.

## User value
Turns the live CEF desktop's input from a hard-coded `Unverified` placeholder into a real,
seat-managed, hotplug-aware device source: a VMware boot with an attached keyboard/mouse transitions
to `Verified` and synthetic key/pointer events actually flow from libinput into PSD-300's routing
core — the missing production half of interactive input. Fail-closed seat handling keeps the boot
input path from ever silently grabbing devices it does not own.

## Non-goals
- NO GPU/CEF changes, NO compositing/damage/placement changes, NO input *routing* logic (that is
  PSD-300 — this only feeds it).
- Do NOT change the `RenderBackend` trait surface beyond returning the new `Verified` availability,
  the existing `InputEvent` variants, or the `VITA-COMPOSITOR` marker shapes.
- Do NOT add a new network dependency or talk to logind over D-Bus with `allowed_network: true`
  (seat acquisition is local IPC/socket only).
- Do NOT weaken or edit any existing test; do NOT add privileged raw-device fallback.

## Acceptance
`acceptance_command` passes: `tools/build/rust-in-docker.mjs` builds the compositor for linux x86_64
in the pinned `rust:1.88.0-bookworm` container, and `cargo test --locked --lib input_device_backend`
is green in that same container. The `input_device_backend` test module must concretely cover, using
the injectable seat-provider + a fake device set (no real `/dev/input`, no root):
- seat acquisition success → devices added → first observed event flips availability to `Verified`;
- **seat-absent fail-closed**: seat acquisition denied → `open()` returns `input_unavailable` and
  availability stays `Unverified`/`Unavailable`, with NO raw-device fallback attempted and no panic;
- hotplug reconciliation: adding a device path raises the device count; removing the last device
  returns availability to `Unverified`; add/remove diffing is deterministic;
- `marker_token()` returns the new `Verified` token and round-trips for all variants;
- the exact `VITA-INPUT-DEVICE: ... status=OK` marker string is asserted.
The `--lib input_device_backend` filter selects the new module by name, so an empty/stub branch with
no such tests runs zero matching tests and the build + self-consistency floor still fails it — no
wildcard globs.

Beyond unit acceptance, the host-verify gate (orchestrator-run, not in `acceptance_command`): a
VMware/QEMU boot with an attached input device transitions `InputAvailability` to `Verified` and a
synthetic key/mouse event reaches PSD-300's routing core; with no seat available the backend stays
`Unverified` and the node does not crash.

## Security/constraints
- **Fail-closed** seat handling: no privileged raw `/dev/input` open without an acquired seat; the
  existing `DeviceAllow char-input r` grant is the only device access (do not broaden it).
- Pure/deterministic for the hotplug-diff and availability-transition logic (same device set + seat
  state → identical availability + byte-identical marker); FFI confined to the libinput/seat dispatch.
- No remote imports; `Cargo.lock` stays committed and `--locked` is used; no package lifecycle
  scripts; no FFI beyond the libinput + seat session bindings. Coordinate/count math must not
  overflow or panic on empty/absent inputs.
- **R3** (boot/privileged compositor input path). Orchestrator runs the independent Codex reviewer
  (`npm run review -- PSD-310`) and merges only on `VERDICT: approve` plus the host-verify boot gate;
  per the active owner override R3 may auto-merge ONLY after that reviewer-approve + independent
  verification, never on a stop condition.

## Rollback plan
Single-branch (`task/PSD-310`), additive to `platform/linux.rs` + the `InputAvailability` enum;
revert the merge commit to restore the prior one-shot `Unverified` device path. No data/schema
migration, no protected-policy or grant changes, so rollback is a clean `git revert`.
