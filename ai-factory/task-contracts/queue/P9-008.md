## Objective
Migrate the `node.config` capability onto the shared manifest (ADR 0007 migration pattern, following P9-007).
The cap's rules (`agent/capabilities/nodeconfig/nodeconfig.go` `validateConfig`) are two CLOSED ENUMS — no
new format needed (existing dialect: `string` + `enum` + `required`).
- **`schema/capabilities/node.config.json`** (capability key `"node.config"`, matching the agent op name +
  the registry convention): fields `mode` (string, `enum:["normal","maintenance"]`, required) and
  `remoteAccess` (string, `enum:["disabled","enabled"]`, required). Reject unknown keys. Regenerate the const
  (`npm run gen:manifests` ⇒ `NODE_CONFIG_MANIFEST`) — it auto-joins `DEFAULT_CAPABILITY_MANIFESTS`.
- **`schema/capabilities/conformance/node.config.json`**: ≥ 12 accept/reject vectors — valid {normal,
  disabled}/{maintenance,enabled} combos; invalid mode/remoteAccess value; absent mode or remoteAccess;
  unknown key; duplicate JSON key (valid final value); non-object.
- **TS + Go conformance tests** (like P9-007): the TS manifest validator AND the Go manifest validator each
  match every vector, AND the Go manifest validator agrees with the AGENT's actual `node.config` validator
  on every vector (drive it through the cap's validate/decode entrypoint). Any disagreement FAILS.
- **Dup-key parity:** if the agent `node.config` decode does NOT already reject duplicate JSON keys (the
  manifest validator does), HARDEN it with `rejectDuplicateObjectKeys` (matching the other caps — a latent
  smuggling gap, as P9-007 found for hostname) so manifest≡agent; include an effective dup-key vector.
- The evaluator's default registry now covers node.config (auto via codegen) — extend the evaluator test to
  evaluate a node.config request.

## Reviewer revision (round 2 — BLOCKING, FOUNDATIONAL: manifests must model the FULL ApplyRequest)
The `/apply` operation `request` IS the capability's full `ApplyRequest` (decoded by `DecodeJSONRequest
[<cap>.ApplyRequest]`), e.g. `{"desired":{"mode":"maintenance","remoteAccess":"enabled"}}`. So for the
evaluator's plan to be submittable AND for conformance to test the agent's REAL entrypoint, every manifest
must model the FULL request, not the inner config. `hostname.json` already does (`{desired: <string>}`);
`timesync.json` + the round-1 `node.config.json` WRONGLY model the inner config. Fix the foundation:
1. **Object-type dialect primitive (governed, TS + Go).** Add `FieldSchema` `{ type:"object", required,
   fields: Record<string, FieldSchema> }` — the validator recurses: reject unknown keys + duplicate JSON
   keys at THIS level, enforce each nested field's presence/type/constraints. Document it in the closed
   type set.
2. **Re-model `node.config.json` AND `timesync.json` as the full request:** a single top-level field
   `desired` of `type:"object"` whose `fields` are the inner config (node.config: `mode`/`remoteAccess`
   enums; timesync: `enabled` bool + `servers` array + the `enabled`⟺`servers` cross-field rule moved under
   the object). Regenerate. `hostname.json` already models `{desired:string}` — leave it.
3. **Conformance against the AGENT's real decode** (both timesync + node.config): vectors are the FULL
   request `{"desired":{...}}` (raw JSON strings so dup-key cases are real); BOTH the manifest validator AND
   the agent path `transport.DecodeJSONRequest[<cap>.ApplyRequest]` (+ `ApplyRequest.Validate`) run each
   vector and MUST agree (manifest≡agent). The round-1 nodeconfig test that unmarshalled `Config` directly
   is the bug — drive the real `ApplyRequest` decode. Harden the cap's request decode for dup-keys if needed
   (so envelope dup-keys are rejected by both).
4. **Evaluator:** `config[capability]` is now the full `{desired:{...}}` request; the manifest validates it;
   the plan operation `request` = the validated full request — directly submittable. Update the evaluator +
   apply-orchestration tests to the full-request shape (consistent across all caps).

This makes the migration foundation correct + consistent (every manifest = the agent's real request, every
conformance = the real entrypoint). It is large but cohesive; if a worker can't land it in one pass, the
orchestrator may split the timesync re-model into a follow-up — but node.config + the object-type primitive +
the real-entrypoint conformance are required here.
