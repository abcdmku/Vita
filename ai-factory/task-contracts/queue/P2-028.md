## Objective
`previewNodeChangeSet(current, desired)` (controller/changeset): the CAPSTONE operator view. Validate
current + desired `NodeChangeSet` (the P0-030 model) via `validateNodeChangeSet`, then compose the EXISTING
subsystem previews into ONE unified report — WITHOUT synthesizing fake data. The four subsystems and their
previews: `nodeConfig`→`previewNodeConfigChange` (P2-020), `services`→`previewServicesChange` (P2-026),
`accounts`→`previewAccountsChange` (P2-027), `capsules`→`previewCapsuleChange` (P2-018).

### Per-subsystem handling rules (authoritative — learn from P2-020: NEVER synthesize a non-empty baseline)
For each of the four subsystem keys, classify by presence in current/desired:
- **present in BOTH** ⇒ run that subsystem's `previewXChange(current[k], desired[k])`; carry its result +
  flags under `subsystems[k]` with `kind: "changed"|"unchanged"` derived from the sub-result.
- **only in desired** (newly managed) ⇒ `kind: "added"`; run the subsystem preview with the EMPTY-VALID
  config of that subsystem as the current side — `{ services: [] }`, `{ accounts: [] }`,
  `{ capsules: [] }` are VALID empty configs (explicit empty list), so the preview reports everything as
  added and still runs the subsystem's own validation. For `nodeConfig`, an absent current is passed to
  `previewNodeConfigChange` as the model permits (P2-020 already handles its sections internally) — do NOT
  hand-build node-config sub-resources.
- **only in current** (no longer managed) ⇒ `kind: "removed"`; run the subsystem preview with the
  empty-valid config as the DESIRED side (symmetric).
- **absent in both** ⇒ omit the subsystem.
NEVER fabricate a non-empty placeholder (no fake service/account/capsule/subvolume) — only the empty-valid
config of that subsystem may stand in for an absent side.

`summary` aggregates the security/privilege signals the sub-previews surface: `wideningInbound`,
`weakensRetention` (from nodeConfig), `newlyEnabledServices` (P2-026 newlyEnabledCount), `newlyEnabledAccounts`
+ `accountGroupChanges` (P2-027). Return `{ ok: true, subsystems, summary } | { ok: false, rejections }`.
Fail-closed: invalid either change-set ⇒ typed rejection (no report, no throw); a subsystem sub-preview that
returns invalid ⇒ surface its rejections (fail-closed), never a throw.

## User value
The single "what does this whole-node change-set do" view (FR-005/006) — every subsystem's diff + every
privilege/security flag in one operator action, on validated inputs only.

## Non-goals
- No apply, no agent call, no network. Compose P0-030 + the four subsystem previews. Do NOT modify any of
  them — import + compose. No fabricated baseline data.

## Dependencies

## Acceptance tests
`acceptance_command` — `changeset-preview.test.ts`: two valid change-sets with several subsystems ⇒ a unified
report with correct per-subsystem sub-diffs; a newly-added services subsystem ⇒ `kind:"added"` with all
services added AND the subsystem's validation still enforced (an invalid added service ⇒ fail-closed); a
removed subsystem ⇒ `kind:"removed"`; the summary aggregates wideningInbound + newlyEnabledServices +
newlyEnabledAccounts + accountGroupChanges from the sub-previews; invalid either change-set ⇒ typed
rejection (no throw); hostile input ⇒ fail-closed (external-counter probe). Orchestrator runs `npm run typecheck`.

baselines (only empty-valid configs for absent sides). Aggregates sub-preview flags faithfully. Strict TS
