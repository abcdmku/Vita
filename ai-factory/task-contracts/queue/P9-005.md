## Objective
Add the Go counterpart to the TS `compileCapabilityValidator`, and — because raw regex CANNOT be kept
semantically equal across JS and Go RE2 (e.g. JS `$` matches before a trailing `\n`, Go's does not; `.`,
`\s`, `\b`, Unicode all differ) — **replace the dialect's raw `pattern` with a closed set of named FORMAT
primitives** implemented identically (as structured, non-regex checks) in BOTH planes. This is the
parity-safe-by-construction dialect ADR 0007 needs; the conformance corpus (P9-006) then locks it in.

### Dialect change (both planes — this is the source-of-truth change, do it in TS + Go + the JSON)
- `FieldSchema` string type drops `pattern`. Its constraints become: `maxLength`, `enum`, `lowercase`,
  `noInlineSecrets`, and `format` — a CLOSED enum, for now exactly `"hostnameRFC1123"`. (A new format is a
  governance decision to extend the closed set, implemented identically in both planes + conformance-tested.)
- **`hostnameRFC1123`** — a STRUCTURED check (NO regex), identical in TS + Go: non-empty; total length ≤ 253;
  split on `.`; ≥1 label; each label 1–63 chars, first+last char `[A-Za-z0-9]`, interior `[A-Za-z0-9-]`; the
  whole string only `[A-Za-z0-9.-]`; REJECT a value of all-numeric dotted-quad IPv4 form
  (`^[0-9]+(\.[0-9]+){3}$` — checked structurally, not via the dialect). This subsumes the old pattern +
  `rejectIpv4Form` with ZERO regex-engine dependence.
- `schema/capabilities/timesync.json` `servers.items` becomes `{ "type":"string", "format":"hostnameRFC1123",
  "maxLength":253, "lowercase":true, "noInlineSecrets":true }` (remove `pattern`). Regenerate the TS const
  (`npm run gen:manifests`). Behavior is UNCHANGED vs the merged manifest (hostnames accept; `10.0.0.1`
  rejects via the IPv4-form rule; `::1`/bad chars reject; case-insensitive dedup) — update the P9-002/003 TS
  tests to the `format` shape, keep their assertions.
- Number handling: parse JSON numbers with JS-`float64` semantics so TS ≡ Go — underflow (`1e-1000`) ⇒ the
  finite value `0` (accepted by an integer field allowing 0), overflow (`1e400` ⇒ ±Inf) ⇒ not a safe integer
  ⇒ reject; match `Number.isSafeInteger`. The TS + Go loaders REJECT any unknown string-schema key (so a
  stray `pattern` fails closed).

### Go package `agent/internal/capmanifest/`
- `LoadManifest(raw []byte) (Manifest, error)`: validate the manifest structure fail-closed against the
  (new) dialect (closed `format` set, no `pattern`; reject unknown keys / bad cross-field refs / unsupported
  version).
- `Validate(manifest Manifest, requestJSON []byte) error`: reject duplicate JSON keys + unknown request keys;
  enforce presence (required-absent ⇒ reject; absent ≠ present-zero/empty), type, `maxLength`, `enum`,
  `format` (the structured `hostnameRFC1123` check), `lowercase` canonicalization before `uniqueItems`,
  `noInlineSecrets` (PEM / `data:`-anywhere / long base64-or-base64url), `minimum`/`maximum`/`minItems`/
  `maxItems`, then the cross-field rules. Fail-closed; never panic. **Decision parity with the TS validator
  on the same manifest+request is the contract** (P9-006 proves it on a shared corpus).

## Reviewer revision (round 4 — BLOCKING, from P9-005.review.md — Unicode case-fold bypass)
The `hostnameRFC1123` format (and the `[A-Za-z0-9.-]`-only charset) is currently checked AFTER `lowercase`
canonicalization in BOTH planes (`strings.ToLower(raw)` in Go; `value.toLowerCase()` in TS) — so a non-ASCII
char that case-folds to ASCII slips through (`"K.example"` — the Kelvin sign — folds to `k.example`).
The conformance corpus would NOT catch this (both planes agree on the wrong behavior). Round 4: in BOTH
planes, run the format + charset validation on the RAW value (reject any char outside `[A-Za-z0-9.-]` and any
non-ASCII before any folding); apply `lowercase` ONLY to derive the canonical value used for `uniqueItems`
dedup (and the returned/stored value). Add a regression on BOTH planes: `"K.example"` (and another
non-ASCII case-folding char) is REJECTED. Keep all other behavior identical.
