## Objective
Phase 5 (spec §21 "Files and shared folders" + "User and household roles"), files arc slice 2: extend the
agentd-mediated files capability shipped by P1-065 from a single owner-scoped folder to **SHARED folders with
per-role access grants**. A shared folder is one whose access mode is decided by the calling principal's
HOUSEHOLD ROLE — this slice covers two roles from spec §11: `owner` (read-write) and `household-member`
(by-grant, default read-only). The privileged Go agent (`agentd`) remains the SOLE mediator and now selects the
EFFECTIVE access for each request from a `{role → access}` policy carried on the grant and a principal→role binding
held in agentd's OWN validated config — NEVER from any role/principal field supplied in the request. The
unprivileged TypeScript runtime still proposes only `{op, grant, path, [data]}`; it cannot name its own role and
cannot widen its own access. Fail-closed throughout.

Concretely, building strictly on the P1-065 surface (`agent/capabilities/files/{files,scope}.go`,
`agent/transport/server.go` `/files` route, `sdk/typescript/src/files-grant.ts`,
`os/.../ts/vita/files-client.ts`, `main.ts`):

- **Grant shape extension (backward-compatible, re-validated, manifest-driven).** Today a `Grant` is
  `{ name, root, access: "read-only" | "read-write" }` (`files.go:52`). Add an OPTIONAL shared-folder facet so a
  grant can declare PER-ROLE access instead of (or in addition to) the flat `access`:
  `{ name, root, shared?: true, roles?: { owner: "read-only"|"read-write", "household-member":
  "read-only"|"read-write" } }`. Keep the flat `access` working unchanged for the existing
  `runtime-files` / `runtime-files-ro` grants (absent ≠ empty — a grant WITHOUT `shared`/`roles` behaves exactly as
  P1-065; the prior boot chain must be byte-for-byte unaffected). Decode STRICTLY via the existing
  `jsonsafe.DecodeStrict` (`files.go:58-66`); reject a grant that sets BOTH a flat `access` and `roles`, a `shared`
  grant missing `roles`, an unknown role key, a role value that is not one of the two access modes, or a `roles`
  map that omits a required role — fail-closed at `NewHandler`/`resolveGrant` time (a misconfigured grant must NOT
  silently fall open). Define the shared TS types in `sdk/typescript/src/files-grant.ts` (the single shared source —
  no duplicated literal) and the Go decode/validate in the new `agent/capabilities/files/shared.go`.

- **Principal → role binding lives in agentd config, NOT the request (the security core).** Add a
  `Principals []Principal` (or equivalent `{ principalKey, role }` binding set) to the files `Options`
  (`files.go:100`) and the transport `Config` (`server.go:80-81`), wired from `agent/cmd/agentd/main.go` alongside
  `FilesGrants`. The principal key is derived ONLY from agentd-side connection context (the authenticated unix-peer
  identity already proven by `ListenAuthenticatedUnixSocket` / `UnixPeerAuthConfig` / SO_PEERCRED, `server.go:201`,
  `peercred_linux.go:40` — reuse it, do NOT invent a second auth path) — agentd maps that peer to a configured role.
  The request envelope gains NO `role`/`principal`/`as` field; if such a field is present it is rejected by the
  strict decoder (unknown key). A request whose resolved principal has NO configured role gets the DEFAULT
  least-privileged role (`household-member`) — never `owner` by default, never owner-by-absence. The runtime CANNOT
  assert a role: agentd reads the binding from its own validated config, never from request text.

- **Effective-access resolution (`shared.go`, pure + well-tested).** Add
  `EffectiveAccess(grant resolvedGrant, role Role) (Access, bool)`: for a flat grant it returns the flat access for
  any role; for a shared grant it returns `roles[role]`, and returns `ok=false` (→ fail-closed reject) for a role
  with no entry. The write gate in `Handle` (`files.go:216`) becomes: resolve effective access for the request's
  PRINCIPAL role, then reject a `write` unless that effective access is `read-write` (new reject reason
  `role_forbidden` distinct from the existing `read_only_grant`; `read_only_grant` stays for the flat-RO grant so the
  P1-065 marker is unchanged). `list`/`read`/`stat` are allowed for any role that has ANY (read-only or read-write)
  effective access on the grant; a role with NO entry on a shared grant is rejected `role_forbidden` for every op.
  A no-op / always-`read-write` resolver MUST fail the suite. Path resolution stays exactly P1-065:
  `ResolveWithinScope` (traversal- + symlink-safe, `scope.go:14`) and the atomic temp+rename write
  (`files.go:425`) are reused verbatim — this slice adds ONLY the role gate, no new FS primitive and no new
  traversal logic.

- **Per-grant data layout unchanged.** A shared grant still maps `name`/`root` to
  `/var/lib/vita/files/<root>/<name>` exactly as `resolveGrant` does today (`files.go:488-507`); agentd still owns +
  creates the dir (`ensureGrantRoot`, `files.go:374`); the runtime never mkdirs. "Shared" here means
  role-scoped ACCESS to one agentd-owned folder, NOT a new on-disk location. NO per-user uid/gid ownership split this
  slice (single agentd-owned tree, access decided in agentd).

- **Unprivileged on-device wiring + MEASURED marker.** Configure TWO additional shared-folder grants in
  `main.go` whose effective access for the runtime's OWN configured principal differs by role, so role-scoping can be
  PROVEN end-to-end on a single-user smoke boot WITHOUT standing up a second OS user:
  - one shared grant where the runtime principal's role resolves to `read-write` (e.g. role=`owner`) — prove a real
    write→list→read-back (bytes match)→stat round-trip via agentd;
  - one shared grant where the runtime principal's role resolves to `read-only` (e.g. role=`household-member`) — prove
    `read`/`list`/`stat` SUCCEED but a `write` is REJECTED `role_forbidden`.
  Add the thin client surface in `files-client.ts` only if the op set changes — it does NOT (the runtime still calls
  `write`/`read`/`list`/`stat` with `{grant, path}`), so the client likely needs only the updated grant TYPES
  imported, no new method. Emit in `main.ts`:
  `VITA-FILES-SHARED: grant=<rw-shared-name> role=owner op=write+read+list+stat bytes=<n> roundtrip=OK status=OK`
  (gated on the real write→read-back byte match, NEVER synthesized) and
  `VITA-FILES-SHARED-REJECT: reason=role_forbidden status=OK` (the household-member-role write is denied);
  `VITA-FILES-SHARED-ERROR: status=FAILSAFE` on any inconsistency. Keep ALL prior markers, including the unchanged
  P1-065 `VITA-FILES:` roundtrip and its two `VITA-FILES-REJECT:` (path_traversal, read_only_grant).

## User value
The node becomes a real shared personal data product for a HOUSEHOLD, not just a single owner: a folder can be
shared with household members at a role-appropriate access level (the owner reads and writes; a household-member can
be limited to read-only), and the privileged agent enforces that role boundary. The unprivileged runtime never holds
raw FS access and — critically — cannot assert or widen its own role: agentd alone binds principal→role from its
validated config and selects the effective access, fail-closed. This delivers spec §21 Phase 5 "shared folders" +
"User and household roles" (FR-016 roles/grants, FR-018 data services) on top of the P1-065 files substrate, and is
the role-scoping foundation later per-application data-capability work builds on.

## Non-goals
NO new roles beyond `owner` + `household-member` this slice (administrator / restricted-member / guest / service
roles from spec §11 are later slices). NO multi-OS-user provisioning, NO per-user uid/gid ownership split of the data
tree (single agentd-owned folder; access decided in agentd). NO directory create/delete/rename/move, NO new file ops
(still list/read/write/stat of FILES, same op set as P1-065). NO quotas/encryption (storage arc). NO controller UI,
NO role-management RPC (roles are agentd config this slice, not runtime-mutable). NO sharing a folder ACROSS capsules
and NO cross-grant access. NO remote/network file access (local socket only). NO change to `ResolveWithinScope`, the
atomic-write primitive, the size cap, or any P1-065 marker. The runtime never receives a raw FS path, never an
`--allow-read`/`--allow-write` for the data root, and never a way to name its own role; agentd composes/acts ONLY
from the re-validated request + its own validated grants + its own principal→role binding, never from raw runtime
text used as a path OR as a role.

## Performance & security constraints
- **Unprivileged runtime, mediated FS, agentd-asserted role (spec §3.4, §7.1, §11):** the runtime gets NO raw FS
  access and NO way to name its own role/principal. agentd binds principal→role from its OWN validated config
  (keyed off the authenticated unix-peer identity, reusing the existing SO_PEERCRED path — no second auth path) and
  selects the effective access; it acts ONLY from the re-validated request + its own grants + its own binding, NEVER
  from raw runtime text used as a path OR a role.
- **Fail-CLOSED everywhere, default-least-privilege:** misconfigured grant (both flat+roles / missing roles / unknown
  role / bad role value / missing required role) rejected at startup; unknown grant / out-of-scope / traversal /
  symlink-escape / oversize / malformed / role-with-no-entry / write-under-RO-role → rejected with a sanitized
  reason. A request with no resolved role defaults to `household-member` (least privilege), NEVER `owner`. A guard
  over untrusted input MUST NOT throw at the trust boundary (a throw is a DoS — return a rejection); prove with a
  malformed/cyclic regression. No owner-by-absence, no role-by-request, no flat-access fall-open for a shared grant.
- **No regression of the P1-065 floor:** `ResolveWithinScope` (traversal- + symlink-safe), the atomic
  `os.CreateTemp(dir, ".name-*.tmp")` → Sync → Close → Rename single-commit-point write (mode 0600, no predictable
  temp), the ≤ 8 MiB size cap, and strict dup-key-rejecting decode are reused VERBATIM — this slice adds only the
  role gate and the shared-grant decode. The existing flat grants and all prior markers behave identically.
- **No keys/secrets** — TEST principals/grants only; never commit or generate production key material; signing /
  TPM / recovery / mesh keys remain OWNER-HELD (§16) and are not touched here.
- **No remote imports** in the TS types/client; lockfiles mandatory; no package lifecycle scripts; no FFI/native
  addons. R2 → reviewer gate (`npm run review` must APPROVE before merge, per the standing R2/R3/R4 gate).
