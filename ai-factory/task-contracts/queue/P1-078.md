## Objective
Phase 3 (spec §21 "Storage durability"), storage-health arc slice 1: give the runtime (and later the controller
dashboard) a READ-ONLY view of the node's **storage health** and a **hardware capability inventory** — the
observability foundation the durability arc (LUKS2/TPM-sealing, btrfs snapshots, power-loss restore) builds on. The
narrow privileged Go agent (`agentd`) collects this state from the kernel/sysfs and exposes it in the existing
`/state` read path; the UNPRIVILEGED TypeScript runtime only READS it over the `/run/vita-agent/agentd.sock` unix
transport (ADR-0008, P1-035). This slice is **purely additive + read-only — NO mutation, NO new privileged write
surface** (mirrors P1-047's `capsuleWorkloads` health-into-`/state` pattern, not a transactional capability).

Concretely:

- **New read-only collector `agent/internal/storagehealth/storagehealth.go`** (NOT a transactional capability — no
  Apply/Undo, no `/apply` registration). A `Collect(ctx, roots) (Report, error)` that reads kernel/sysfs/statfs and
  returns a deterministic snapshot. The collector takes its read roots as fields (default `/proc`, `/sys/block`,
  `/proc/mounts` or the statfs targets) so tests inject fixtures — exactly the `linuxDiscoveryRoots.withDefaults()`
  pattern in `agent/hardware/discover_linux.go`. Two parts:
    - **Storage health** (`storageHealth`): for each relevant mount/device, report
      `{ device, mountPoint, fsType, totalBytes, usedBytes, availableBytes, usedPercent, rotational, nvme,
      readOnly, status }` where `status ∈ {ok, degraded, unknown}`. Usage comes from `statfs`/`/proc/mounts`
      (blocks×fragment-size math); `rotational`/`nvme` from `/sys/block/<dev>/queue/rotational` + the `nvme` name
      prefix (REUSE the proven helpers/derivation in `hardware/discover_linux.go:readBlockSizeMiB`/`readSysfsBool`,
      do not re-roll a looser copy). "SMART-ish" = a best-effort device-health signal from sysfs ONLY (e.g. a
      block device flagged read-only / a near-full filesystem `usedPercent ≥ a fixed threshold` → `degraded`); a
      missing/unreadable signal → `status=unknown` (NOT an error, NOT `ok`). NO `smartctl`/no extra binaries/no ioctls
      this slice — sysfs + statfs only, so it runs unprivileged-read and is deterministic in CI fixtures.
    - **Hardware inventory** (`hardwareInventory`): `{ arch, cpuCores, cpuModel, memTotalBytes, disks: [{name,
      sizeBytes, rotational, nvme}] }` — REUSE the existing `hardware.Capabilities` discoverer
      (`agent/hardware/`: `CPUCapabilities`, `MemoryCapabilities`, `[]StorageDevice`) rather than re-parsing
      `/proc/cpuinfo`/`/proc/meminfo`; this slice MAPS that already-collected inventory into the read model (and may
      widen MiB→bytes consistently). Do not duplicate the cpuinfo/meminfo parsers.

- **Determinism + read-only (spec §8.2 spirit):** `Collect` performs NO mutation and NO network. Output is stable for
  the same fixture inputs: mounts/devices/disks SORTED by a fixed key (device then mountPoint; disk name); bytes are
  integers (no float rounding that varies). Two collects over an unchanged fixture are byte-identical. A transient
  unreadable signal yields `unknown`, never a panic and never a fabricated value.

- **`/state` extension (read path only).** Add `storageHealth` and `hardwareInventory` to the `/state` JSON alongside
  `capabilities` + `capsuleWorkloads` (see `agent/transport/server.go:handleState` ~706 and the
  `capsuleWorkloadSnapshot()` ~748 pattern). Wire a snapshot func on the handler (e.g.
  `storageHealth func() storagehealth.Report`) defaulting to the linux collector, overridable in tests via a Config
  hook (mirror P1-047's `Config.CapsuleWorkloads` + `capsuleWorkloadSnapshotFunc`). On collector error, emit an
  inline `{"error":"<code>"}` for that section (the existing `stateCapabilityError` discipline) — `/state` as a whole
  MUST still return 200 with the other sections (fail-soft on the READ path; never 500 the whole snapshot because one
  signal was unreadable). NO change to `/apply` or any capability registry.

- **Shared read model `sdk/typescript/src/storage-health-model.ts`** — the typed `StorageHealth` /
  `HardwareInventory` shapes + a `validateStorageHealthState(input)` that `safeNormalize`s untrusted `/state` input
  and fail-CLOSED rejects malformed/unknown-field/wrong-type/oversized input WITHOUT throwing (follow
  `sdk/typescript/src/node-health-model.ts` exactly: `safeNormalize` → reject on `!ok`, `rejectUnknownFields`,
  non-negative-integer/enum checks, inline-key-material rejection, `Object.freeze`, returns `{ok:false,errors}` not a
  throw). This is the single source of the shape so the runtime + a future controller dashboard share it (no
  re-invention).

- **Unprivileged on-device wiring (`main.ts`).** After the existing markers, the runtime reads `/state` over the
  existing unix transport (it already does for capsule health, ~1972), validates the two sections with
  `validateStorageHealthState`, and emits a MEASURED marker proving real collected data — gated on the boot disk's
  filesystem actually appearing with a sane `usedPercent` AND the inventory reporting `arch`/`cpuCores≥1`/
  `memTotalBytes>0` (NEVER synthesized — the marker is the real /state read, the boot is the floor). The runtime keeps
  its AF_UNIX-only Deno sandbox (no new FS/network allow).
  Markers: `VITA-STORAGE-HEALTH: mounts=<n> arch=<a> cores=<c> memBytes=<m> rootUsedPct=<p> status=OK` (gated on a real
  validated `/state` read with the root fs present + a sane inventory); `VITA-STORAGE-HEALTH-ERROR: status=FAILSAFE`
  (validation/read failed → the runtime reports the failsafe, does NOT crash the chain). Keep ALL prior markers.

## User value
The node can SEE its own storage and hardware: how full each filesystem is, whether a disk is rotational/NVMe/
read-only or looking degraded, and what CPU/memory/disk/arch it actually runs on — read provably without any privilege
to mutate. This is the observability substrate the storage-durability arc (encryption/sealing, btrfs snapshots,
power-loss restore, capacity planning) and an operator storage dashboard depend on; it is the first slice of spec §21
Phase 3 "Storage durability" delivered on-device. A near-full or read-only filesystem becomes visible BEFORE it causes
a failure.

## Non-goals
NO mutation of ANY kind — no formatting, mounting, resizing, snapshotting, encryption, sealing, or quota change (those
are later durability slices, each their own R3 capability). NO new transactional capability / `/apply` change / agentd
write surface. NO `smartctl`/`hdparm`/`nvme-cli`/extra binaries and NO device ioctls (sysfs + statfs ONLY this slice —
keeps it deterministic + unprivileged-read; real SMART attribute reads are a deferred slice). NO TPM/LUKS/btrfs logic.
NO controller UI (the shared model is built so the dashboard can consume it later, but no UI here). NO per-disk
temperature/wear telemetry. NO secrets/keys — signing/TPM/recovery/mesh keys are OWNER-HELD (§16); none are read,
generated, or committed. agentd composes the report ONLY from kernel/sysfs reads, never from raw runtime text.

## Performance & security constraints
- **READ-ONLY, unprivileged-consumable (spec §3.4, §7.1):** the collector performs NO mutation, NO network, NO extra
  binaries, NO ioctls — sysfs + statfs reads only; the runtime only READS `/state` over the unix socket and gets NO
  new FS/network allow. No new privileged write surface; no `/apply`/registry change.
- **Deterministic (spec §8.2 spirit):** same fixture inputs → byte-identical report; mounts/devices/disks sorted by a
  fixed key; integer bytes (no nondeterministic float rounding).
- **Fail-CLOSED / fail-soft on the read path:** an unreadable signal → `status=unknown` (never fabricated `ok`, never a
  panic); a collector error → inline section error while `/state` still serves the rest (a read-path error must not
  500 the whole snapshot or crash agentd). The SDK validator MUST NOT throw on hostile input (a throw at the trust
  boundary is a DoS — return `{ok:false}`); prove with a cyclic/accessor/`__proto__` regression.
- **No secrets/keys:** read no key/seed/credential material; the SDK model rejects inline key material (reuse the
  node-health-model secret-field/inline-material rejection). TEST data only; never commit/generate production material
  (§16: signing/TPM/recovery/mesh keys are owner-held).
- **No remote imports** in the TS model/wiring; lockfiles mandatory; no package lifecycle scripts; no FFI/native
  addons. R2 → reviewer gate (`npm run review` must APPROVE before merge, per the standing R2/R3/R4 gate).
