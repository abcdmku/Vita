## Objective
An ADDITIVE proof-of-concept for ADR 0007 (`architecture/adr/0007-shared-capability-schema.md`) — does NOT
touch the agent/TCB or any existing model; it stands alone to prove the shared-manifest approach handles
real capability rules including CROSS-FIELD invariants. In `sdk/typescript/src/capability-manifest.ts`:
- **Dialect types** for a restricted, CLOSED capability manifest:
  - `FieldSchema` = a discriminated union by `type`: `"string"` (optional `pattern`, `maxLength`, `enum`,
    `noInlineSecrets`), `"integer"` (`minimum`/`maximum`), `"boolean"`, `"array"` (`items: FieldSchema`,
    `minItems`/`maxItems`, `uniqueItems`). Each field has `required: boolean` (explicit-presence: a required
    field absent ⇒ reject; the dialect distinguishes absent from a present zero/empty).
  - `CrossFieldRule` = a CLOSED, small set keyed by a boolean control field: `requireNonEmptyArrayWhenTrue`
    and `requireEmptyArrayWhenFalse` (control: a boolean field name, target: an array field name). This is
    the bounded way the dialect expresses invariants like timesync `enabled`⟺`servers` WITHOUT becoming a
    general language. (If a cap ever needs an invariant outside this closed set, that is a governance
    decision to extend the dialect — document this limitation in the file header.)
  - `CapabilityManifest` = `{ capability: string; fields: Record<string, FieldSchema>; crossFieldRules:
    CrossFieldRule[] }`.
- `compileCapabilityValidator(manifest): (input: unknown) => { ok: true; value } | { ok: false; rejections }`
  — `safeNormalize` the input first; reject unknown keys; validate each field per its schema (presence,
  type, constraints, §13.1 noInlineSecrets via PEM/`data:`/long-base64 detection); apply the cross-field
  rules; fail-closed, never throws.
- **A concrete manifest constant `TIMESYNC_MANIFEST`** mirroring the agent timesync rules: `enabled` boolean
  required; `servers` array of strings (each a hostname `^[A-Za-z0-9.-]+$` or IP-literal, bounded, unique),
  with `requireNonEmptyArrayWhenTrue(enabled, servers)` + `requireEmptyArrayWhenFalse(enabled, servers)`.

## User value
A concrete, additive demonstration (de-risking the owner's ADR 0007 decision) that ONE declarative manifest
can drive fail-closed validation matching a real capability's rules — including the cross-field invariant
that a naive JSON-Schema dialect cannot express — without re-implementing per-cap logic by hand. The
foundation a closed config→plan evaluator (P9-001) would consume.

## Reviewer revision (round 2 — BLOCKING, from P9-002.review.md)
1. **IP-literal validation drifts from the agent.** The hand-rolled `TIMESYNC_SERVER_PATTERN` rejects valid
   IP literals the Go agent (`netip.ParseAddr`) accepts — e.g. IPv4-mapped IPv6 `::ffff:192.0.2.1`. Round 2:
   give the dialect a closed string `format` primitive `"hostnameOrIp"` backed by a ROBUST IP-literal
   validator accepting IPv4 (dotted quad, octets 0–255, no leading zeros) AND IPv6 including `::`
   compression and IPv4-mapped `::ffff:x.x.x.x`, plus RFC-1123 hostnames. Add accepted-corpus cases:
   `::ffff:192.0.2.1`, `2001:db8::1`, `::1`, `10.0.0.1`, `pool.ntp.org`. Document in the file header that
   EXACT Go-`netip` parity is precisely what ADR 0007's shared/generated validator delivers — this PoC
   approximates it and the residual drift is the motivation for the ADR (call this out explicitly).
2. **`noInlineSecrets` under-detects.** `data:` is matched only at string START and long-base64 misses
   base64url. Round 2: detect `data:` ANYWHERE (case-insensitive), PEM (`-----BEGIN`), and a long blob over
   BOTH standard base64 AND base64url (`[A-Za-z0-9+/_-]{N,}`). Add a regression: a server string with an
   embedded `data:`/base64url blob MID-STRING is rejected.
