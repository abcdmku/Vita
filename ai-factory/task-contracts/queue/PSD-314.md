## Objective
US-only raw keycodes are not a usable OS. Add an **XKB-backed layout translation core** that turns a
(keycode + modifier state + configured layout) into the correct **printable character** for the
selected layout, with **basic dead-key / compose** support, so the CEF OSR host can deliver real
`char` key events instead of US-only ASCII. This builds directly on the verified evdev→VK/DOM
keycode+modifier table from **PSD-301** (`sdk/typescript/src/ui-kits/cef-keymap.ts`) and the routed
key path from **PSD-300** — those resolve *which* key and *which modifiers*; this slice resolves
*which character* under a chosen layout.
- Ship the translation core as a **TS source-of-record module** `sdk/typescript/src/ui-kits/cef-layout-map.ts`
  (the form the test exercises headlessly — CEF cannot be linked in CI), encoding a small **vendored
  keymap matrix** for at least two layouts: **`us`** (QWERTY) and **`de`** (QWERTZ). Each layout maps
  the DOM `code` (e.g. `KeyA`, `KeyZ`, `KeyY`, `Digit1`) + the active modifier state (shift/altgr/caps)
  to its printable character (`us` `KeyZ`→`z`/`Z`; `de` `KeyZ`→`y`/`Y` and `KeyY`→`z`/`Z`; `de`
  `Digit1`→`1`/`!`, AltGr where applicable). CapsLock affects letters only, not digits/symbols
  (consistent with PSD-301).
- **Dead-key / compose**: a small **pure state machine** holds a pending dead key (e.g. `de` `´`/`^`
  accent, or US-international style) and folds the next printable key into a **single composed
  character** (`´` then `e` → `é`); a non-composable follow-up emits the dead key's spacing form then
  the base char (deterministic, documented), and a second press of the dead key emits its spacing
  character. The composed result is a single `char` ready for `CefBrowserHost::SendKeyEvent` as a
  `KEYEVENT_CHAR`.
- **Configurable layout**: the active layout is selected by a `keyboard.layout` setting value
  (`"us"` | `"de"`) passed into the translator; **switching the layout changes the produced
  character** for the same keycode. The settings/control-plane wiring (reading `keyboard.layout`)
  and the actual `SendKeyEvent` char delivery in `spikes/cef-osr/osr_host.cc` are **thin
  downstream wiring** consuming this core — NOT built or tested here.
- **Unknown / unmapped (code, layout) pairs are dropped** (translator returns null / no char) —
  fail-closed, never a bogus character, matching the PSD-301 unknown-evdev contract.
- Mirror the PSD-301 lockstep convention: place the Rust-facing vendored keymap data under
  `packages/compositor-core/src/input/` (the `compositor-rust` area) as a CEF-free, I/O-free data
  module with a header comment pointing at the TS source-of-record so the two encodings stay in
  lockstep; the **authoritative automated check is the TS test**.
- Pure and deterministic: same `(code, modifiers, layout, compose-state)` in → byte-identical char
  out. No DOM, no rendering, no CEF link, no ambient I/O.

## User value
Moves the live CEF desktop from a US-only keyboard toy toward a real OS: users on non-US layouts get
the **correct characters** (incl. accented characters via dead-key compose), driven by a
`keyboard.layout` setting. The gnarly, error-prone layout + compose rules land as an independently
verified unit so the later CEF `SendKeyEvent` char-delivery and control-plane wiring slices stay thin
over a table already proven correct.

## Non-goals
- NO `CefBrowserHost::SendKeyEvent` call / no CEF link / no edit to `osr_host.cc` (a later wiring
  slice consumes this core). NO control-plane/settings persistence code (only accept a layout value).
- NO full IME (no candidate windows, no CJK input methods, no preedit UI) — dead-key/compose baseline
  only. NO key-repeat policy, NO mouse/pointer/touch.
- NO reading `/dev/input`, no device/locale I/O, no loading system XKB files at runtime (the keymap is
  vendored data). NO DOM/CSS/rendering. Do not weaken or edit any existing test, and do not change the
  PSD-301 keycode table or the PSD-300 routing shapes — consume them, additive only.

## Acceptance
`acceptance_command` passes: `npm run typecheck` is clean and the Node test
`sdk/typescript/test/ui-kits/cef-layout-map.test.ts` asserts concrete entries (no vacuous glob, so an
empty/stub branch fails):
- a keycode + modifier resolves to the **correct character for ≥2 layouts** — e.g. `us` `KeyZ`→`z`,
  `Shift`→`Z`; `de` `KeyZ`→`y`, `KeyY`→`z`; `de` `Digit1` shift→`!`;
- a **dead-key compose** path produces a **single composed character** (`´` then `e` → `é`), and the
  non-composable / double-dead-key fallbacks emit the documented spacing form;
- an **unknown / unmapped** `(code, layout)` pair is **dropped** (returns null/no char);
- **switching the layout** (`keyboard.layout` `us`→`de`) changes the produced character for the same
  keycode.
Pure, headless, deterministic — no CEF link needed for the translation test.

## Security/constraints
- Pure/deterministic, no ambient I/O, no device/locale access, no network. Vendored keymap data only
  (no runtime XKB file loading). No remote imports; `package-lock.json`/`Cargo.lock` unchanged; no
  package lifecycle scripts; no FFI/native addons in the TS module. The Rust-side keymap data under
  `packages/compositor-core/src/input/` is a CEF-free, dependency-free leaf so it cannot widen the
  compositor's attack surface. Fail-closed on unknown input (drop, never emit a bogus char).

  vendored mirror data, the two encodings agreeing on the documented matrix and cross-referenced by
