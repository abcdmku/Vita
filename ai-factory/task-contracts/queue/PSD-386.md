## Objective
Headless, deterministic **view-model** for the flagship desktop's **global top menu bar** — the
`File / Edit / View / Go / Window / Help` strip rendered next to the `Vita.ts` brand in
`ui_kits/desktop/index.html` (`<div class="v-menubar"> … <div class="v-menus"><span>File</span>…`,
visible in `cef-live.png`). Today that strip is **static markup with no model**:
`ui_kits/desktop/viewmodels/SurfaceMenu.ts` is the desktop **context** menu (right-click surface),
NOT the top bar. Build the missing top-bar model on the existing command-registry + SDK ports only —
injected ports, NO platform internals, NO DOM/rendering.
- **State / tree:** a per-app menu tree — top-level menus (`File`, `Edit`, `View`, `Go`, `Window`,
  `Help`) each with ordered items; each item has a stable `id`, `label`, optional `accelerator` label
  (display-only string, e.g. `Cmd+N`), `disabled` enable/disable state, and optional submenu. The
  active app id selects which tree is exposed (fall back to a base/desktop tree).
- **Navigation:** `openMenu(menuId)` / `closeMenu()` / `highlight(itemId)` produce a **frozen**
  `MenuBarSnapshot` (open menu, highlighted item, full tree). Disabled items are **non-actionable** —
  they appear in the snapshot but `select` on them is rejected (fail-closed), never silently no-op'd.
- **Action dispatch:** `select(itemId)` routes the chosen command id into the injected
  command-registry / host: it maps the menu item to a command id and returns a **frozen**
  `MenuActionResult` carrying the typed `CommandAction` the registry produced (launch via
  `launcher.intent`, window ops via `wm.intent`, settings via `settings.write`). Unknown item id,
  unknown/unavailable command id, or a disabled item **rejects** with a structured error
  (`{ ok:false, reason, error:{ code, message, path } }`) — fail-closed, never throws.
- Build on the existing **command-registry view-model**
  (`ui_kits/desktop/viewmodels/command-registry.ts` — `createCommandRegistry`, `execute(id, ctx)`
  returning a typed `CommandAction`; `isAvailable`/`available` for enable state). Route `select`
  through `registry.execute`; an item whose command is not `isAvailable` is rendered `disabled` and
  rejects on select. Mirror the result/deny shape and the `Object.freeze` discipline used in
  `SurfaceMenu.ts` (`SurfaceMenuResolveResult` / `SurfaceMenuDeniedResult`).
- Put the code under `ui_kits/desktop/viewmodels/menu-bar.ts` and tests under
  `sdk/typescript/test/ui-kits/menu-bar.test.ts`.
- Import the SDK exactly as `ui_kits/desktop/viewmodels/SurfaceMenu.ts` /
  `ui_kits/desktop/viewmodels/files.ts` do (relative `../../../sdk/typescript/src/desktop-sdk/index.ts`);
  use ONLY public exports.

## User value
Turns the flagship's static top menu bar (`File/Edit/View/Go/Window/Help`) into real, testable
desktop behavior — the interaction logic the CEF-rendered HTML hydrates against, with menu commands
actually routed to launch/window/settings instead of being dead markup.

## Non-goals
- NO DOM/CSS/rendering/CEF; NO platform internals; NO new visual design (the `v-menubar` HTML is the
  design of record). Do NOT re-implement the command-registry or SDK ports — consume them. NOT the
  context menu (`SurfaceMenu.ts` already covers right-click). No real keystroke handling — the
  `accelerator` is a display-only label, not a shortcut binder (that is the shortcuts view-model's job).

## Acceptance
`acceptance_command` passes. Deterministic, headless, no-DOM unit tests in
`sdk/typescript/test/ui-kits/menu-bar.test.ts` cover, against a fake/seeded command-registry:
open a menu and navigate (`openMenu`/`highlight`/`closeMenu`) yielding a frozen `MenuBarSnapshot`;
a disabled item is present in the snapshot but `select` on it is rejected (non-actionable);
`select` on an enabled item returns a frozen `MenuActionResult` whose action routes to a known
command id; an unknown item id and an unknown/unavailable command id both reject with the structured
error; same inputs → byte-identical snapshots (deterministic ordering, no clocks/I-O). Typecheck clean.

## Security/constraints
- Injected ports only (no ambient I/O); capability-mediated via the command-registry; fail-closed on
  unknown/disabled/unavailable; pure/deterministic (no clocks, no randomness); all returned snapshots
  and results `Object.freeze`d (deep, per `SurfaceMenu.ts`). No remote imports; lockfile mandatory;
  no package lifecycle scripts; no FFI/native addons.
