## Objective
The flagship desktop host (the unprivileged Deno peer that PSD-343 builds the AF_UNIX client for)
connects to agentd over the SAME hardened socket the runtime already uses
(`/run/vita-agent/agentd.sock`, the P1-035 transport in `agent/transport/server.go`). agentd must
(a) AUTHENTICATE that peer by the kernel-supplied credentials it already reads — `SO_PEERCRED` +
`vita-agent` group membership via `SO_PEERGROUPS`/`/proc` (P1-048, the `readUnixPeerInfo` /
`peerAuthorizedForGroup` path) — and (b) SCOPE which capabilities a connection presenting the
desktop host's uid/gid may reach: the desktop host gets an explicit, **default-deny** allowlist of
desktop-facing capabilities (`files`, `capsule.execute`, `settings`/nodeconfig) and is REJECTED,
fail-closed, on any other capability or the full `/apply` mutation surface. This stops the desktop
host from being a privilege-escalation path into agentd.

Concretely:
- REUSE the existing peer-cred transport — do NOT invent a new auth mechanism. The connection's
  authenticated principal keys already flow through the context
  (`unixPeerPrincipalKeysFromContext` in `agent/transport/server.go`, derived from
  `UnixPeerUserPrincipalKey(uid)` / the authorizing group key in
  `(*authenticatedUnixListener).peerPrincipalKeys`). The scope check keys off THOSE
  kernel-derived keys, never off request content (so it is not spoofable by the body).
- Add a desktop-host capability allowlist (default-deny): a connection whose authenticated peer
  principal resolves to the desktop host may call ONLY the allowlisted desktop capabilities; any
  capability not on the list — and the full apply surface for non-desktop capabilities — is
  rejected at the transport boundary BEFORE the registry/transaction runs, returning the sanitized
  `{error:{code,message}}` shape (code e.g. `capability_forbidden`) and recording one audit event
  (mirror the `recordPeerUnauthorized` / `unixPeerAuthCapability` pattern with a desktop-scope
  reason). No partial effect occurs on a rejected call.
- Wrong peer-cred (a connection NOT presenting the desktop host's uid/gid, or not in `vita-agent`)
  is rejected exactly as today (connection closed + `peer_unauthorized` audit) — this slice does
  NOT loosen the existing P1-048 gate; it ADDS the per-capability scope ON TOP of it.
- Put the scope policy + enforcement in `agent/transport/desktop_host_scope.go` and the Go test in
  `agent/transport/desktop_host_scope_test.go`. Use `agent/identity/roles` for the role vocabulary
  if the scope is expressed as a role binding (the desktop host is a `service`-class principal, not
  an owner) — never synthesize a new role.

## User value
The privileged control channel — which can spawn workloads and mutate the host — only honors the
narrow desktop-facing surface for the desktop host process, even though that process shares the same
authenticated socket as the rest of the runtime. A compromised or buggy desktop host cannot reach
identity/storage/boot/updater/owner capabilities or the full apply surface; it is confined,
fail-closed, to files/capsule.execute/settings. Closes the privilege-escalation gap PSD-343's host
client would otherwise open.

## Non-goals
- NO new wire transport, NO token/mTLS auth — peer-cred over AF_UNIX stays the on-device control.
- NO change to the request/response semantics of the allowlisted capabilities themselves.
- Do NOT loosen the P1-048 group gate, the socket `0660 group=vita-agent` perms, or the existing
  TCP-dev behavior.
- NO new role value; NO privilege ordering/inheritance (`agent/identity/roles` is a closed set with
  no hierarchy — every access stays explicit per grant).
- NO DOM/CSS/CEF; NO TS/desktop view-model code in this slice (that is PSD-343 and the view-models).

## Acceptance

`TestDesktopHostPeer*` in `agent/transport/desktop_host_scope_test.go` are green (the `-run`

prove:
- An allowlisted desktop capability (`files`, `capsule.execute`, `settings`/nodeconfig) IS served
  for the desktop-host peer.
- ANY other capability, and the full apply surface for a non-desktop capability, is REJECTED
  fail-closed with the sanitized `{error:{code,message}}` body (stable `capability_forbidden`-class
  code), no registry/transaction effect, and one audit event recorded.

  is rejected as before (closed + `peer_unauthorized`), i.e. the existing P1-048 gate is intact.
- The scope decision derives from the kernel-supplied peer principal keys (not request content),
  proven by a request that names an allowlisted capability in the body from a non-desktop peer NOT
  being granted the desktop scope.

## Security/constraints
- Default-deny: anything not explicitly allowlisted for the desktop host is rejected. Scope checked
  BEFORE the registry/transaction runs; rejection is fail-closed + audited; no partial effect.
- Decision keyed off kernel-derived authenticated principal keys only — never spoofable request
  content. Sanitized error codes only (never leak raw peer/path errors).
- Does not loosen P1-048/P1-035; defense-in-depth ON TOP of the group gate and socket perms.
- Go `vet`/build clean; existing `agent/transport/...` tests stay green. No keys/secrets. R3
  (privileged-daemon access control) → parallel-candidate + GPT-5.5 xhigh reviewer gate.
