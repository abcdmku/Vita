## Objective
`previewAccountsChange(current, desired)` (controller/accounts): given current + desired `AccountsConfig`
(the P0-029 SDK model), validate BOTH via `validateAccountsConfig`, then compute a typed, fail-closed
**change diff** WITHOUT applying: accounts `added` (name new), `removed` (name gone), `modified` (same name,
any field changed — surface which fields), keyed by account name. Surface privilege-delta signals the
operator must see: `newlyEnabledCount` (accounts flipped to enabled or added enabled), and
`groupChanges` (accounts whose `groups`/`primaryGroup` changed — a privilege-relevant delta). Return
`{ valid, diff, newlyEnabledCount, groupChanges, rejections }`. Fail-closed: invalid either side ⇒ typed
rejection, no diff, never a throw.

## User value
The management-plane "what will this accounts change do" view (FR-007/006) — shows account add/remove/modify
and flags privilege-relevant deltas (newly enabled accounts, group-membership changes), on validated inputs
only (both sides already pass the P0-029 privilege gates).

## Non-goals
- No real useradd, no agent call, no network. Validate + diff only. Do NOT modify the P0-029
  `accounts-model`; import it.

## Dependencies
P0-029 (accounts model: validateAccountsConfig), P0-015. Merged.

## Acceptance tests
`acceptance_command` — `accounts-preview.test.ts`: identical configs ⇒ empty diff, counts 0; added/removed/
modified accounts ⇒ correctly classified (modified surfaces the changed field names); an account flipped to
enabled ⇒ counted in `newlyEnabledCount`; a group/primaryGroup change ⇒ surfaced in `groupChanges`; invalid
current OR desired ⇒ typed rejection (no diff, no throw); hostile input ⇒ fail-closed (external-counter
accessor probe). Orchestrator also runs `npm run typecheck`.

## Performance & security constraints
Deterministic, no I/O/network. Fail-closed (reuse `validateAccountsConfig`; never throw). Privilege-delta
flags correct. Strict TS (no `any`). R2 → reviewer-gated.
