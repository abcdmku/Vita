## Objective
**Storage durability, slice 1 — encrypt the authoritative data volume (spec §10.2 "LUKS2 encryption for authoritative
data").** Today the `vita-data` partition (the ext4 `/var`-backing created by P1-029's `repart-verity/40-data.conf`,
mounted by `verity-overlay/.../var.mount` at `/dev/disk/by-label/vita-data`) is PLAINTEXT. Make it a **LUKS2** container
that is **unlocked at boot with a TEST key**, then mount `/var` on the *decrypted mapper* — proving the encryption
MECHANISM end-to-end exactly as Secure Boot proved enforcement with a TEST db key (`tools/secureboot-test-keys.sh`).

This is the MECHANISM only. **The real unlock secrets are OWNER-HELD (spec §16): a TPM-sealed key + an N-of-M offline
recovery key. NEVER generate or commit production key material.** Use a THROWAWAY TEST keyfile for the build (mirroring
the Secure Boot `.secureboot/` precedent), and STUB the TPM-seal + recovery-key INTERFACE so the owner wires the real
secrets later without re-architecting.

Concretely:
1. **TEST keystore (gen-once, gitignored, never shipped)** — add `tools/luks-test-keys.sh`, modeled on
   `tools/secureboot-test-keys.sh`: idempotent generator that writes a random TEST keyfile to a **gitignored** dir
   (`os/x86_64/.luks/data.key`, 4096 random bytes from `/dev/urandom`, mode 0400) PLUS a separate non-enrolled "rogue"
   keyfile (`os/x86_64/.luks/rogue.key`) for the wrong-key negative test. Carry a self-identifying `DO-NOT-SHIP` provenance
   note. Extend `os/x86_64/.gitignore` (or the repo `.gitignore` that anchors `.secureboot/`) so the WHOLE `.luks/` dir
   — key and any derived material — can NEVER be tracked, and assert it with `git check-ignore` exactly as the SB script
   does (fail loudly BEFORE any `git add` can stage a key). The key/cert are EXCLUDED from any reproducibility claim
   (the image is reproducible GIVEN a fixed key; the throwaway key is not).
2. **Format + populate at build time** — in the VITA_VERITY build path (`os/x86_64/build-and-boot.mjs`, behind a
   `VITA_LUKS=1` gate so the plain smoke + non-LUKS verity images are unaffected): after repart lays down the `vita-data`
   partition, `cryptsetup luksFormat --type luks2` the partition with the TEST keyfile (LUKS2 default params; document
   the chosen cipher/KDF), `luksOpen` it to a mapper, `mkfs.ext4 -L vita-data` the *mapper* (the ext4 LABEL moves onto
   the decrypted volume so `var.mount`'s `/dev/disk/by-label/vita-data` resolves the DECRYPTED device), close. The ext4
   `FileSystemLabel` therefore must be set on the LUKS-INNER fs, NOT the outer partition — adjust `40-data.conf`
   accordingly (the outer partition is now an opaque LUKS container; the by-label resolution must hit the mapper).
3. **Unlock at boot (systemd-cryptsetup)** — add a `vita-data-luks.service` (or a crypttab + `systemd-cryptsetup@`
   instance) in `verity-overlay/` that, BEFORE `var.mount`, `cryptsetup luksOpen`s the `vita-data` LUKS container with the
   TEST keyfile baked into the (read-only, verity-measured) rootfs at a fixed path, producing the mapper that
   `var.mount` then mounts. Order it `Before=var.mount` and make `var.mount`'s `What=` resolve to the decrypted device
   (keep the `by-label` resolution working by labelling the inner fs per step 2). Keep `var.mount`'s existing
   `ConditionPathExists`/`nofail` skip-semantics intact so a plain (non-LUKS, non-verity) smoke image still boots and
   falls back to `/var` on the rw root (condition unmet = success-skip, NEVER a hard fail that cascades to vita-agentd's
   `StateDirectory` — the P1-029 lesson).
4. **TPM-seal + recovery-key INTERFACE, STUBBED** — define the seam, do NOT implement real sealing. The unlock service
   reads its key via a small, documented resolver with a CLOSED, ordered set of key sources:
   `(a)` TPM-sealed slot — **STUB**: a clearly-marked no-op/`exit-unsupported` path with a `# OWNER WIRES §16` comment
   pointing at where `systemd-cryptenroll --tpm2-device=auto` / a sealed token would attach; `(b)` recovery key — **STUB**:
   same, marked for the owner's N-of-M offline recovery flow; `(c)` the TEST keyfile — the ONLY source that actually
   unlocks in this build. The resolver must FAIL CLOSED: if no usable source yields a valid key, the unlock FAILS and
   `/var` does NOT mount on a plaintext fallback (no fail-open to an unencrypted volume). Document that on certified
   hardware the order is TPM-first then recovery, and the TEST keyfile source is BUILD-ONLY (gated by `VITA_LUKS=1`,
   never present in a release image).
5. **MEASURED marker (the P1-055 lesson — never synthesized)** — the on-device `VITA-LUKS` marker is emitted only after
   REAL checks: `cryptsetup isLuks` confirms the `vita-data` partition IS a LUKS2 container (encrypted=OK), the mapper is
   open and `/var` is mounted ON THE MAPPER not the bare partition (unlocked=OK), and a sentinel file written to `/var`
   on the FIRST boot is still present on a SECOND boot (persists=OK across reboot). The wrong-key negative
   (`rogue.key`) is exercised by the acceptance test (not on the live boot): `luksOpen` with the rogue key MUST FAIL
   (fail-closed). Marker:
   `VITA-LUKS: encrypted=OK unlocked=OK persists=OK tpm=stub recovery=stub status=OK`;
   fail path `VITA-LUKS-ERROR: reason=<specific step+errno> status=FAILSAFE`. Keep ALL prior markers. The TPM/recovery
   stubs surface as `tpm=stub recovery=stub` so it is unambiguous the real secrets are not yet wired.

## User value
The node's authoritative data — user data, app state, snapshots, the local backup cache (spec §10.1) — sits on an
encrypted volume so a stolen disk discloses nothing (spec §16 "Vendor cannot decrypt local disks"). This slice lands the
LUKS2 mechanism end-to-end (format → unlock → mount → persist, with wrong-key fail-closed) on a TEST key, and stubs the
TPM-seal + offline-recovery seams that the OWNER wires with real, owner-held secrets — the encryption foundation for the
Phase-3 "LUKS2 data volume", "TPM key sealing on x86", and "Recovery-key flow" deliverables (spec §21 Phase 3, §10.2/10.4).

## Non-goals
NO TPM2 sealing implementation and NO recovery-key generation/escrow — those are the OWNER's real secrets (§16); this
slice ONLY defines + stubs the interface. NO production key material generated or committed (TEST keyfile + rogue only,
gitignored). NO Btrfs (the data fs stays ext4 this slice; Btrfs/snapshots/quotas are later Phase-3 slices). NO change to
the dm-verity RO root or the Secure Boot chain. NO ARM/Pi LUKS (x86_64 only; the Pi NVMe flow is a separate slice). NO
re-encryption/key-rotation/`luksAddKey` UX (later). NO disk-full / power-loss handling beyond what already exists. The
plain smoke image and non-LUKS verity image stay byte-compatible (everything gated behind `VITA_LUKS=1`).

## Acceptance tests
`acceptance_command`: `bash os/x86_64/test/luks-data.test.sh` — a self-contained host-side (build-host / WSL) test that
does NOT require a full QEMU boot, so a worker can run it. It MUST, using `cryptsetup` against a loopback-backed file
image (losetup a sparse file; skip-with-clear-message if not root / no loop devices — the BOOT is the real floor):
1. **Encrypted:** `luksFormat --type luks2` a test partition image with a generated TEST keyfile; assert
   `cryptsetup isLuks` is true and the LUKS2 header reports version 2 (encrypted=OK).
2. **Unlocks with the TEST key:** `luksOpen` with the TEST keyfile SUCCEEDS; `mkfs.ext4 -L vita-data` the mapper; mount it;
   write a sentinel; unmount; `luksClose`. Re-`luksOpen` + remount + assert the sentinel is still there (persists=OK).
3. **Wrong key FAILS CLOSED:** `luksOpen` with the `rogue.key` MUST return non-zero and NOT open the mapper (fail-closed).
4. **Key resolver:** the resolver's TPM + recovery sources are STUBS (return unsupported), the TEST source unlocks, and
   with NO usable source the unlock FAILS (no plaintext fallback). Assert the stub paths are clearly marked and inert.
5. **No key material is committed:** assert `git check-ignore` covers `os/x86_64/.luks/data.key` and `.../rogue.key`
   (the SB-script discipline).
Then `bash tools/luks-test-keys.sh` is idempotent (re-run = skip). Do NOT put hidden/rotating cases here.
**Orchestrator host-verifies on Borg51 (the decisive floor):** `VITA_LUKS=1 VITA_VERITY=1 VITA_SECURE_BOOT=1` build →
QEMU boot → serial shows `VITA-LUKS: encrypted=OK unlocked=OK persists=OK tpm=stub recovery=stub status=OK` (MEASURED:
`isLuks` true on `vita-data`, `/var` mounted on the mapper, sentinel survives a forced reboot), and the prior chain
(VITA-TS / EVAL / APPLY / CAPSULE-* / NET-* …) still PASSES with `/var` now on the encrypted mapper.

## Performance & security constraints
LUKS2 only (reject LUKS1). The TEST keyfile + rogue are THROWAWAY, host-local, gitignored, NEVER shipped, and excluded
from reproducibility (spec §16: signing/encryption secrets unavailable to dev agents — TEST keys only). Fail-CLOSED: any
unlock-source failure → `/var` does NOT mount on a plaintext fallback; the marker is MEASURED, never synthesized;
specific step+errno on failure. The unlock service is the only privileged actor; it composes its `cryptsetup` invocation
from FIXED, code-controlled args + the resolved key — NEVER from raw runtime-supplied text. The TEST keyfile source is
BUILD-ONLY (gated by `VITA_LUKS=1`); a release image carries ONLY the TPM/recovery sources (stubbed here, owner-wired
later). No remote imports; no package lifecycle scripts; no network. R3 (boot/storage/identity — privileged TCB) →
**reviewer gate** (`npm run review -- P1-068`) + independent host-verify before merge.
