## Objective
`simulate(profile, plan)` (simulation/harness): a PURE, deterministic simulation of applying a node plan
against a simulation profile (the hardware/resource profile types from P6-002), producing a typed
`SimulationResult` — WITHOUT any real execution. It checks each plan operation against the profile's
declared resources/capabilities and reports: which ops would succeed, which would be rejected (and why),
projected resource usage vs the profile's limits, and a final feasible/infeasible verdict. NEW validator
⇒ use `safeNormalize` for the untrusted `profile`/`plan` boundary, then operate on the trusted plain value.
- Deterministic: same (profile, plan) ⇒ byte-identical result. Fail-closed: a malformed profile/plan, or
  an op that cannot be evaluated against the profile, ⇒ a typed rejection (never a throw, never "assume ok").
- Standalone module — import the P6-002 profile types + safeNormalize; no shared-index edits.

## User value
Lets a node config be SIMULATED against a target profile before it touches real hardware (§20, FR-022) —
catch infeasible plans (over-budget resources, missing capability) deterministically + offline.

## Non-goals
- No real execution, no agent, no I/O/network, no timing/perf measurement. Pure feasibility simulation
  over declared profile resources. Do NOT modify the P6-002 profile-types source; import it.

## Dependencies
P6-002 (simulation profile types), P0-019 (storage model for storage-op feasibility), P0-015 (safeNormalize). All merged.

## Acceptance tests
`acceptance_command` — `simulate.test.ts`: a feasible plan within profile limits ⇒ feasible result, all
ops ok; a plan exceeding a resource limit ⇒ infeasible with the over-budget op flagged; a plan needing a
capability the profile lacks ⇒ infeasible with that op rejected; determinism (same inputs ⇒ identical
result); fail-closed on malformed profile/plan via safeNormalize (typed rejection, no throw). Orchestrator
also runs `npm run typecheck`.

## Performance & security constraints
Pure/deterministic, no I/O/network. Fail-closed via safeNormalize (never throw; never assume-ok on an
unevaluatable op). Strict TS (no `any`). R2 → reviewer-gated.

## Reviewer revision (round 2 — BLOCKING, from P6-003.review.md)
Profile-side storage health is ignored: `projectProfile` grants storage from `profile.storageLayout`, but
`rejectStorageIssues` only checks the OPERATION's `layout.diskHealth` (critical / SMART failed) — so a
storage op with a healthy plan layout is feasible against a PROFILE whose declared storage is critical/
failed. Evaluate the op against the PROFILE's declared storage health too: if the profile's storageLayout
is critical or has SMART-failed devices, the storage op is INFEASIBLE (reject it in the simulation
result). Add a regression: a healthy plan op + an unhealthy profile storage layout ⇒ infeasible.
(Keep it lean — the round-1 NOTE flags the implementation is larger than needed; trim incidental surface.)
