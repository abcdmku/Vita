## Objective
Build the **thin native compositor-core skeleton** that backs the PSD-001 substrate interface (spec §6.2): a minimal
native (Rust or C++; pick the most maintainable with strong wgpu/DRM bindings — justify in an ADR) process that:
- Opens a DRM/KMS scanout + GPU device, sets up a GPU compositing surface, and reads libinput events.
- Holds a registry of **GPU textures/surfaces** keyed by surface id, and **composites** them per a placement list with
  **damage tracking** — moving/resizing a surface REPOSITIONS its texture on the GPU (NO repaint of content).
- Exposes the PSD-001 substrate interface over the OS seam: register-surface(id)→texture handle, update-placements(list),
  set-focus, input-events stream. The TS WM policy (PSD-004) drives it; the compositor is pure MECHANISM.
- A **headless/offscreen render mode** (render to an offscreen GPU target + a CPU-readback path) FOR TESTS/SCREENSHOTS
  ONLY — the normal path is accelerated on-GPU (spec §6.3: CPU readback only for tests/screenshots/fallback).

## User value
The thin, package-swappable native substrate that makes the render/composite split real — content rendered once,
repositioned on the GPU. Not OS-coupled.

## Non-goals
- NO CEF/web engine yet (PSD-003 bridges CEF→texture). This slice composites OPAQUE TEST textures (solid-color/
  checkerboard surfaces) to prove placement + damage + no-repaint.
- NO WM policy (PSD-004 provides it; here just the mechanism + a trivial test driver).

## Dependencies
- PSD-001 substrate interface (extend `desktop-substrate.ts` with the texture/surface + placement surface; reconcile
  with PSD-001 at merge, keep-both).

## Acceptance
- `acceptance_command` (typecheck of the TS interface additions) passes; the native core BUILDS (cargo/cmake) for
  linux x86_64. The native build + render correctness is verified on the **VMware Workstation Pro GPU target** (3D
  accel) once the PSD-VH1 harness lands — emit `VITA-COMPOSITOR: surfaces=N composited=OK reposition=no-repaint
  damage=OK status=OK` MEASURED there (a moved surface's content texture is byte-identical pre/post move via the
  test-only readback, proving no repaint). Until the VMware harness exists, the slice lands REVIEW-APPROVED + BUILT but
  NOT boot-merged (verification floor deferred to the GPU target — note this explicitly, never claim GPU-verified).

## Security/constraints
- The compositor is a system component but NOT part of the OS image — a desktop-package-provided substrate. Runs with
  only the device access it needs (DRM/input), no broad privilege. Fail-closed on device-open failure (fallback mode).
- No remote imports; pinned deps/lockfile; no lifecycle scripts.

## Definition of done
- Native core skeleton builds (linux x86_64); composites test textures with damage tracking + no-repaint reposition;
  exposes the PSD-001 seam; offscreen+readback test path. ADR on engine/bindings choice. R2 reviewer gate; GPU boot-
  verify on VMware deferred until PSD-VH1 — clearly flagged as build+review-complete, GPU-unverified.

## REVISION 2 (Codex R2 review: REVISE — real KMS scanout + image GPU stack + input stream — 2026-06-25)
rev1 built the crate but missed 3 core requirements. `os/x86_64` is now IN target_paths (the earlier omission was a
contract error). Fix all three:
1. **OS image GPU stack (now in scope):** add the minimal x86_64 GPU stack to the mkosi image so a real DRM render node
   + KMS device exist in the VMware 3D-accel VM — the `vmwgfx` DRM/KMS driver (ensure the kernel module loads) + Mesa
   (the `vmwgfx`/`svga` Gallium GL/EGL driver + `libgbm`). The compositor must find `/dev/dri/card0` (+ a render node)
   and get a working EGL/GLES context on `vmwgfx`. Do NOT regress the 22 headless markers.
2. **Real DRM/KMS SCANOUT (not an offscreen pbuffer):** `linux.rs` currently renders to an EGL pbuffer — that never
   reaches the screen. Implement the real present path: KMS modeset on a connector/CRTC, a GBM scanout surface (or KMS
   dumb/framebuffer for the composited result), and page-flip/atomic-commit to PRESENT each composited frame to the
   VMware virtual display. Moving a surface re-composites + page-flips WITHOUT re-rendering the surface's content
   texture (no-repaint). Fail-closed (FAILSAFE marker) if KMS/DRM master can't be acquired.
3. **Input-events STREAM:** expose libinput events as a real stream through the PSD-001 substrate seam (don't poll +
   discard with `count=N`). The seam consumer can receive pointer/keyboard events.
4. **MEASURED on VMware:** emit `VITA-COMPOSITOR: gpu=vmwgfx surfaces=N composited=OK reposition=no-repaint

   boots a compositor-enabled image on the VMware target and confirms the marker (`node tools/vmware-verify.mjs
   --image <img> --markers VITA-COMPOSITOR`). Until that boot confirms it, state GPU-UNVERIFIED honestly.
Verify: `npm run typecheck`; the compositor builds for linux x86_64; the image carries vmwgfx+Mesa; then the VMware

## REVISION 3 (Codex R2 re-review: REVISE — fail-closed discipline on the GPU/input paths — 2026-06-25)
(Finding 1, the mockup-in-diff, is fixed: the mockup is a separate main commit; PSD-002's diff is now compositor-only.)
Two real fail-closed bugs remain:
1. **`VITA-COMPOSITOR ... status=FAILSAFE` on ANY GPU-path failure (not just backend-open):** `main.rs` only emits
   FAILSAFE when `open_default_gpu_backend()` fails. If KMS modeset/present, page-flip, GL readback, or the no-repaint
   verification fails inside `run_reposition_self_test(backend)?`, `main()` exits with bare stderr and NO marker. FIX:
   wrap the WHOLE GPU self-test so EVERY failure path emits `VITA-COMPOSITOR: gpu=<...> ... status=FAILSAFE` (with the
   failing reason) — the marker is ALWAYS emitted (OK or FAILSAFE), never omitted. The contract says don't fake OR omit it.
2. **Fail-closed libinput (no silent empty stream):** `LibinputState::open()` returns `None` and `poll_events()` returns
   empty on load/context/device failure — so a broken/absent libinput yields an empty input stream while the compositor
   still reports OK. FIX: fail-closed — if libinput can't open its context/device, emit `status=FAILSAFE`
   (reason=input_unavailable), do NOT report an OK marker with a silently-empty input stream. A real input-events stream
   or an honest FAILSAFE — never silent degradation. (Security constraint: fail-closed on device-open failure.)
Verify: `npm run typecheck`; the compositor builds for linux; the self-test ALWAYS prints a VITA-COMPOSITOR line
(OK xor FAILSAFE) on every path; libinput-open failure → FAILSAFE.

## REVISION 4 (Codex R2 re-review: REVISE — fail-closed input + marker test-integrity — 2026-06-25)
Two precise fixes (the compositor core is otherwise solid):
1. **Fail-closed on ANY selected input-device add failure:** `linux.rs` ignores `libinput_path_add_device()` failures as
   long as one device opens. FIX: any SELECTED `/dev/input/event*` that fails to add → `input_unavailable` →
   `status=FAILSAFE` (don't degrade to a partial stream while reporting OK). If a device is intentionally out of scope,
   don't select it in the first place; a selected-but-failed device is a fail-closed condition.
2. **`present=kms` OK marker ONLY from the real GPU/KMS path (test-integrity — do not let the fake backend fake it):**
   the CPU `RecordingBackend` (lib.rs:722-731, 862-864) can currently emit `VITA-COMPOSITOR ... present=kms ...
   status=OK` — the exact acceptance marker. That makes the GPU verification gameable. FIX: `present=kms` (and the
   acceptance-shaped OK marker) is produced ONLY by the real DRM/KMS presentation backend. The CPU/recording/self-test
   backend MUST use a DISTINCT `present=` value (e.g. `present=offscreen` or `present=recording`) and must never produce
   `present=kms status=OK`. The VMware boot's `present=kms status=OK` must be unforgeable by any non-GPU path. Keep the
   FAILSAFE-always discipline from rev3.
Verify: `cargo test` (incl. a test asserting the CPU backend's marker is NOT `present=kms status=OK`); selected
input-device add failure → FAILSAFE; the OK `present=kms` marker is reachable only via the real KMS backend.
