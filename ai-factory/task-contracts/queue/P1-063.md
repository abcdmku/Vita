## Objective
Build the **catalog supply-chain root**: a canonical, deterministic **signed application CATALOG manifest** and a
**fail-closed verifier** that gates every install. This is the first slice of the App-catalog arc (the largest Phase-4
gap — no app supply chain yet). It is a THIN vertical TS slice: the catalog format + its signature/integrity
verification, reusing the existing per-entry validator (`packages/catalog/src/catalog-entry.ts`, `validateCatalogEntry`)
and the package-contract types — it does NOT add a Go agentd handler, an on-device boot marker, or an installer (see
Non-goals; those are explicit follow-up slices).

Concretely:
1. **Catalog manifest shape** (`packages/catalog/src/catalog-manifest.ts`): a top-level signed object
   `{ catalog: { schemaVersion, catalogVersion, generatedAt, apps: CatalogApp[] }, signature: CatalogSignature }`. Each
   `CatalogApp` = `{ id, versions: CatalogAppVersion[] }`; each `CatalogAppVersion` =
   `{ version, packageRef, integrity, riskSummary, grantsSummary }` where:
   - `packageRef` is a reference URI to the capsule/package artifact (reuse the reference-syntax + embedded-material
     rejection already in `catalog-entry.ts` — references only, NEVER embedded bytes/secrets, §13.1).
   - `integrity` is an **SRI string** (`sha256-…`/`sha384-…`/`sha512-…`, base64 std/raw) — the artifact digest the
     runtime/agent will later verify the fetched bytes against (mirror the `sriIntegrity` shape already used by
     capsule fetch; reuse the SDK SRI parser if one is exported, else add a small pure parser under `sdk/typescript`).
   - `riskSummary` = the declared risk class (R0–R4 enum) for the app version; `grantsSummary` = a deterministic,
     sorted summary of the capability grants the app version requests (ids only — the human-facing "what it can do").
2. **Canonical serialization** (`packages/catalog/src/catalog-canonical.ts`): a pure, deterministic canonicalizer that
   produces the **byte-identical** payload that is signed and verified — reuse/extend the existing `canonicalize`
   approach in `sdk/typescript/src/repro.ts` (lexicographically-sorted keys, no insignificant whitespace, reject
   non-finite/NaN, reject cyclic/exotic shapes). The signature is computed over `canonical(catalog)` ONLY (the
   `signature` envelope is excluded from its own payload). Same inputs → identical signed bytes.
3. **Signature** = ed25519 over the canonical catalog bytes. `CatalogSignature` =
   `{ algorithm: "ed25519", keyId, value }` (`value` = base64 signature; `keyId` selects the public key). Provide a
   **TEST signing key** ONLY in `packages/catalog/test/fixtures/catalog-test-signing.ts` (generated/derived at test
   time or a checked-in TEST keypair clearly labelled `TEST ONLY — NOT A RELEASE KEY`). Mirror the Secure-Boot precedent
   (P1-027) which used a TEST db key: the real release signing key is **OWNER-HELD (§16)** and is NEVER committed or
   generated by the worker. The verifier accepts a caller-supplied set of trusted public keys (keyed by `keyId`); the
   TEST key is wired ONLY in tests.
4. **Verifier** `verifyCatalog(value: unknown, trustedKeys): CatalogVerificationResult` — **fail-closed**, never throws
   (a throw at this trust boundary is a DoS — see AGENTS.md "Validators/guards … must be fail-closed and NEVER throw").
   It MUST, in order: normalize the input intrinsic-safely (reuse the `catalog-entry.ts` plain-normalization pattern:
   reject getters/accessors, symbols, exotic prototypes, cycles, method-shadowing arrays; snapshot once); validate the
   manifest shape AND every entry via `validateCatalogEntry`/the shared package-contract validator; recompute
   `canonical(catalog)`; verify the ed25519 signature against the `trustedKeys[keyId]` public key; and verify EACH
   version's `integrity` SRI is well-formed. Returns `{ ok: true, catalog }` only if ALL pass; otherwise
   `{ ok: false, errors }`. An **unsigned** catalog (no/empty signature), a **wrong/forged** signature, an **unknown
   keyId**, a **tampered** field (any byte change flips the signature), or a **malformed/missing integrity** on any
   entry MUST be REJECTED (fail-closed). The verifier does not fetch bytes — it gates the catalog so a later
   fetch/install slice can trust `integrity` per artifact.

Security model (encode it): the TS runtime is UNPRIVILEGED — this verifier runs in the runtime/SDK and only DECIDES
trust over data; privileged host mutation (actually installing) belongs ONLY to the narrow Go agentd in a later slice
and MUST act from a re-validated manifest, never raw runtime text. NO real keys/secrets: signing/TPM/recovery keys are
OWNER-HELD (§16); use a TEST ed25519 key only, never commit/generate production key material. No remote imports;
lockfile mandatory; no package lifecycle scripts; pure/deterministic (no I/O in the canonicalizer/verifier beyond the
crypto primitive).

## User value
The node gets the **root of trust for its app supply chain**: before any app is installed, the catalog it came from is
proven to be authored by a trusted key and untampered, and each app version carries a verifiable artifact digest plus a
human-readable risk/grants summary. A tampered or unsigned catalog, a forged signature, or a bad entry digest is
rejected fail-closed — closing the "no app supply chain yet" gap called out as the largest Phase-4 gap in STATE.md, and
implementing the §9.3/FR-013 signed-catalog requirement. Establishes the format every later slice (agentd verify,
fetch-by-integrity, install) builds on.

## Non-goals
- **NO Go agentd catalog handler** and **NO on-device boot marker** — there is no catalog verification in agentd today;
  wiring `agentd` + an on-device `VITA-CATALOG: entries=N verified=OK` measured marker is an explicit FOLLOW-UP slice.
  This slice is SDK/package-unit-level (per the slice scope: "on-device marker if wired, else SDK/unit-level").
- **NO actual fetch/download or install** — the verifier gates trust; it does not retrieve or unpack artifacts (a later
  fetch-by-integrity slice reuses the capsule fetch SRI gate).
- **NO npm/JSR mirror / registry pull** — offline, local catalog object only.
- **NO real/production signing key**, no key rotation policy, no revocation/transparency-log, no SBOM/vuln scanning
  beyond the fields already modelled in `catalog-entry.ts` (out of scope here).
- **NO changes to the existing per-entry validator's semantics** — reuse `validateCatalogEntry` as-is; only add the
  catalog-level wrapper + signature/integrity verification.

## Acceptance tests
`acceptance_command`: `node --experimental-strip-types --test "packages/catalog/test/*.test.ts" && npm run typecheck`
(matches the P1-003 catalog suite invocation; `npm run typecheck` enforces strict TS 7 — the strip-types run does NOT
type-check, per AGENTS.md §2). `packages/catalog/test/catalog-manifest.test.ts` must prove (do NOT put any
hidden/rotating cases here):
- A valid catalog signed with the TEST key **verifies** (`ok: true`) and round-trips its apps/versions.
- **Determinism:** canonicalizing the same catalog twice is byte-identical; key-reordering the input object yields the
  same canonical bytes and the same signature verifies.
- **Tamper rejection:** flipping ANY field after signing (an app id, a version, a `packageRef`, an `integrity`, a
  `riskSummary`, a grant) → `ok: false` (signature mismatch). Reordering `apps`/`versions` arrays (semantically
  meaningful order) is detected if it changes canonical bytes.
- **Unsigned / forged / unknown-key:** a catalog with no/empty signature → reject; a signature produced by a DIFFERENT
  key → reject; a `keyId` not in `trustedKeys` → reject. All fail-closed.
- **Per-entry integrity:** a version with a malformed/missing `integrity` SRI → reject; a well-formed SRI passes the
  format check (this slice does NOT fetch bytes).
- **Fail-closed never-throws:** malformed/cyclic/deeply-nested input, accessor-property (getter) fields, symbol keys,
  method-shadowing arrays, exotic prototypes (`new Date()`/`Map`/`Proxy`) → `ok: false`, NEVER a throw (regression
  test asserts no exception). A name-keyed map (if any) is built with `Object.create(null)` and proven against a
  `__proto__`/`constructor`-keyed input.
- Existing `packages/catalog/test/*.test.ts` (catalog-entry, lockfile-policy) still PASS unchanged.

## Performance & security constraints
Deterministic + pure (no I/O beyond the ed25519 primitive; the canonicalizer is I/O-free). Fail-closed at the trust
boundary, never throws (AGENTS.md). Intrinsic-safe normalization of untrusted input (snapshot once; reject
getters/accessors, symbols, exotic prototypes, cyclic, method-shadowing — reuse the `catalog-entry.ts` pattern; do NOT
call methods off untrusted objects). Signature is over canonical bytes ONLY, excluding its own envelope. References
only — embedded secret/content material rejected (§13.1). **NO production key material** committed or generated — TEST
ed25519 key only, clearly labelled, confined to `test/fixtures/`; the release key is owner-held (§16). No remote
imports; lockfile mandatory; no package lifecycle scripts; no FFI/native addons. R2 (supply-chain trust root) → reviewer
gate (`npm run review` must approve) + orchestrator independent verification before merge.
