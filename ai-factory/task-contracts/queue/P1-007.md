## Objective
Implement the first **real transactional capability** so the agent can actually apply a declarative
host change with rollback (exercises P1-006's engine end-to-end). Manage a SMALL, closed set of
declarative node settings written to a config file the agent owns (e.g. a key=value node config under
a fixed agent state dir — NOT arbitrary files). Provide:
- `agent/capabilities/nodeconfig/nodeconfig.go` — a `TxCapability` (per P1-006): `Name()`,
  `Handle()` (read current), and `Apply(ctx, req) (Undo, error)` where `req` is a **typed** desired
  node-config (closed field set), and `Undo` is a typed compensating action that restores the prior
  config. NO arbitrary path/command in the request — the target file path is FIXED/internal, derived
  from an agent state root, never from the request.
- A small **abstraction over the filesystem** (an interface: read/atomic-write/replace) so the Linux
  impl and an in-memory test impl share logic. Atomic write = write temp + rename (no partial file).
- `apply_linux.go` (`//go:build linux`) — real impl using the fixed agent state path (atomic
  temp+rename, restrictive perms). `apply_stub.go` (`//go:build !linux`) — typed unsupported error.
- Tests use the **in-memory FS impl** (deterministic, no real disk): Apply sets the config and returns
  an Undo that restores the exact prior bytes; integrate with `transaction.Apply` to prove a plan with
  this capability commits on success and rolls back (restores prior config) on a later failure.

## User value
This is the agent doing real, safe, reversible work — the concrete proof that TypeScript-declared
desired state can be applied transactionally to a host and rolled back (spec §8.2, FR-007).

## Non-goals
- Only this one closed node-config setting class; no general file/host management.
- No arbitrary paths/commands; the request never names a path or command.

## Acceptance tests
`acceptance_command` (go test in golang:1.26) + `go vet` clean. Using the in-memory FS:
1. `Apply` writes the desired config and returns an `Undo` restoring the exact prior state; applying
   then undoing yields the original bytes.
2. Wired through `transaction.Apply`: a plan with this capability + a passing health check commits
   (config persisted); a plan where a later op fails rolls back THIS capability (prior config restored).
3. Atomic write leaves no partial file on a simulated mid-write failure (temp+rename; the live file is
   either old or new, never partial).
4. The capability rejects a malformed/typed-invalid request fail-closed (no write, typed error); the
   request cannot name an arbitrary path.

## Reviewer revision (round 2 — BLOCKING, from P1-007.review.md)
**No error path may exist AFTER the atomic commit point.** Currently `AtomicWrite` renames the temp
into place (commit) and THEN `os.Chmod`s the live file; if that post-rename chmod fails it returns an
error, so `transaction.Apply` records no Undo and leaves the live config already mutated — an
untracked, un-rolled-back change. Fix:
- Do ALL preparation (write bytes, set permissions/ownership on the TEMP file, fsync) BEFORE the
  rename. The `rename` is the single atomic commit point; **nothing after it may fail the apply.**
  Remove the post-rename `os.Chmod` (the temp already has the right mode and rename preserves it).
- Guarantee: `Apply` either (a) returns success + a working `Undo` whenever the live file was swapped,
  or (b) returns an error having made NO change to the live file. There is no third state.
- Add a regression test: a failure injected at/after the commit point must NOT leave an untracked
  mutation — i.e. either the op reports success with a restoring Undo, or the live file is unchanged.
(Non-blocking, optional: wire a `nodeconfig` capability into the `agentd` registry in main.go so it is
runtime-discoverable.)
