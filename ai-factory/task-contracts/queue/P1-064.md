## Objective
Add a **pure, deterministic mirror resolver** to the package-platform: given (a) an already-policy-validated
lockfile and (b) a vendored **mirror store** (a content-addressed map from package@version → the artifact bytes the
mirror retains), produce a `MirrorResolution` that proves every production dependency is satisfied **only from the
mirror** and **byte-verified against its lockfile SRI integrity** — or fail closed with structured violations.

Implement `resolveFromMirror(lockfileInput: unknown, store: MirrorStore): MirrorResolutionResult` in
`packages/install/src/mirror.ts`. Required behavior, **fail-closed**:
1. **Reuse, don't re-implement, the policy gate.** Run the lockfile through the existing
   `validateLockfilePolicy` (`packages/catalog/src/lockfile-policy.ts`) FIRST; on any policy violation, return
   `{ ok: false, errors: [...] }` and resolve **nothing** (un-pinned ranges, unknown fields, remote/non-mirror
   sources, and lifecycle/`hasInstallScript`/`requiresBuild` indicators are already rejected there — do not weaken or
   duplicate those checks; surface them as `POLICY_REJECTED` errors).
2. **Resolve only pinned, mirror-backed artifacts.** For each resolved package entry (npm `packages` map and JSR
   `resolved` map), require an exact `name@version` and a valid SRI `integrity`. Look the artifact up in `store` by
   a canonical content key. If the artifact is **absent from the mirror**, reject with `NOT_IN_MIRROR` (NEVER fall
   back to a remote fetch — there is no network; absence is a hard reject, not a warning).
3. **Verify bytes against the SRI.** Re-compute the digest of the mirror bytes with `node:crypto`
   (`createHash(algorithm)`), encode base64, and require it to **equal** the lockfile entry's SRI digest for the
   declared algorithm. On mismatch, reject with `INTEGRITY_MISMATCH` and the offending path. A package may carry
   multiple SRI hashes; verify against the strongest declared algorithm and require at least one match.
4. **Reject remote/un-pinned/lifecycle at this layer too (defense in depth).** Even though the policy gate runs
   first, this resolver must independently refuse any entry whose source is not a bare `name@exactversion` or a
   configured `local-mirror://` / `vita-mirror://` reference, any non-exact version, and any lifecycle-script
   indicator — so the resolver is safe to call on a lockfile that bypassed the gate. (Mirror the constants in
   `lockfile-policy.ts`; do not loosen them.)
5. **Determinism + safe-boundary.** `safeNormalize` the lockfile input ONCE at the boundary (reuse
   `sdk/typescript/src/safe-normalize.ts`), reject accessor/exotic shapes, never re-read an untrusted field across
   decisions, and produce a **sorted, stable** `resolved` list (byte-identical output for identical inputs). The
   `MirrorStore` is a typed in-memory map passed by the caller (`{ get(key): Uint8Array | undefined }` over a plain
   record / `Map`) — **no filesystem, no network, no subprocess**: the resolver is pure I/O-free config code (§8.2).
6. **Never throw at the trust boundary.** Malformed, cyclic, deeply-nested, or method-shadowing inputs (hostile
   iterators, getters, `__proto__` keys) return a rejection, not an exception.

On success return `{ ok: true, resolution: { packages: readonly { name, version, integrity, key }[] } }` listing
exactly the mirror-verified artifacts, sorted by `name@version`.

## User value
The supply-chain guarantee for the application platform (spec §9.3, §15 "npm supply-chain compromise" mitigation,
§28): a Vita node installs packages **only** from its own hashed, vendored mirror, with every artifact's bytes
proven to match the pinned lockfile integrity — so a compromised or unreachable upstream registry cannot inject,
substitute, or run code on the node, and a tampered mirror artifact is caught before install. No remote imports, no
lifecycle scripts, lockfiles mandatory and verified — the byte-level half that `validateLockfilePolicy` (which only
checks the SRI is well-formed) does not yet cover. This closes the resolver gap between policy-validation and a real
install plan.

## Non-goals
- **No actual fetching/network/filesystem.** The mirror store is supplied in-memory by the caller; this slice does
  not implement a downloader, an OCI/registry client, an on-disk CAS layout, or a CLI. (Those are later slices.)
- **No new policy.** Do not invent integrity rules, length caps, charset limits, or source schemes beyond what
  `lockfile-policy.ts` already enforces — that would make this layer STRICTER than the gate and reject valid input.
  Reuse the existing constants/validator; if you believe the gate is too loose, that is a separate contract.
- **No changes to `lockfile-policy.ts`, `resolve.ts`, `catalog-entry.ts`, the SDK, the agent, or the OS image.**
- **No signature verification / catalog trust-tier logic** (covered by `resolve.ts` / catalog slices).
- **No on-device boot marker** — this is a pure host-side TS module; no `main.ts` / overlay change.

## Acceptance tests
Restated `acceptance_command`: `node --experimental-strip-types --test "packages/install/test/*.test.ts"` (offline,
Node built-ins only — `node:test`, `node:assert/strict`, `node:crypto`). The new `mirror.test.ts` must include at
least:
- **Happy path (npm + JSR):** a policy-valid lockfile whose every resolved package is present in the store with bytes
  whose recomputed SRI equals the lockfile integrity → `ok: true`, `resolution.packages` lists exactly those
  artifacts, **sorted**, with the right `name@version` and `integrity`.
- **Determinism:** the same inputs in a different key order yield a byte-identical `resolution` (deep-equal).
- **NOT_IN_MIRROR:** a pinned package missing from the store → rejected, no remote fallback, the artifact is NOT in
  the resolution.
- **INTEGRITY_MISMATCH:** store bytes that hash to a different digest than the lockfile SRI → rejected with the
  offending path; a correct-bytes control passes.
- **Algorithm coverage:** verification works for sha256/sha384/sha512 (at least sha256 and sha512), and a
  wrong-length / malformed SRI is rejected (delegated to the policy gate).
- **POLICY_REJECTED passthrough:** an un-pinned range, a remote (`https://…`) source, an unknown field, and a
  lifecycle-script / `hasInstallScript:true` / `requiresBuild:true` indicator each cause a fail-closed rejection with
  no artifacts resolved (the gate fires first).
- **Trust-boundary / fail-closed:** a cyclic object, a getter/accessor-bearing top-level params object, a
  `__proto__`-keyed packages map, and a hostile-iterator array do NOT throw — each returns a rejection. The existing
  `resolve.test.ts` suite still passes unchanged.
Do NOT add hidden/rotating cases here; the orchestrator verifies independently and may add hidden cases.

## Performance & security constraints
Pure and deterministic (spec §8.2): no I/O, no network, no subprocess, no FFI, no lifecycle scripts, no remote
imports (§9.3). Fail-CLOSED on every invalid/ambiguous/exotic input; a throw at this trust boundary is a DoS and a
test failure. The TS runtime is UNPRIVILEGED — this resolver only computes a resolution from supplied data; it never
mutates the host (privileged mutation belongs solely to the narrow Go agentd, which re-validates from a typed
manifest, never from raw runtime text). NO real keys/secrets — integrity uses public SRI hashes only; signing/TPM/
recovery key material is owner-held (§16) and must never be committed or generated. `node:crypto` `createHash` only
(no key/HMAC material). Linear-time over the lockfile; bounded by `safeNormalize`'s depth/node caps.
