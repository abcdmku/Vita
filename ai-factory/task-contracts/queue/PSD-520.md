## Objective
Remove the placeholder in the smoke VM compositor self-test where window textures are **hardcoded solid-color rectangles** generated from a hardcoded 3-window layout, so the resulting `VITA-COMPOSITOR status=OK` + GPU-readback PNG can no longer be mistaken for "the live desktop renders."
- Evidence: `os/x86_64/compositor-smoke-layout.mjs:16-37` constructs `NativeCompositorPort` with a hardcoded `colors` map (`surface:desktop`=`18344eff`, `surface:panel`=`12181fff`, `texture-files`=`e6edf2ff`, `texture-notes`=`fcebb3ff`, `texture-terminal`=`1f232cff`) and a hardcoded 3-window layout (`smokeWindow("files"…)`, `"terminal"`, `"notes"`), producing the solid-fill command stream at `os/x86_64/smoke-overlay/usr/lib/vita/compositor/vita-compositor-smoke.commands:1-11`. The selftest/service header calls this "TS driver-produced compositor layout"; the run emits `VITA-COMPOSITOR status=OK` + a GPU-readback PNG used as the boot "desktop renders" proof.
- Real fix (pick the honest-scoped option that fits the existing driver surface, prefer (a)):
  - **(a) Real content:** drive each window texture from actual app/CEF buffer-surface content the way the cef-live path does — i.e. the per-window RGBA comes from an injected buffer-surface source, NOT from a literal hardcoded `colors` map / per-window constant fill in this generator. The hardcoded `colors` object and the hardcoded literal RGBA fills must be GONE from `compositor-smoke-layout.mjs`; texture pixels must originate from the injected source (which may be a deterministic, test-supplied buffer-surface provider — but it is injected, not a constant baked into the generator).
  - **(b) Honest marker (fallback if (a) is out of scope for R1):** keep the solid-color self-test but RENAME the emitted marker (and the smoke-overlay header text) from the bare `VITA-COMPOSITOR status=OK` / "desktop renders" wording to an honestly-scoped name (e.g. `VITA-COMPOSITOR-SELFTEST status=OK` describing a compositor wiring/path self-test, NOT live desktop content), so the green status cannot be read as proof that the flagship desktop rendered. The misleading "desktop renders" / "TS driver-produced compositor layout" framing must be GONE.
- Add `sdk/typescript/test/ui-kits/compositor-smoke-layout.test.ts` that imports the generator's layout-building logic (extract a pure exported helper from `compositor-smoke-layout.mjs` if needed so it is unit-testable without writing files) and asserts the chosen fix.

## User value
The boot "desktop renders" proof becomes truthful: a green compositor self-test either reflects real injected app/CEF content or is clearly labelled as a wiring self-test — so reviewers and the boot gate cannot mistake a hardcoded solid-color rectangle for the live flagship desktop.

Do NOT weaken or delete the smoke boot check — keep it deterministic and green; only make its meaning honest. NO network, NO remote imports.
