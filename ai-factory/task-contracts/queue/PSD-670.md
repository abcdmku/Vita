## Objective
Add a selectable **btrfs** data-filesystem build path for the decrypted LUKS2 `/var` volume, per spec §10.1/§10.2
(btrfs on the encrypted data volume for checksums, subvolumes, quotas, and read-only snapshots). Today the
`VITA_LUKS=1` path labels the inner volume `vita-data` but `mkfs` it as **ext4**
(`os/x86_64/build-and-boot.mjs:347` runs `mkfs.ext4 -F -L vita-data`; `os/x86_64/verity-overlay/usr/lib/systemd/system/var.mount:18`
declares `Type=ext4`). Introduce a `VITA_BTRFS=1` build switch that:
- formats the decrypted `/dev/mapper/vita-data` with `mkfs.btrfs` (replacing the ext4 mkfs only for the **data
  volume** — OS roots stay immutable dm-verity, untouched);
- mounts `/var` as btrfs (`Type=btrfs`, drop `x-systemd.growfs` which is ext4/xfs-specific; keep
  `nofail,x-systemd.device-timeout=5s`) on the same `/dev/mapper/vita-data` mapper produced by
  `os/x86_64/verity-overlay/usr/lib/vita/luks/vita-data-unlock.sh`;
- leaves the **ext4 path fully selectable** so non-btrfs smoke (`VITA_BTRFS` unset) still boots unchanged.
- emits a new boot marker `VITA-BTRFS: fstype=btrfs onMapper=OK status=OK` from a
  `vita-btrfs-marker.sh` overlay unit, gated so it only asserts when btrfs is selected.

Scope is the data volume only. `VITA_BTRFS=1` requires `VITA_LUKS=1` (and thus `VITA_VERITY=1`); fail-closed with a
clear error otherwise, mirroring the existing `VITA_LUKS=1 requires VITA_VERITY=1` guard at
`os/x86_64/build-and-boot.mjs:561`. Do NOT alter the LUKS unlock resolver, the closed key-source order, or the
existing `VITA-LUKS` persistence semantics — `/var` must still mount ONLY the mapper, never the plaintext outer.

## User value
Brings the encrypted data volume to the spec-mandated filesystem (§10.2): per-block checksums catch silent
corruption, and subvolumes/quotas/read-only snapshots become available for later backup/rollback work — without
touching the immutable verity OS roots or the LUKS trust path.

## Non-goals
- NO subvolume layout / quota groups / snapshot scheduling yet (this slice only lands the btrfs filesystem +
  mount + marker; subvolumes are a follow-up).
- NO change to dm-verity OS roots, the LUKS2 outer container, the unlock resolver, or the key-source order.
- NO removal of the ext4 path — it stays the default and must keep booting when `VITA_BTRFS` is unset.
- NO TPM/recovery key work (owner-held, see Security/constraints).

## Acceptance
`acceptance_command` passes: the deterministic Node build-unit test
`os/x86_64/test/btrfs-data.test.ts` asserts that with `VITA_BTRFS` unset the build still synthesizes the **ext4**
data path (the named case `ext4 fallback synthesizes when VITA_BTRFS unset` is green; this case must EXIST and run,
not pass vacuously). The same test file also asserts that with `VITA_BTRFS=1` (and `VITA_LUKS=1`) the build plan
selects `mkfs.btrfs` for the mapper and a `Type=btrfs` `/var` unit, and that `VITA_BTRFS=1` without `VITA_LUKS=1`
fails closed.

**Host-verify boot gate (orchestrator runs this; not the worker's acceptance_command — workers have no QEMU):**
a `VITA_LUKS=1 VITA_BTRFS=1` Borg51 QEMU boot must show, on the serial console:
- `findmnt -n -o FSTYPE --target /var` == `btrfs` AND `findmnt -n -o SOURCE --target /var` resolves to
  `/dev/mapper/vita-data` (never the plaintext outer);
- the new marker `VITA-BTRFS: fstype=btrfs onMapper=OK status=OK`;
- the existing two-boot `VITA-LUKS: encrypted=OK unlocked=OK persists=OK ... status=OK` persistence marker still
  passes on the btrfs `/var`.

## Security/constraints
- **R3 — privileged storage/boot component. DO NOT MERGE on worker or orchestrator say-so.** Requires the
  human/owner approval gate per CLAUDE.md §3 (R3 = two human approvals; the active auto-merge override still
  requires independent verification + a GPT-5.5 xhigh `npm run review` `approve` AND the human storage-owner
  sign-off recorded in `STATE.md` before integration). This contract is **propose-only** for the worker.
- **Owner-held material (spec §16):** TPM-sealed slots and N-of-M recovery keys remain STUBS
  (`os/x86_64/verity-overlay/usr/lib/vita/luks/vita-data-unlock.sh:18-30`). This slice MUST NOT generate, escrow,
  ship, or wire any signing/recovery/TPM key, and MUST NOT touch the closed key-source order. Build-only throwaway
  TEST keyfile path is unchanged.
- Fail-closed: `/var` mounts only `/dev/mapper/vita-data`; a wrong/absent key must not fall open to plaintext.
  `VITA_BTRFS=1` without `VITA_LUKS=1` is a hard build error.
- Determinism: build-plan synthesis stays pure/no-I/O so the unit test is byte-stable. No remote imports;
  lockfile; no package lifecycle scripts; no FFI/native addons.
- `allowed_network: false`.

## Rollback plan
- `VITA_BTRFS` is opt-in and defaults off: not setting it yields the byte-identical existing ext4 LUKS path.
- Revert is a clean `git revert` of the task branch; no on-disk migration is performed (fresh format only), so
  reverting before any owner deploy carries no data-migration risk. The R3 gate blocks merge until owner approval,
  so nothing reaches a customer system pre-approval.
