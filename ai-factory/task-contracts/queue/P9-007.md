## Objective
The FIRST capability migration onto the shared manifest (ADR 0007), establishing the repeatable pattern.
Author a manifest for the `hostname` capability whose rules MATCH the agent's hand-written hostname
validator (`agent/capabilities/hostname` — read it for the exact rules: the request shape + the hostname
constraints), and PROVE the match via conformance.
- **`schema/capabilities/hostname.json`**: the hostname capability's request as a manifest in the dialect
  (named formats only — use `format:"hostnameRFC1123"` + `maxLength` for the hostname field; the request's
  other fields per the agent). Regenerate the TS const (`npm run gen:manifests` ⇒ adds `HOSTNAME_MANIFEST`).
- **`schema/capabilities/conformance/hostname.json`**: ≥ 15 accept/reject vectors covering the hostname
  rules (valid hostnames; too-long; bad chars; IPv4 form; empty; absent required field; etc.).
- **`sdk/typescript/test/hostname-conformance.test.ts`**: the TS manifest validator matches every vector.
- **`agent/internal/capmanifest/hostname_conformance_test.go`**: BOTH (a) the Go manifest validator matches
  every vector, AND (b) the Go manifest validator agrees with the AGENT's actual hostname-capability
  validator on every vector — i.e. the manifest faithfully captures the cap's real rules (if the cap
  validator isn't directly invokable, drive it through the cap's public validate/decode entrypoint). Any
  disagreement FAILS — this is the migration's correctness proof.
- **Evaluator registry:** add `HOSTNAME_MANIFEST` to the default `CapabilityManifestRegistry` the evaluator
  (P9-001) / apply path uses, so `evaluateNodeConfig` now covers hostname too. (If the registry currently
  lives in the evaluator/test, extend it; expose a shared default registry built from the generated manifests.)

## User value
The repeatable cap-migration pattern + the first expansion of whole-node apply coverage beyond timesync —
hostname configs now evaluate to validated plans, PROVEN to match what the agent enforces (no drift).

## Non-goals
- Do NOT rewrite the agent hostname cap's validator (the agent keeps it; conformance proves the manifest
  matches it). No transport/wiring changes. No IP-literal format. Additive manifest + conformance + registry entry.

## Dependencies
P9-005 (Go validator + dialect), P9-006 (the conformance pattern), P9-001 (the evaluator + registry). All merged.

## Acceptance tests
`acceptance_command` runs the TS hostname conformance. The ORCHESTRATOR runs the Go conformance in the
container (`node tools/build/go-in-docker.mjs --dir agent test ./internal/capmanifest/...`) — BOTH the
manifest≡corpus AND manifest≡agent-validator assertions must pass — and `npm run typecheck` + the evaluator
tests (now covering hostname). A wrong corpus expectation must fail.

## Reviewer revision (round 2 — BLOCKING: the evaluator-coverage DoD + a codegen-emitted default registry)
Round 1 added the hostname manifest + conformance (good) but did NOT make `evaluateNodeConfig` cover
hostname — there is no shared default registry (the evaluator takes one as a parameter). Establish that
infrastructure ONCE so every future migration is just a JSON file:
- **Codegen emits the default registry.** Extend `tools/schema/gen-capability-manifests.mjs` to also emit,
  in `capability-manifests.generated.ts`, a `DEFAULT_CAPABILITY_MANIFESTS` — a deep-frozen mapping of EVERY
  `schema/capabilities/*.json` manifest, keyed by its `capability` field (so timesync + hostname today,
  auto-including future caps). `capability-manifest.ts` exports it plus a helper
  `defaultCapabilityRegistry(): CapabilityManifestRegistry` (a `ReadonlyMap` over it).
- **Keying consistency:** ensure each manifest's `capability` key is the SAME identifier the evaluator's
  config + the agent operation use (audit timesync vs hostname — align them; the registry key must match
  what `evaluateNodeConfig` looks up). Document the convention.
- **Evaluator covers hostname.** Add `sdk/typescript/test/capability-registry.test.ts` asserting the default
  registry contains timesync + hostname, and extend the evaluator tests so `evaluateNodeConfig(<hostname
  config>, defaultCapabilityRegistry())` produces a valid plan and an unknown cap still rejects.
- Keep the freshness gate (the generated registry stays in sync with the JSON files).
Keep round-1's manifest + conformance (incl. manifest≡agent-validator) intact.
