## Objective
Phase-5 "AT Protocol PDS module", v1 slice: add a **local AT-Protocol repository/records store** to the node, built
ON TOP of the existing `pds.sync-state` cursor (P1-042, `agent/capabilities/pdssync/pdssync.go`). The sync-state stores
ONE cursor per repo (repo DID + cursor + repoHead CID); this slice adds the **records inside that repo** plus the
**commit log/cursor** that orders them — the data half of the PDS, scoped to LOCAL repo CRUD only.

The privileged, persistent store is a **NEW agentd capability `pds.repo`** in Go (`agent/capabilities/pdsrepo/`),
because persistent on-device state may be mutated ONLY by the narrow privileged Go agent — never by the unprivileged
TS runtime directly (the P1-042 boundary). The unprivileged runtime PROPOSES a re-validatable record/commit request
over the existing `/apply` (write) + `/state` (read) transport; agentd RE-VALIDATES from the decoded manifest/struct
(never raw runtime text), persists transactionally (atomic-write + undo, single commit point), and FAILS CLOSED on any
invalid input. Model the whole capability on `pdssync.go` — reuse its proven patterns verbatim where they fit.

Concretely:
- **New capability `pds.repo`** (`Name = "pds.repo"`), registered in `agent/cmd/agentd/main.go` alongside
  `pdssync.NewCapability()`. It owns a per-node repo store file under `defaultStateRoot` (`/var/lib/vita-agent`, e.g.
  `pds-repo.json`) using the SAME atomic-write/undo/`transaction.Undo` machinery as `pdssync.go`
  (`os.CreateTemp(stateRoot, ".pds-repo-*.tmp")` → Chmod 0600 → Write → Sync → Close → `os.Rename` as the SINGLE commit
  point; an `Undo` that Replaces the prior snapshot). NO new transport surface beyond the existing typed Apply + Read.
- **Repo model (v1, local):** a repo is keyed by its `repo` DID (the SAME `did:plc:`/`did:web:` validator as
  `pdssync.isSupportedDID` — reuse it, don't fork a weaker copy). It holds an ordered set of **records**, each:
  `{ collection, rkey, valueDigest }` where `collection` is an NSID-shaped string, `rkey` is a record key
  (`[A-Za-z0-9._~:-]`-bounded, length-capped), and `valueDigest` is the SHA-256 hex digest of the record value (the
  record VALUE BYTES themselves are NOT stored in this slice — only their digest + key, keeping the store small and the
  trust surface narrow; storing full record bodies is a later slice). A monotonic **commit cursor** (`int64`, the same
  `0..9007199254740991` bound + non-regression rule as pdssync) orders commits; each Apply that creates record(s)
  advances the cursor and is recorded in an append-only **commit log** entry `{ cursor, op, collection, rkey }`.
- **Operations (v1 = local CRUD + commit log):**
  - **create-record:** Apply a `{ desired: { repo, commit:{cursor}, records:[{collection,rkey,valueDigest}, …] } }`
    request (the EXACT decode-target shape — define it, document it, mirror the pdssync `UnmarshalJSON` discipline:
    `RejectDuplicateObjectKeys`, `rejectUnknownFields`, `isSecretFieldName` inline-secret rejection, required-field
    checks, integer-literal cursor (no `.`/`e`/`E`), explicit-presence for optional fields via pointers). Creating a
    record that already exists at `(collection, rkey)` with a DIFFERENT digest is a CONFLICT → reject (fail-closed,
    no silent overwrite); identical (collection,rkey,valueDigest) is IDEMPOTENT (a no-op converge, like pdssync's
    same-desired-state). The commit cursor MUST NOT regress.
  - **read records / commit log:** a typed Read (like `pdssync.ReadRequest`/`ReadResponse`) returning
    `{ exists, repo, records:[…], commitCursor, log:[…] }` (re-serialized canonical form of the VALIDATED struct, never
    the raw stored bytes — the duplicate-key/last-wins TCB hazard from AGENTS.md §2).
  - Scope v1 to CREATE + READ (+ the commit cursor/log). DELETE/UPDATE of records, full record bodies, and the firehose
    subscription are explicitly later slices.
- **On-device wiring** (`os/x86_64/ts-overlay/usr/lib/vita/ts/vita/pds-repo.ts`, mirroring `vita/pds-write.ts` +
  `vita/pds-read.ts`): build a FIXED, idempotent `pds.repo` create request (a deterministic test repo DID matching the
  P1-042 test repo + a couple of fixed records + a commit cursor), drive it through the vendored `applyNodeConfig` /
  `/apply` path, then READ it back via the agent client `/state`. Format the marker from agentd's MEASURED outcome.
- **`main.ts`:** AFTER the existing `VITA-PDS-WRITE` marker, apply the `pds.repo` create + read it back and print
  `VITA-PDS-REPO: records=<N> committed cursor=<K> status=OK` where N + K come from the READ-BACK of agentd's persisted
  state (NEVER synthesized from the request — the read-back is the proof the records committed). Also drive a
  DELIBERATELY-INVALID `pds.repo` request (e.g. a regressed commit cursor, a bad DID, a conflicting record, or an
  inline-secret field) and print `VITA-PDS-REPO: outcome=rejected reason=<sanitized> status=OK` proving agentd fails
  closed; transport/read failure → `VITA-PDS-REPO-ERROR: status=FAILSAFE`. Keep ALL prior markers.

If `pds.repo` is not already in the on-device evaluator's manifest registry / capability-manifest dialect, NOTE that gap
in the worker report (a follow-up manifest slice) rather than forcing a divergent manifest — the load-bearing trust
surface this slice is the AGENT validator + the apply/read transport, exactly as P1-042 drove pds.sync-state.

## User value
The first real DATA inside the PDS: the node can hold an AT-Protocol repository's records and an ordered commit log on
its own persistent storage, written through the privileged boundary and surviving reboot — the foundation of FR-018
("install and manage an AT Protocol PDS module"). pds.sync-state proved the node remembers a cursor; this proves it
remembers the repo's CONTENT, fail-closed, with no new attack surface and no federation yet.

## Non-goals
NO federation / relay / firehose / `com.atproto.sync.subscribeRepos` (explicitly Phase-5-later). NO real DID resolution
or PLC directory calls (offline; the repo DID is validated syntactically, reusing pdssync's validator). NO full record
VALUE bodies stored (digest + key only this slice). NO UPDATE/DELETE of records (CREATE + READ + commit log only). NO
MST/Merkle-Search-Tree or signed commit objects yet (the commit cursor/log is the v1 ordering primitive). NO new
transport surface beyond the existing typed Apply + Read. NO direct `/var` write from the runtime (agentd owns the
store). NO keys/secrets — signing/PLC-rotation/TPM keys are OWNER-HELD (§16); use ONLY syntactic TEST DIDs/digests,
never generate or commit production key material. Benign + idempotent.

## Performance & security constraints
The TS runtime is UNPRIVILEGED and only PROPOSES; agentd (the sole privileged mutator) RE-VALIDATES from the decoded
typed struct (never raw runtime text), persists transactionally with a single commit point + working undo, and FAILS
CLOSED on any invalid/partial/exotic input (reuse pdssync's validators — neither stricter nor looser). Apply surface =
exactly the existing `/apply` + `/state` (no new endpoint). Idempotent benign request. Re-serialize the VALIDATED struct
on read (never echo raw stored bytes — the duplicate-key TCB hazard). No FFI/shell/`os/exec` on runtime-controlled
input. No remote imports; lockfiles mandatory; no package lifecycle scripts (TS side). No keys/secrets — TEST DIDs and
SHA-256 hex digests only; reject inline-secret-named fields. R3 (privileged persistent store on the TCB path) → two
parallel Codex candidates + reviewer (`npm run review`) gate before merge.
