## Objective
Tie the two merged layers together: when the unified app model (PSD-008 `AppHost`) launches an app, a window surface
should flow through the WM into the compositor driving seam (PSD-009 `CompositorDriver`) — so "launch app" becomes
"window on the GPU". Pure, deterministic, headless TypeScript over INJECTED ports (the real AppHost + CompositorDriver
are injected; tests use fakes). NO GPU/FFI.
- An `AppWindowHost` that observes `AppHost` launch/stop events (via an injected subscription/port) and maintains the
  shell+WM window model the `CompositorDriver` reconciles: launch → add a window surface (default placement from the
  app's window hints + WM policy), stop → remove it, with the surfaceKind (tsx/wasm/container/web) carried through.
- **Consistency:** a launch whose window registration fails rolls back the app launch (or records pending cleanup) —
  reuse PSD-008's fail-closed lifecycle invariants; never leave an app running with no window or a window with no app.
- Deterministic ordering + idempotent reconcile (reuse PSD-009's driver semantics; don't fork them).

## User value
The missing glue: the app platform (PSD-008) and the GPU pipeline (PSD-009/010) become one flow — launching a TSX/web/
wasm/container app yields a managed window driven onto the GPU. The spine of the actual desktop UX.

## Non-goals
- NO real content/textures (the window surface is a placeholder until the content rasterizer/CEF lands) — this wires
  the LIFECYCLE (app↔window), not pixels. NO GPU/compositor/AppHost/driver changes (compose them via injected ports).

## Acceptance
`acceptance_command` passes: launch→window-add, stop→window-remove, surfaceKind carried, failed window-registration
rolls back the launch fail-closed, idempotent reconcile; comprehensive unit tests with fake AppHost + fake
CompositorDriver. Pure, headless.

## Security/constraints
- Compose via INJECTED ports only; fail-closed on registration/teardown failure (no app-without-window or
  window-without-app); pure/deterministic. No remote imports; lockfile; no lifecycle scripts.

## Definition of done
- `AppWindowHost` composing PSD-008 AppHost + PSD-009 CompositorDriver (launch↔window lifecycle, fail-closed,
  idempotent) over injected ports; comprehensive unit tests incl. rollback; typecheck clean. R1 review + integrate.

## REVISION 1 (Codex R1: real event subscription + fail-closed maybe-landed rollback — 2026-06-25)
1. The AppHost port is only launch/stop/snapshot with a manual `observe()` — the contract requires AppWindowHost to
   OBSERVE AppHost launch/stop via an INJECTED subscription. Define an injected `AppHostEvents`-style port
   (`subscribe(listener) -> unsubscribe`, delivering launch/stop events) that AppWindowHost uses to AUTO-produce/remove
   windows; an app launched through the real AppHost must automatically yield/withdraw a compositor window. Tests: a fake
   AppHost emits launch/stop through the port → windows appear/disappear without a manual call.
2. Fail-closed rollback (index.ts ~257): a failed window `registerSurface` MAY have partially landed in the injected
   compositor port, but the code reconciles from the CompositorDriver's (uncommitted) snapshot + records no pending
   cleanup → can leave a native window with no app. Treat a failed registerSurface as "surface MAY be live": attempt
   removeSurface and/or record a pending-cleanup retry; NEVER leave app-without-window or window-without-app. Test:
   registerSurface throws → end state has no untracked live window (removed or pending-cleanup).

## REVISION 4 (COMPREHENSIVE maybe-live consistency — all rollback paths at once — 2026-06-25)

multi-app scope → now rollback-stop-fail). Fix the ROOT comprehensively. INVARIANT: a compositor reconcile/register/
update MAY land in the injected compositor before the driver commits, so the failed launch's OWN newly-introduced

  failed launch's surfaces; on any cleanup/stop failure, record pending-cleanup that RETAINS those surfaces as

TEST MATRIX (add; keep the 9): for each path {createSurface-fail, WM-emit-fail, reconcile-throw, rollback-AppHost-stop-

## REVISION 5 (Codex R1: subscription + own-launch double-process race — single serialized path — 2026-06-25)
rev4's comprehensive maybe-live fix landed, but a design tension remains: with `appHostEvents` configured, the
AppWindowHost processes a launch TWICE — its own `launch()` calls `appHost.launch()` AND independently reconciles, while
the subscribed AppHost launch event ALSO queues `observe(launch)`. `#eventQueue` serializes only subscribed events, not
the public `launch()/stop()/reconcile()`, so on compositor failure two `#rollbackLaunch()` can race the same AppLaunch
(one stops the app; the other sees APP_NOT_RUNNING → stale pending cleanup / rollback-failure). FIX: ONE serialized
lifecycle path — route the wrapper's own `launch()/stop()/reconcile()` through the SAME `#eventQueue` as subscribed
events, and DEDUPE so a given app launch/stop is processed EXACTLY ONCE (whether triggered by the wrapper's method or by
the subscribed event for the same launch — coalesce by launch/app id). No concurrent double-rollback; deterministic
ordering preserved. Add a regression for the REAL combined path: `appHostEvents` configured + call `host.launch()` +
the AppHost emits its launch event + the compositor fails → exactly one rollback, consistent fail-closed end state (no
stale pending cleanup, no double-stop). Keep all existing tests.
Verify: npm run typecheck && node --experimental-strip-types --test sdk/typescript/test/app-window-host/*.test.ts

## REVISION 6 (COMPREHENSIVE: reconcile against CURRENT truth, robust to any event delivery order — 2026-06-25)
The dedupe-by-id-with-deletion (rev5) breaks under DELAYED async event delivery: deleting the opposite-event dedupe key
(index.ts:223,280) lets a late subscription event fall through and apply STALE intents against changed state (e.g.
launch then stop, then the delayed launch event reconciles a stopped app → window-with-no-app; symmetric stop-after-
relaunch removes the live window). Stop patching dedupe; fix the ROOT: EVERY lifecycle action — whether from the
wrapper's own `launch()/stop()` OR a (possibly delayed/out-of-order) subscribed AppHost event — must be applied by
RECONCILING the window model to the CURRENT AUTHORITATIVE AppHost state (the live snapshot), NOT by replaying the
event's captured intents. A delayed/stale event must NEVER apply intents that contradict current truth: derive the
desired window set from "which apps are currently running per AppHost" and reconcile to that; an event for an app whose
current state no longer matches is a no-op (already reflected) or reconciled-to-truth, never a stale mutation. Serialize
through the one queue; idempotent; fail-closed. Tests MUST exercise DELAYED/out-of-order delivery: the subscription fake
emits events ASYNCHRONOUSLY and out of order relative to the wrapper's calls — assert the final window set always equals
the current AppHost running set (no window-without-app, no app-without-window) regardless of delivery order. Keep all
existing tests.
