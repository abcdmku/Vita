## Objective
Close the Phase-4 application-lifecycle deliverable (spec §21 "App lifecycle and health checks", "Package
backup/update hooks") and the matching exit gate **"Verified app update can be restored to pre-update state."**
A capsule is RUNNING today (`capsule.execute`, P1-044), is health-supervised (`capsule.health` via the P1-047
supervisor in `agent/internal/capsule-runtime`), and the node has a verifiable backup/restore capability
(`backup.archive`, P1-066). This slice adds the missing **lifecycle controller** that ties them together.

Add a NEW privileged Go capability `capsule.lifecycle` in `agent/capabilities/capsule/lifecycle.go` (registered in
`agent/cmd/agentd/main.go`) with three operations, each driven by a re-validated manifest (never raw runtime text)
and each transactional (validate → act → record undo → audit), fail-CLOSED:

- **update** (the keystone — the exit gate): given a target capsule id + the new version's installed entry/manifest:
  1. **backup-before-update hook** — invoke the existing `backup.archive` Create path over the capsule's own
     persistent state (its `StateDirectory`/volume roots from the running `ExecuteStatus`/manifest, the same
     `/var/lib/...` state P1-046 mounts) to produce a verifiable point-in-time archive (capture its `backupId`).
     If the backup or its post-create verify fails, ABORT the update with no change (fail-closed — never update an
     app whose state could not be safely captured).
  2. **stop old** — stop the currently-running transient unit (reuse the `capsule.execute` stop/undo path).
  3. **start new** — start the new version as a hardened transient unit (reuse `capsule.execute`'s manifest-only
     unit composition + the `vita-ts.service` hardening template; NO new spawn surface, NO raw unit text).
  4. **health-gate** — wait (bounded, with the manifest `healthChecks` interval/timeout) for the new unit to report
     `StatusOK` from the P1-047 supervisor.
  5. **rollback-on-unhealthy** — if the new version does NOT become healthy within the gate, STOP the new unit,
     RESTORE the captured backup (`backup.archive` Restore of `backupId`), and RESTART the previous version, so the
     node returns to its pre-update state. The update Apply RETURNS an error (rejected), and its Undo is a no-op or
     the same restore (idempotent), so the transaction engine never records a committed-but-broken state.
- **restart** — stop then re-start the SAME capsule's unit (same manifest), health-gate, record undo.
- **stop** — stop the running unit, record an undo that re-starts it.

**Health-driven hook:** the P1-047 supervisor already detects unhealthy workloads (detect+report only). This slice
adds the POLICY half: a small policy field on the manifest (`lifecyclePolicy: { onUnhealthy: "restart" | "fail" }`,
default `fail`) that the lifecycle controller honors when asked to remediate an unhealthy workload — `restart` runs
the restart op (bounded retry/backoff count), `fail` stops it and records the failed status. The remediation entry
point is agentd-driven (the unprivileged TS runtime PROPOSES `capsule.lifecycle{op:"remediate", id}` over the
existing unix apply transport; agentd re-validates and acts) — NO autonomous privileged background loop is added in
this slice (the supervisor stays read/report; remediation is an explicit, audited, transactional operation).

Markers (emitted by `main.ts` from agentd's outcome):
- `VITA-CAPSULE-LIFECYCLE: op=update id=<id> from=<v1> to=<v2> backup=<backupId> health=OK status=OK`
- `VITA-CAPSULE-LIFECYCLE: op=update id=<id> rollback-on-unhealthy=OK restored=<backupId> status=OK` (the new
  version was forced unhealthy → agentd rolled back to the pre-update state; the gate is MEASURED, not synthesized)
- `VITA-CAPSULE-LIFECYCLE-REJECT: op=<op> reason=<code> status=OK` (unknown/invalid manifest → fail-closed; no unit
  touched, no backup taken on a rejected request)
- `VITA-CAPSULE-LIFECYCLE-ERROR: status=FAILSAFE` (transport/unexpected — never crash the oneshot)

The on-device boot marker the orchestrator measures: `VITA-CAPSULE-LIFECYCLE: update=OK rollback-on-unhealthy=OK`
(a single summary line printed after both the happy-path update AND the forced-unhealthy rollback have run).

## User value
The node can SAFELY update its apps: an app update is always preceded by a verifiable backup of the app's state and
is automatically rolled back to the exact pre-update state if the new version is unhealthy. This is the Phase-4 exit
gate "Verified app update can be restored to pre-update state" — the difference between a personal node you trust to
self-update and one you don't. Plus restart/stop for routine lifecycle and a policy for unhealthy workloads.

## Non-goals

proposed+audited op — a future slice may add an opt-in policy daemon). NO OCI/WASM-specific lifecycle quirks (reuse

## Performance & security constraints
The unprivileged Deno runtime only PROPOSES lifecycle ops over the existing ADR-0008 unix apply transport; agentd is
the SOLE privileged actor — it RE-VALIDATES the manifest and composes any transient unit ONLY from validated fields +
the `vita-ts.service` hardening template (DynamicUser, empty CapabilityBoundingSet/AmbientCapabilities,
NoNewPrivileges, ProtectSystem=strict, seccomp, cgroup caps), NEVER from raw runtime-supplied unit text. Fail-CLOSED
at every step: invalid/unknown → reject with no side effects; backup-create/verify failure → abort the update;
new-version unhealthy → rollback to pre-update state and return error. No new spawn surface beyond `capsule.execute`'s.
Lifecycle ops act ONLY on the capsule's own computed unit (no arbitrary-unit control). NO keys/secrets — signing/TPM/
recovery-key material is owner-held (§16); tests use only baked test capsules + injected fakes. No remote imports;
lockfiles mandatory; no package lifecycle scripts; no FFI/native addons in the TS sandbox (spec §9.3). Bounded
health-gate + bounded remediation retry (no unbounded loops/thundering herd).

## REVISION 2 (Codex R2 review: REVISE — 2 blocking — 2026-06-24)
1. **Health gate must MEASURE, not assume.** `lifecycle.go:664` returns healthy when a manifest has no checks — absence
   is treated as healthy. FIX: the update/restart health gate must be gated on the P1-047 supervisor StatusOK
   measurement (the unit is genuinely active/healthy), never "no checks => healthy".
2. **restart must restore the prior on failure (no left-stopped state).** `restart` stops the running capsule then, on
   start-failure or health-gate-failure, returns an error WITHOUT restarting the prior instance — and the transaction
   engine records no undo when Apply returns an error, so the capsule is left STOPPED. FIX: on any restart failure after
   the stop, RESTART the prior instance (explicit rollback in the op) so a failed restart leaves the capsule RUNNING as
   before (fail-closed to the prior good state, no stuck-stopped).
Verify: go-in-docker tests (health-gate uses real status; restart-failure restores prior running) + Borg51 boot
VITA-CAPSULE-LIFECYCLE update=OK rollback-on-unhealthy=OK.

## REVISION 3 (Codex R2 review: REVISE — recurring transactional-undo gaps — 2026-06-24)
Same class recurring: ops that MUTATE then return an error on a later step leave a partial/stopped/untracked state,
because the transaction engine records NO undo when Apply returns an error. `stopManifest` stops + clears tracking then
returns on Teardown-fail; the backup-before-update path; restart. FIX COMPREHENSIVELY — make EVERY lifecycle op
(update/restart/stop/remediate) transactional with EXPLICIT in-op rollback: if any step after a mutation fails, the op
must RESTORE the prior good state (re-start the previously-running unit, re-track it, undo partial teardown) BEFORE
returning the error — so a failed Apply leaves the capsule EXACTLY as before (running+tracked if it was). NEVER a
stopped/untracked/partial residue on any error path. (The only intended state changes are on SUCCESS.) Add tests for each
op's failure path asserting prior-state restoration (running+tracked) on: start-fail, health-gate-fail, teardown-fail,
backup-fail. Verify: go-in-docker lifecycle tests (every failure path restores prior running+tracked) + Borg51 boot
VITA-CAPSULE-LIFECYCLE update=OK rollback-on-unhealthy=OK.

## REVISION 4 (Codex R2: REVISE — rollback path itself unsafe + racy backup id — 2026-06-24)
1. **restoreAndRestart must not leave a MIXED state.** `restoreAndRestart` restarts the prior version even when the
   backup Restore failed (lifecycle.go:672/678) — leaving the OLD binary running against NEW/unrestored state while Apply
   returns an error and no undo is recorded. FIX: the rollback must reach the prior GOOD state atomically — restore THEN
   restart prior; if Restore FAILS, do NOT restart against unrestored state — leave the capsule STOPPED and return a
   clear `rollback_failed` error (fail-CLOSED; never a mixed old-binary/new-state running capsule). Test: restore-fail
   during rollback => capsule stopped + rollback_failed error, NOT running-mixed.
2. **Backup id must come from the Create RESULT, not racy last-state.** The adapter reads `backup.archive` last-state via
   `readLast` after a separate Apply (lifecycle.go:905); concurrent agentd requests can change `.last` between create and
   read => verify/restore the WRONG backup. FIX: obtain backupId directly from the archive Create RESULT (call the
   archive capability's Create/Verify/Restore methods directly, non-racy result channel) — never via mutable shared
   last-state. Test: concurrent backup update does not corrupt the lifecycle backup id.
Verify: go-in-docker lifecycle tests (rollback-restore-fail => stopped+error; backup-id from create result) + Borg51
boot VITA-CAPSULE-LIFECYCLE update=OK rollback-on-unhealthy=OK.
