## Objective
Provide the **host-side backend** that the desktop host's `postNotification` / `registerTrayItem`
methods forward into, so notifications and tray items posted by `apps`/`desktop` are actually
**stored and persist** in the real shell notification/tray store (the PSD-016 shell model:
`NotificationCenter` + `TrayModel` in `sdk/typescript/src/shell/notifications/index.ts`) instead of
being normalized/grant-checked and then dropped. Today the per-package router
(`createDesktopHostForPackage`, `sdk/typescript/src/desktop-sdk/loader.ts:468` and `:506`) validates
and grant-checks the input and then calls `host.postNotification` / `host.registerTrayItem` on the
backing `DesktopHost` — but no shippable backend wires those calls into a `NotificationCenter` /
`TrayModel` whose snapshot the Notifications screen reads. This slice builds that backend factory.
- **Factory.** Add `createShellNotificationsHost(options)` to `sdk/typescript/src/shell/notifications/index.ts`
  (re-exported from `sdk/typescript/src/desktop-sdk/index.ts` alongside the existing
  `NotificationCenter`/`TrayModel` exports). It owns one `NotificationCenter` and one `TrayModel`
  (constructed from an injected `ShellCapabilityPort` + `NotificationClock`) and returns:
  `postNotification(appId, input)` → `ShellResult<ShellNotification>` (delegates to
  `NotificationCenter.post`, storing the item); `registerTrayItem(appId, input)` →
  `ShellResult<TrayItem>` (delegates to `TrayModel.register`, storing the item); a read-back
  `snapshot()` returning the live `NotificationCenterSnapshot` + tray snapshot the Notifications
  view-model (`ui_kits/desktop/viewmodels/Notifications.ts`) consumes via its existing
  `NotificationsNotificationPort` (`Pick<NotificationCenter,"dismiss"|"snapshot">`) and
  `NotificationsTrayPort` (`Pick<TrayModel,"register"|"selectMenuItem"|"snapshot">`); `dismiss(appId, id)`
  to dismiss a stored notification; and action/menu routing back to the originating app via
  `NotificationCenter.createActionIntent` (→ `NotificationIntent`) and `TrayModel.selectMenuItem` /
  `click` / `openMenu` (→ `TrayIntent`), so an action dispatched from the panel resolves to the
  `appId` that posted/registered it.
- **Grant-gated, fail-closed.** The backend never bypasses grants: `shell.notifications.post` /
  `shell.tray.register` are enforced by the injected `ShellCapabilityPort` exactly as
  `NotificationCenter`/`TrayModel` already enforce them — a missing grant returns
  `{ ok: false, error: { code: "MISSING_CAPABILITY", ... } }` and stores nothing.
- **No host-bridge / loader behaviour change.** Do NOT change `loader.ts` routing, the validation /
  grant order, the host-bridge transport (`ui_kits/desktop/runtime/host-bridge.ts`), or the wire
  guards (`isShellNotification`/`isTrayItem`). This is the *backend* the router's `host.*` calls land
  on; values it returns must pass those existing guards unchanged.
- Put the factory in `sdk/typescript/src/shell/notifications/index.ts`, re-export it from
  `sdk/typescript/src/desktop-sdk/index.ts`, and put the test under
  `sdk/typescript/test/ui-kits/notifications-tray-backend.test.ts`. Import the SDK exactly as
  `ui_kits/desktop/package.ts` does — public `@vita/desktop-sdk` exports only.

## User value
Notifications and tray items posted by apps and the desktop now appear and persist in the
Notifications screen instead of being validated-then-discarded — the host-side sink that makes the
PSD-016 shell model a live, app-facing surface, with dismissal and action/menu dispatch routed back
to the app that owns the item.

## Non-goals
- NO DOM/CSS/CEF/rendering and no new visual design (the HTML is the design of record).
- NO change to `loader.ts` routing/validation/grant order, the host-bridge transport or wire guards,
  or the `DesktopCapability`/grant union. No new persistence backend on disk — "persist" here means
  the items survive in the live store across reads/snapshots within the host session.
- Do not re-implement `NotificationCenter`/`TrayModel` — consume them. No ambient I/O.

## Acceptance
`acceptance_command` passes. Author `sdk/typescript/test/ui-kits/notifications-tray-backend.test.ts`
with deterministic `node:test` cases against a fake `ShellCapabilityPort` (use
`createStaticShellCapabilityPort`) and a manual `NotificationClock`:
1. **postNotification stores + returns a ShellNotification.** With `shell.notifications.post` granted,
   `postNotification(appId, input)` returns `{ ok: true, value }` where `value` satisfies the
   `isShellNotification` guard from `ui_kits/desktop/runtime/host-bridge.ts`-equivalent shape
   (appId/id/title/priority/createdAtMs/actions), and a fresh `snapshot()` shows the stored item.
2. **registerTrayItem stores + returns a TrayItem.** With `shell.tray.register` granted,
   `registerTrayItem(appId, input)` returns `{ ok: true, value }` satisfying the `isTrayItem` shape
   (appId/id/iconRef/tooltip/order/menu), and `snapshot()` shows the stored tray item.
3. **View-model reads back posted items.** Construct the Notifications view-model
   (`ui_kits/desktop/viewmodels/Notifications.ts`) over the backend's notification/tray ports and
   assert it surfaces the items posted in (1)/(2).
4. **Missing grant fails closed.** Without the grant, `postNotification` and `registerTrayItem`
   return `{ ok: false, error: { code: "MISSING_CAPABILITY" } }` and store nothing (`snapshot()`
   total counts stay 0).
5. **Tray menu action routes to the registered handler.** A menu selection / click resolves to a
   `TrayIntent` carrying the `appId` of the app that registered the item; a notification action
   resolves to a `NotificationIntent` carrying the originating `appId`.
`npm run typecheck` is clean. Pure, headless, deterministic. R1 — reviewer (the orchestrator)
verifies the diff and re-runs `acceptance_command`.
