## Objective
Build the missing **theme backend** that implements the `DesktopHost.readTheme()` port
(`sdk/typescript/src/desktop-sdk/ui-package.ts:139`). Today nothing implements it on the SDK side:
the host bridge `forwardTheme` (`ui_kits/desktop/runtime/host-bridge.ts:406-413`) only forwards to an
external transport and returns the hard-coded `DEGRADED_THEME`
(`host-bridge.ts:160`) whenever the transport is missing or the value fails `isDesktopTheme`
(`host-bridge.ts:1050-1062`). This contract backs `readTheme` with the merged `VitaThemeTokens`
catalog built in PSD-023 (`sdk/typescript/src/desktop-sdk/theme-tokens.ts` — `themeTokens` /
`themeTokens.variants.{light,dark,graphite}`), selected by the settings store's stored
`appearance.theme` (and `appearance.accent`), so the rendered surface re-themes live when the user
changes the theme in Settings.
- A deterministic theme backend `createDesktopThemeBackend({ readSetting, tokens? })` that returns a
  `readTheme(): DesktopTheme` satisfying `DesktopTheme` (`ui-package.ts:92-96`): `{ id, version,
  tokens: { colors, spacing, radii, typography } }` shaped to pass the host-bridge guard
  `isDesktopTheme` (colors = string record, spacing/radii = number record, typography =
  string|number record).
- It reads the currently-selected variant from an **injected** settings reader (the PSD-345 store's
  `readSetting` port shape: `(req:{key}) => DesktopHostResult<PlainJson>`), keyed on `appearance.theme`
  (`light|dark|graphite`, the enum set from PSD-345 / `ui_kits/desktop/viewmodels/Settings.ts` — do not
  redefine it divergently), and projects the matching `VitaThemeTokens` variant group into the
  `DesktopThemeTokens` shape: map `color` → `tokens.colors` (string values verbatim), `space` → split
  into `tokens.spacing` (`space-*`/`size-*`/`*-h` numeric px) and `tokens.radii` (`radius-*` numeric
  px), and `type`+`font` → `tokens.typography`. Coerce px/unit-bearing strings to numbers for
  spacing/radii deterministically; carry `var(--…)` / non-numeric values through typography as strings.
- The returned `tokens` come straight from the catalog so a given selection → byte-identical
  `DesktopTheme` every call (pure, no `Date.now()`/`Math.random()`). `version` is a deterministic
  content marker of the projected token set (e.g. a sorted-key content hash), identical tokens →
  identical version.
- **Fail-closed**: when the settings reader errors, the `appearance.theme` key is absent, or the stored
  value is not one of the known variant ids, `readTheme()` returns the same `DEGRADED_THEME`-equivalent
  fail-closed theme the bridge expects (id `vita.host-bridge.degraded`, passing `isDesktopTheme`) —
  never a throw, never a partial/invalid theme.
- Put the code under `sdk/typescript/src/desktop-theme-backend.ts` and tests under
  `sdk/typescript/test/ui-kits/desktop-theme-backend.test.ts`. Import desktop types only from the public
  `sdk/typescript/src/desktop-sdk/index.ts` barrel and the catalog from
  `sdk/typescript/src/desktop-sdk/theme-tokens.ts` (both already public-exported), as
  `host-bridge.ts` / the view-models do.

## User value
Makes the flagship desktop actually carry its real design tokens: `readTheme` returns the live PSD-023
catalog theme matching the user's stored Appearance selection instead of the black-and-white degraded
fallback, and changing the theme in Settings (persisted by PSD-345) re-themes the surface on the next
read. This is the backend the host-bridge theme port has been forwarding into a void.

## Non-goals
- NO DOM/CSS/rendering/CEF; no host-bridge changes (`forwardTheme` already calls the port + falls back
  to `DEGRADED_THEME` — don't rewrite it). NO new visual design or new token values (PSD-023's catalog
  is the design of record — consume it, don't redefine it). Do not re-implement the settings store
  (consume PSD-345's `readSetting` port via injection) or the `/var` wiring. Do not redefine the theme
  enum divergently from `viewmodels/Settings.ts`. Do not widen capability grants or touch
  protected-policy files.

## Acceptance
`acceptance_command` passes. Deterministic unit tests in
`sdk/typescript/test/ui-kits/desktop-theme-backend.test.ts` cover, against a fake `readSetting` port
(no ambient I/O):
- `readTheme()` returns the catalog theme matching the stored selection and passes the same shape the
  host-bridge guard checks (`id`/`version` strings; `tokens.colors` string record; `tokens.spacing` and
  `tokens.radii` number records; `tokens.typography` string|number record).
- After the store reports `appearance.theme = "dark"`, `readTheme()` returns the dark variant token set
  (a dark-only override value, e.g. a `surface`/`accent` color from `DARK_TOKEN_OVERRIDES`, is present
  and differs from the light value); `light` and `graphite` likewise select their variant groups.
- An unknown/absent `appearance.theme` value, or a settings reader error, yields the fail-closed
  degraded theme (id `vita.host-bridge.degraded`) and still passes the guard shape — never throws.
- Determinism: identical stored selection → byte-identical `DesktopTheme` (deep-equal across two calls,
  identical `version`); a changed selection → a different token set and `version`.
Typecheck clean under `tsconfig.base.json`; pure/deterministic.

## Security/constraints
- Injected ports only (the `readSetting` reader) — no ambient I/O, no `node:fs`; capability-mediated
  through the store, fail-closed on missing/malformed selection. Pure/deterministic projection
  (sorted-key content marker for `version`; no `Date.now()`/`Math.random()`). No remote imports;
  lockfile mandatory; no package lifecycle scripts; no FFI/native addons.
