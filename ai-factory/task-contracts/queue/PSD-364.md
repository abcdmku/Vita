## Objective
Ship **Settings** as a separable FIRST-PARTY app package (per ADR-0016 / PSD-360), on the app-package SDK foundation
(PSD-361). Three artifacts, mirroring the flagship-package pattern + the existing
`ui_kits/desktop/viewmodels/Settings.ts`:
1. **App package** under `apps/settings/`: `manifest.ts` exporting an `AppPackage` via `defineAppPackage(...)` —
   `id: "vita.app.settings"`, `version`, `sdkVersion: SDK_VERSION`, `entry: "index.html"`, MINIMAL `capabilityGrants`
   (`settings.read`, `settings.write` from the `DesktopCapability` union, `ui-package.ts:25-34`) and a `WebAppDescriptor`
   (`surfaceKind:"web"`, `runtime:{ url:"index.html", partition:"vita-app-settings" }`, `title:"Settings"`,
   `defaultWindow`).
2. **CEF-rendered web-app entry** `apps/settings/index.html` — a static HTML/CSS settings surface (sidebar sections +
   panel), CSS-var tokens, no inline JS (behavior via the view-model / binder convention), in the design-of-record style
   of `ui_kits/desktop/Settings.html`. Minimal; NOT the acceptance target.
3. **Headless deterministic view-model** `ui_kits/desktop/viewmodels/apps/settings-app.ts` — the app's interaction logic in
   the injected-port, frozen-`snapshot()`, discriminated-union-result style of `ui_kits/desktop/viewmodels/Settings.ts`,
   built ONLY on injected `@vita/desktop-sdk` public ports (the settings read/write port subset of `DesktopHost` —
   `readSetting`/`previewSetting`/`applySetting`, `ui-package.ts:135-137`). State: section list with active section,
   appearance state (theme/accent/layout), pending preview diff. Actions: `selectSection(id)`, `readSetting(key)`,
   `previewSetting(key,value)`, `applySetting(key,value)`. All reads/writes go through the injected settings port,
   **fail-closed if the grant is missing/denied**. Deterministic ordering. NO DOM/CSS/rendering, NO platform internals, NO
   ambient I/O.

## User value
Settings becomes a swappable first-party package the dock/launcher lists + launches into its own WM window (not a shell
built-in), with real preview/apply behavior on the SDK settings port — proving the app-package pattern for a
config-bearing app with the preview->apply transaction.

## Non-goals
- NO DOM/CSS/rendering/CEF logic in the view-model; NO platform internals; NO new SDK ports (consume PSD-361 + existing).
- Do NOT bake Settings into the desktop shell or modify `ui_kits/desktop/package.ts` / `viewmodels/Settings.ts`. Do NOT
  add capabilities beyond `settings.read`/`settings.write`. OFFLINE only.

## Acceptance
`acceptance_command` passes: deterministic `node --test` unit tests at `sdk/typescript/test/ui-kits/settings-app.test.ts`
cover the manifest (`defineAppPackage` accepts it; `hasAppCapabilityGrant` true for `settings.read`/`settings.write` and
false otherwise; descriptor url === entry) and the view-model state transitions + fail-closed paths
(selectSection; read/preview/apply happy paths against fake ports; missing/denied settings grant fails closed; preview
diff shape; deterministic ordering/snapshot). `npm run typecheck` is clean. Pure, headless. (The exact test path exists
only when the work lands — an empty branch fails.)

## Security/constraints
- MINIMAL capabilityGrants (`settings.read`/`settings.write` only); injected ports only; capability-mediated +
  fail-closed; pure/deterministic. OFFLINE. No remote imports; lockfile; no lifecycle scripts.

## Hardware profiles
Portable-first; host-agnostic, runs on any dev box (no GPU/VM needed).

## Allowed tools + network
Local filesystem + Node test runner + `npm run typecheck` only. `allowed_network: false`.
