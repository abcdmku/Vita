## Objective
`previewNodeConfigChange(current, desired)` (controller/node-config): the TOP-LEVEL operator view that
validates current + desired `NodeConfig` (the P0-022 aggregate) and composes the EXISTING per-section
change-previews — `previewStorageChange` (P2-011), `previewNetworkChange` (P2-012), `previewBackupChange`
(P2-014) — into ONE unified `{ ok: true, sections: { storage?, network?, backup?, identity? }, summary } |
{ ok: false, rejections }`. Handle the three cases per section EXPLICITLY (see the Section handling rules
below) — do NOT synthesize a fake "absent" baseline and run the change-preview against it. `summary` rolls
up: sections added/removed/changed, plus security flags (`wideningInbound` from network, `weakensRetention`
from backup). Fail-closed: invalid either config ⇒ typed rejection (no diff, no throw); a section without a
dedicated preview (identity) is diffed structurally (present/added/removed).

### Section handling rules (per section, authoritative — supersedes any "baseline" idea)
- **changed** (present in BOTH): run `previewXChange(current, desired)`; use ITS diff + ITS security flag
  directly. On `!valid` ⇒ map to typed rejections.
- **added** (only in desired): validate the desired side with that section's validator
  (`validateStorageConfig`/`validateNetworkConfig`/`validateBackupConfig`) — fail-closed on rejection; the
  diff is "all desired resources ADDED" (NO synthetic removals); flags computed DIRECTLY from desired:
  network `wideningInbound = (desired has ≥1 inbound allow rule)`, backup `weakensRetention = false`
  (adding backup strengthens).
- **removed** (only in current): validate the current side; the diff is "all current resources REMOVED"
  (NO synthetic additions); flags computed DIRECTLY: backup `weakensRetention = true` (removing backup
  ALWAYS weakens retention, regardless of the prior retentionDays value), network `wideningInbound = false`
  (removing the firewall section does not widen inbound in this model).
- **absent in both**: omit the section.
NEVER construct a placeholder interface (`lo`), subvolume (`/absent/...`), schedule, or `retentionDays`
to feed a change-preview — those leak fake resources into the diff and produce wrong boundary flags.

## User value
The single "what does this whole-node config change do" view (FR-005/006) — composes every section diff +
surfaces the security-relevant flags (inbound widening, weakened backup retention) in one operator action.

## Reviewer revision (round 2 — BLOCKING, from P2-020.review.md)
The section helpers short-circuit `added`/`removed` when one side is absent and NEVER run the section's
change-preview for the present side — so an ADDED section bypasses that section preview's own fail-closed
checks (e.g. storage `DUPLICATE_SUBVOLUME_KEY`) which `validateNodeConfig` does NOT enforce. An added
storage section with duplicate app-state role/path keys returns `ok:true` instead of a typed rejection.
Round 2: for a section present in EITHER config, ALWAYS subject the present side to that section's
fail-closed validation — do NOT short-circuit. Either (a) call the section change-preview with the missing
side as the section's typed "absent" form, or (b) if a section preview cannot represent an absent side,
run that section's underlying validator (e.g. `validateStorageConfig`/`validateNetworkConfig`/
`validateBackupConfig`) on the present side directly. INVARIANT: an added/removed/changed section is NEVER
reported `ok:true` unless the present side passed the section-level validation, not just `validateNodeConfig`.
Add the regression: current WITHOUT `storage`, desired WITH a storage layout that passes
`validateNodeConfig` but is rejected by `previewStorageChange` ⇒ unified result `ok:false`. Keep it
fail-closed and never-throw.

## Reviewer revision (round 3 — BLOCKING, from P2-020.review.md)
Round 2 fixed the storage validation short-circuit but introduced/left the ANALOGOUS network bug: the
added-`network` branch hard-codes `wideningInbound: false`, so a change from NO network section to a
desired config with non-empty `firewall.allow` hides the widening. GENERAL RULE for round 3 — apply to
EVERY section and EVERY security/diff flag (`wideningInbound`, `weakensRetention`, and any other):
**never hard-code a flag on an added/removed section.** Compute each flag from the present side by
composing that section's change-preview against the absent side represented as the section's safe
conservative baseline — network: an empty deny-all firewall (so ANY inbound allow rule on an added
network ⇒ `wideningInbound: true`); backup: the baseline that makes `weakensRetention` reflect the real
delta. Audit added AND removed for ALL sections; do not leave any flag stubbed. Add regressions: (1)
current WITHOUT `network`, desired WITH non-empty `firewall.allow` ⇒ `wideningInbound: true`; (2) the
symmetric removed cases. Keep fail-closed + never-throw + the round-2 section-level validation invariant.

## Reviewer revision (round 4 — BLOCKING, from P2-020.review.md — DESIGN CORRECTION)
The rounds-2/3 "synthetic absent baseline + run previewXChange" approach is WRONG and is now forbidden by
the **Section handling rules** above (which supersede the earlier "compose against an absent sentinel"
wording). Two concrete defects to eliminate:
1. **Wrong boundary flags**: the fake absent-backup baseline used `retentionDays: 1`, so removing a backup
   whose current retention is already `1` compared `1→1` and reported `weakensRetention: false`. REMOVING
   backup must ALWAYS report `weakensRetention: true`. Compute removed/added flags directly (per the rules),
   never via a fake-baseline diff.
2. **Polluted diffs**: added/removed sections must NOT show synthetic resources (fake `lo`, `/absent/...`
   subvolumes, fake schedule/target). An added section's diff is purely "desired resources added"; a removed
   section's diff is purely "current resources removed".
Also (was a NOTE, now fix it): the hostile-input accessor test is INEFFECTIVE — `previewNodeConfigChange`
catches throws, so an `assert.fail()` inside a getter is swallowed. Use an EXTERNAL counter incremented in
the malicious accessor and assert it stayed 0 AFTER the call (the P2-018 lesson). Add regressions:
removed-backup-at-retention-1 ⇒ `weakensRetention:true`; added/removed sections produce NO synthetic
resources in the section diff. Keep the round-2 section-level validation + fail-closed/never-throw.
