## Objective
Today the verity image has a read-only root + `systemd.volatile=overlay` (a tmpfs overlay) → **nothing persists
across reboot**. Add a **persistent writable data partition** so node state survives. Concretely:
- Add a systemd-repart def `os/x86_64/repart-verity/40-data.conf`: a growable `Type=var` (or
  linux-generic) ext4 partition, label `vita-data`, `SizeMinBytes` small + grow-to-fill, `Format=ext4`,
  `FactoryReset=` off — it is the mutable state partition. (The verity root stays ro; this partition is
  the ONLY writable area.)
- Extend `image-layout.mjs` (`planImageLayout`) so the deterministic plan MODELS this data partition
  (name, type, mountpoint `/var`, fs ext4, growable) alongside the existing ESP + A/B roots — pure/no-I/O
  (spec §8.2), same shape as the existing partitions. This is the single source of truth the executor reads.
- The mount: prefer `systemd.volatile=state` semantics (root ro, `/var` from the data partition) OR a
  discoverable `/var` mount (the data partition's GPT type makes systemd auto-mount it at `/var`). Document
  which, and how `build-and-boot.mjs`'s VITA_VERITY cmdline should change (the orchestrator wires the
  cmdline post-merge; do NOT edit build-and-boot.mjs here — state the exact cmdline change in the contract
  result so the orchestrator applies it).

## User value
The foundation for a usable node: the agent's `StateDirectory=vita-agent` (/var/lib/vita-agent), logs, and the
future PDS all need a writable home that survives reboot. Without this the OS is amnesiac.

## Non-goals

## Reviewer revision (round 1) — BLOCKING (Opus cross-review)
The round-1 approach DOES NOT PERSIST. You used `Type=var` + a discoverable mount, but the Discoverable
Partitions Spec only auto-mounts `/var` when the partition UUID == HMAC-SHA256(machine-id, var-GUID). That UUID
is NOT set (no machine-id seeded; `systemd.firstboot=off`; `systemd-repart` runs at BUILD time only and derives a
generic seed UUID, not the machine-id-keyed one). At boot, gpt-auto-generator computes the expected `/var` UUID
from the running machine-id, finds no match, and SKIPS the partition → with a dm-verity read-only root, `/var`
falls back to the ro root → `StateDirectory=vita-agent`/`/var/lib/vita-agent` writes fail → nothing persists. The
contract's whole objective is unmet. (`systemd.volatile=state` also fails — it makes /var a tmpfs.)

FIX (do NOT rely on the machine-id HMAC):
1. In `40-data.conf`, give the data partition a FIXED identity independent of machine-id: a GPT
   `Label=vita-data` (PartitionLabel) AND an ext4 filesystem label `vita-data` (mkosi/repart `Format=ext4` with a
   label — confirm the repart key, e.g. set the fs label so `/dev/disk/by-label/vita-data` exists).
2. Stage an EXPLICIT systemd `var.mount` unit in an overlay shipped via `--extra-tree` (prefer the EXISTING
   `os/x86_64/smoke-overlay/` so no new build-and-boot wiring is needed): `[Mount] What=/dev/disk/by-label/
   vita-data`, `Where=/var`, `Type=ext4`, `Options=x-systemd.growfs` (grow on first boot). Order it correctly for
   an early `/var` (`Before=local-fs.target`, `DefaultDependencies=no`, `Conflicts=umount.target` as a /var mount
   needs). Enable it so it's active at boot (a `local-fs.target.requires/var.mount` symlink, git mode 120000, OR
   systemd's automatic ordering for unit named `var.mount`).
3. cmdline becomes `ro` (drop `systemd.volatile=overlay`; the explicit var.mount provides the writable /var).
   State the exact build-and-boot VITA_VERITY cmdline change in the result.
4. Model the partition label + the mount in `planImageLayout` deterministically; extend the test to assert the
   `vita-data` label + the var.mount (What/Where/Options).
The orchestrator host-verifies: build VITA_VERITY=1, boot, `touch /var/lib/vita-test`, reboot → file PERSISTS,
root still verity-ro. This MUST work, not just the plan-shape test.
