## Objective
Replace the **placeholder** in the production `CompositorDriver.reconcile` path where every app window is filled with a flat
palette color instead of its real rendered pixels, and carry actual per-window pixel content through the bridge.

Evidence of the placeholder (production-intended, NOT a test harness):
- `sdk/typescript/src/compositor-bridge/index.ts:210-234` — `defaultNativeCompositorSurfaceColor()` returns a solid RGBA per surface; app windows get `WINDOW_COLOR_PALETTE[fnv1a32(id) % len]` (`:226-233`, palette `:353-360`).
- `registerSurface` (`:115-140`) emits `registerSurface <id> <w> <h> <rgba>` via `resolveNativeCompositorColor` (`:1318-1334`).
- `CompositorWindowPlacement` (`:236-244`) has **no** field for actual texture/pixel content — windows are colored rectangles.
- The native sink for real pixels (`registerBufferSurface` / `updateBufferSurface`, fed by the CEF `OnPaint` RGBA) already exists on the Rust side at `osr_host/.../main.rs:325-355` and is what the live CEF path uses, but the TS bridge never reaches it.

Real fix:
- Extend `CompositorWindowPlacement` (and the desired/diff/snapshot path) so a window may carry a **buffer-surface content source** — an RGBA framebuffer (bytes + stride/width/height/format) sourced from the app/CEF `OnPaint` output (or, where supplied, an opaque shared-texture/DMABUF handle).
- For a window WITH content, the driver MUST emit a buffer-surface registration/update command (`registerBufferSurface` / `updateBufferSurface`) carrying that content, NOT a flat `registerSurface <id> ... <rgba>`. The wire encoder (`encodeNativeCompositorCommand`) gains the corresponding command variant.
- The solid-color fill becomes a **clearly-flagged degraded fallback only** — it must be reachable only when a window has no content source (e.g. via an explicit `degraded`/`fallbackReason` flag), and shell chrome (`shell:*`) keeps its existing flat colors.

## User value
Real desktop windows show their actual rendered contents (the live CEF/app pixels) instead of meaningless solid rectangles, making the flagship desktop usable rather than a color-coded mock. This closes the gap between the live CEF GPU path and the SDK reconciler.

## Non-goals
- NO new GPU/DMABUF allocation logic, no CEF integration changes, no Rust changes (`main.rs` sink already exists — the TS bridge must drive it). NO visual redesign. Don't widen the public API beyond what carrying buffer content requires. Keep shell-chrome flat colors as-is.

## Acceptance
`acceptance_command` passes. The new deterministic test `sdk/typescript/test/ui-kits/compositor-buffer-surface.test.ts` MUST assert, against a fake recording `CompositorPort`:
1. **Placeholder is GONE for real windows:** reconciling a `CompositorWindowPlacement` that carries real RGBA buffer content emits a buffer-surface command (`registerBufferSurface`/`updateBufferSurface`) whose payload is the **injected real pixel bytes** — and the test asserts NO flat `registerSurface <id> ... <rgba>` palette command is emitted for that window, and that the bytes equal the injected framebuffer (not any `WINDOW_COLOR_PALETTE` entry).
2. **No hardcoded sample:** changing the injected framebuffer bytes changes the emitted command payload byte-for-byte (proves data flows from the injected source, not a constant).
3. **Honest degraded fallback:** a window with NO content source still produces a flat-color surface ONLY when explicitly flagged degraded (assert the `degraded`/`fallbackReason` flag is set on that path); shell-chrome surfaces (`shell:*`) keep their existing flat colors unchanged.
4. Updating a window's content on a subsequent `reconcile` emits an `updateBufferSurface` (not a re-register) carrying the new bytes.
Typecheck clean; pure/headless; deterministic.
