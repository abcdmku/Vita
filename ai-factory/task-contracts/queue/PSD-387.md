## Objective
Headless, deterministic **view-model** that binds the desktop menu-bar (the menu-bar view-model from PSD-386) to two existing SDK/desktop surfaces: the **command-registry** (`ui_kits/desktop/viewmodels/command-registry.ts`) and the **WM focus state** from `@vita/desktop-sdk` (`focusedWindowId(model)` + `WindowModel`/`WindowState` from `sdk/typescript/src/wm/policy.ts`). Menu contents and per-item enablement must track the active app so the menu-bar reflects the focused window's commands.
- **Active-window context.** Derive a `CommandContext` from the WM state: the focused `WindowId` (via `focusedWindowId`) and its `appId`/title, exposed as context keys (e.g. `focusedWindowId`, `focusedAppId`) so command `when` predicates gate on the active app. Recompute deterministically whenever the bound `WindowModel` changes.
- **Menu contents + enablement.** Build menu sections from the command-registry `snapshot(context)`/`available(context)` so items appear and are enabled exactly per the registry's `when` predicates under the active-window context. Disabled items remain visible-but-disabled (do not silently drop registered commands).
- **Window menu.** Add a "Window" menu listing the open windows (from `model.windows`, ordered deterministically — focused-first by `focusStack`/`order`) with the focused window **marked**. Selecting a Window entry emits a focus **intent** for that `windowId` as a typed `wm.intent` with `{ type: "setFocus", windowId }` (the existing `WindowManagerIntent` shape) — it returns the intent, it does NOT perform effects.
- Put the code under `ui_kits/desktop/viewmodels/menu-bar-binding.ts` and tests under `sdk/typescript/test/ui-kits/menu-bar-binding.test.ts`.
- Import the SDK exactly as `ui_kits/desktop/viewmodels/stage.ts` / `command-registry.ts` do; use ONLY public exports of `@vita/desktop-sdk`. Reuse the PSD-386 menu-bar view-model and the existing `createCommandRegistry` — do NOT re-implement either.

## User value
Makes the menu-bar live: menu contents and enablement follow the active app, and the Window menu lets the user see and switch among open windows by menu — the basis of app/window switching from the shell, the logic the CEF-rendered menu-bar hydrates against.

## Non-goals
- NO DOM/CSS/rendering/CEF. NO platform internals. NO new visual design. Do NOT re-implement the command-registry, the menu-bar view-model (PSD-386), or WM policy — consume them. Do NOT actually mutate WM state or perform focus effects (emit the typed intent only). No global app-switcher UI / keyboard chord handling (that is a separate slice).

## Acceptance
`acceptance_command` passes: deterministic unit tests against fake/seeded SDK ports and a constructed `WindowModel` cover, at minimum —
- focus app A → menu shows A's commands with the correct enabled set (per `when` predicates evaluated against the active-window context); changing focus to app B re-derives the menu deterministically;
- the Window menu lists all open windows in deterministic order with exactly the focused one marked;
- selecting a Window entry returns a typed `wm.intent` whose intent is `{ type: "setFocus", windowId }` for the selected window;
- fail-closed: selecting an unknown/closed windowId or an unavailable command yields no effect (no thrown error; no intent for a non-existent window).
Typecheck clean. Pure, headless, byte-identical output for identical inputs.

## Security/constraints
- Injected ports/state only (no ambient I/O, no clocks); capability-mediated and fail-closed (consistent with `command-registry.ts` which never performs effects — `execute` returns a typed action). Pure/deterministic. No remote imports; lockfile present; no package lifecycle scripts; no FFI/native addons.
