## Objective
W6-S5 (ADR-0011 slice 5 — THE GATE; the FR-011 Phase-4 exit, mirroring the OCI cgroup gate P1-054): prove on a real
boot that a HOSTILE capsule — one that actively tries to violate its network grants — is BLOCKED AT THE KERNEL on EVERY
axis, and the NODE SURVIVES (agentd + the benign capsules keep working). This is the BLOCKING precondition before any
UNTRUSTED capsule may receive network grants: widening RestrictAddressFamilies removed a coarse backstop, so containment
now rests on netns + nft holding — and that MUST be re-verified against an adversary.

Build a HOSTILE test capsule (granted a SPECIFIC egress CIDR + a SPECIFIC ingress port, like the benign one) that then
ATTEMPTS to break out, and confirm each attempt is DENIED by the kernel (not by cooperation):
- **Egress violation:** connect to a NON-granted CIDR/host (e.g. the host's real addr, another capsule's veth, an
  arbitrary public-range addr) → MUST be DROPPED by the egress nft default-deny (P1-060).
- **Ingress violation:** attempt to be reachable on / bind-and-serve a NON-granted port, and from a non-host-veth source
  → MUST NOT be reachable (the input policy DROP from P1-059/060 holds; no DNAT for un-granted ports, P1-061).
- **Isolation violation:** try to see host interfaces / reach the host beyond its own veth /32 / reach a SECOND capsule's
  netns / raw-socket or netlink-escape → MUST be contained by the netns + the empty CapabilityBoundingSet + seccomp
  (the AF widening did NOT grant CAP_NET_RAW/ADMIN to the workload).
- **DoS attempt:** a burst of connections/packets → the per-capsule netns + nft + cgroup contain it; agentd + the node
  do NOT degrade.
agentd CONFIRMS enforcement (independent of the workload's self-report): re-read the nft policy is DROP with only the
granted accepts, the netns has only its veth+lo, the host is not reachable — and the NODE SURVIVES (agentd healthz OK,
the benign capsule's NET-EGRESS/NET-INGRESS/NET-NS markers STILL emit OK after the hostile capsule ran).

## User value
The security guarantee that makes network grants safe for UNTRUSTED apps: a malicious capsule provably gets ONLY its
declared network and nothing else — the kernel (netns + nftables), not good behavior, enforces it, and one hostile
capsule cannot reach the host, other capsules, or un-granted destinations, nor take the node down. The Phase-4 exit.

## Non-goals
NO new enforcement mechanism (this VERIFIES the S2–S4 netns/nft/DNAT enforcement against an adversary — it does not add
new privileged surface). NO public exposure. NO weakening of any S2–S4 control to make the test pass. The hostile
capsule is a TEST artifact (first-party, baked) — not a real untrusted package.

## REVISION 2 (host-verify FAILED — honest FAILSAFE, but the confirmation failed — 2026-06-23)
The adversarial review APPROVED the DESIGN (the marker is genuinely measured + dual-gated — no synthesized enforced=OK;
keep ALL of that). But the boot showed `VITA-CAPSULE-NET-LIMITS: egress=NOT_enforced ingress=NOT_enforced
isolation=NOT_enforced status=FAILSAFE reason=capsule_net_limits_failed` (early, ~4.7s) — the confirmation FAILED on the
real node (the node DID survive: the benign NET-NS/EGRESS/INGRESS chain still PASSED). The reason is GENERIC — I can't
tell which step failed. Fix:
1. **DIAGNOSABILITY (HARD REQ — the recurring lesson):** `capsule_net_limits_failed` MUST carry the SPECIFIC step + errno,
   e.g. `:hostile_launch` / `:egress_setns` / `:nft_read` / `:egress_confirm` / `:ingress_probe` / `:iface_list`. The next
   boot must name exactly which confirmation step failed.
2. **DIAGNOSE + FIX the runtime failure.** The benign capsule's egress+ingress WORK on this same boot (the chain passes at
   ~7s), so the HOSTILE capsule's identical setup should too. Investigate: (a) does `local.hostile-net.capsule` actually
   LAUNCH + get its egress+ingress netns set up on the node (or does its manifest/attacks break setup)? (b) does the
   agentd confirmation (confirmCapsuleNetLimits → setns into the capsule netns → sysdeps.ListNftTable + net.Interfaces())
   error at runtime (the early ~4.7s failure suggests the hostile capsule or the confirm runs before its netns/nft is
   ready — a sequencing/readiness issue, like the S2/S3 netns timing)? Ensure the confirmation runs AFTER the hostile
   capsule's netns+nft are fully established, and reads the RIGHT netns (the same /proc/<pid>/ns/net resolution S2/S3 use).
3. **Fold in the review's minor hardening** (all non-blocking but cheap): assert the `~` DENY-prefix in SystemCallFilter
   (not merely that it CONTAINS @privileged/@raw-io — an allow-list would falsely pass); use a word-boundary CIDR match in
   the only-granted-accept enumeration (not strings.Contains — a superstring like 203.0.113.100 vs grant 203.0.113.10
   could mis-classify) + add a superstring mutation case; consider an agentd-side egress DENIED-destination active probe
   for symmetry with the ingress probe.
Verify: go-in-docker (real-op skip-on-EPERM) + Borg51 boot — NET-LIMITS egress=enforced ingress=enforced
isolation=enforced status=OK (MEASURED) AND node survives (full prior chain still PASSES), or a SPECIFIC-step reason if
any axis still can't be proven.

## REVISION 3 (diagnosability WORKED — pinpointed `:ingress_confirm` — 2026-06-23)
rev2 boot: `VITA-CAPSULE-NET-LIMITS: … status=FAILSAFE reason=capsule_net_limits_failed:ingress_confirm` — the
step+errno diagnosability landed (good; keep it). Node survives. The INGRESS-axis confirmation is the failing step. Most
likely cause: the gate's ingress confirm dials BOTH granted-must-reach AND denied-must-not-reach, but the HOSTILE test
capsule does not SERVE its granted ingress port (it is busy attacking), so the granted-reach probe fails → ingress_confirm
fails even though the DENIAL holds. The gate is conflating benign FUNCTIONALITY (granted-reach, already proven by S4) with
the SECURITY DENIAL (the gate's actual claim). Fix:
1. **Deepen diagnosability ONE more level:** `ingress_confirm:granted_unreachable` vs `:denied_reachable` vs
   `:probe_error` — so the next boot names the exact sub-cause if it still fails.
2. **PRIMARY FIX — make the hostile capsule a realistic SUPERSET of the benign one:** it must SERVE its granted ingress
   port (a real listener) AND attempt all the violations. Then the gate proves the strongest statement: a capsule that
   works normally AND attacks still gets its grants enforced and every attack denied — ingress_confirm's granted-reach
   succeeds, the denied-port/isolation/egress violations are all blocked. (Alternative if a hostile capsule genuinely
   cannot serve: gate the ingress AXIS on the DENIAL only — non-granted port unreachable + isolation — since granted-reach
   is benign functionality S4 already proved; but prefer the superset capsule.)
3. Keep the measured+dual-gated design (review-approved) + the egress/isolation confirms (which were not the failing step)
   + the review's minor hardening (~ deny-prefix assertion, word-boundary CIDR match).
Verify: go-in-docker + Borg51 boot — NET-LIMITS all-enforced + node survives, or the deeper specific reason.
