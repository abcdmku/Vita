## Objective
Remove the placeholder-grade guard on the `readSetting` host-bridge forward and replace it with a
**real, key-aware structural guard** that validates the value the backend returns against the
declared setting shape.

Evidence: `ui_kits/desktop/runtime/host-bridge.ts:254-259` wires `readSetting` through
`forwardHostResult(..., "readSetting", [readRequest], isJson)`, and `isJson`
(`ui_kits/desktop/runtime/host-bridge.ts:1245-1247`) is literally `value !== undefined`. Unlike every
other forwarded port (`requestFile`, `previewSetting`, `applySetting`, … all use a precise structural
guard), `readSetting` accepts whatever the backend returns. The request already carries the setting
key (`DesktopSettingsReadRequest { readonly key: string }`,
`sdk/typescript/src/desktop-sdk/ui-package.ts:98-100`), and the settings store enforces a per-key
schema via `normalizeSettingValue(key, value, path)` keyed on `DesktopSettingKey`
(`sdk/typescript/src/desktop-settings-store.ts:615-663`, switch over `DESKTOP_SETTING_KEYS`). So the
correct value can and must be constrained to the declared setting shape rather than "any defined
JSON".

Concretely:
- Replace the `isJson` argument at `host-bridge.ts:254-259` with a guard that, given the
  `readRequest.key`, accepts the forwarded value **only if it matches that key's declared value
  schema** (the same per-key constraints the store's `normalizeSettingValue` enforces — e.g. theme is
  one of the supported theme enum strings, `reduceMotion` is a boolean, `cursorSize` is an in-range
  number, the input-accessibility policy has only its supported fields, etc.), and **rejects** (honest
  error via the bridge's existing reject path) when the key is unknown or the value does not match.
- Do NOT widen or weaken any other guard. Keep `isJson` only if still used elsewhere; if `readSetting`
  was its sole caller, remove the now-dead placeholder so it can't be mistaken for a real guard.
- Reuse the existing `DESKTOP_SETTING_KEYS` / per-key validation surface from the settings store
  (import the public validator or mirror the exact constraints) rather than hand-rolling a looser
  approximation. Pure/deterministic, no I/O, injected transport only.

## User value
A desktop UI reading a setting now receives a value the host-bridge has actually validated against the
setting's declared shape — a malformed or wrong-typed backend response is caught at the bridge with an
honest error instead of being passed through as "any defined JSON". Closes the lone placeholder guard
so the `readSetting` forward matches the precision of every sibling port.

## Non-goals
- NO DOM/CSS/rendering/CEF. NO change to the transport, the router, or the settings store's own logic.
- Do NOT relax or alter the guards for `requestFile`, `previewSetting`, `applySetting`, or any other
  forward. Do NOT broaden what counts as a valid setting value beyond what the store already enforces.
- Do NOT re-implement the settings store; consume/mirror its per-key constraints exactly.

## Acceptance
`acceptance_command` passes. The new deterministic test
`sdk/typescript/test/ui-kits/host-bridge-read-setting.test.ts` drives the host-bridge with a fake
transport and asserts, with NO wildcard glob (exact path), all of:
- **Placeholder is gone / real validation present:** for a representative valid key (e.g. the
  appearance `theme`), a backend returning a value that is defined JSON but NOT a member of the
  declared shape (e.g. `theme: "not-a-real-theme"`, or a number where a boolean is required for
  `reduceMotion`) is **rejected** by `readSetting` — proving the old `isJson` (`value !== undefined`)
  behavior no longer applies (under `isJson` this case would have passed through).
- **Real values flow through:** for the same key, a backend value that DOES match the declared shape
  (e.g. a supported theme enum string) is returned unchanged.
- **Unknown key:** a `readRequest.key` that is not a `DesktopSettingKey` is rejected honestly (no
  silent pass-through, no hardcoded sample value).
- The value returned on success is exactly what the (valid) backend supplied — no hardcoded/sample
  substitution.
- `npm run typecheck` is clean.
