## Objective
A **pure/offline** catalog-publish helper that assembles and signs a catalog manifest from
already-validated inputs, producing a `SignedCatalogManifest` that the existing
`verifyCatalog` (`packages/catalog/src/catalog-manifest.ts:110`) accepts.

- Add `packages/catalog/src/catalog-publish.ts` exporting a `publishCatalog(...)` (pure, no I/O)
  that takes: a set of validated `CatalogEntry` inputs (each first run through
  `validateCatalogEntry` — `packages/catalog/src/catalog-entry.ts:106` — for
  publisher/SBOM/vuln/trustTier/EOS/digest), the per-app `CatalogAppVersion` data, and the
  manifest header fields (`schemaVersion`, `catalogVersion`, `generatedAt`).
- It assembles the canonical `CatalogPayload` (`apps` sorted by `id`; each app's `versions`
  preserving caller order; `grantsSummary` sorted-unique as `verifyCatalog` requires —
  `catalog-manifest.ts:474`), then signs the canonical bytes via a **caller-supplied signer
  interface** (e.g. `interface CatalogSigner { readonly keyId: string; sign(bytes: Uint8Array): Uint8Array }`),
  returning `{ catalog, signature: { algorithm: "ed25519", keyId, value: <base64> } }`.
- Canonical bytes come from `canonicalizeCatalogBytes` (`packages/catalog/src/catalog-canonical.ts:18`)
  so they are byte-identical regardless of input object key order.
- Any entry that fails `validateCatalogEntry` must be **rejected** (return an
  errors result, mirroring the `{ ok: false, errors }` shape already used by
  `validateCatalogEntry` / `verifyCatalog`) — never silently dropped, never signed.
- Tests at `packages/catalog/test/catalog-publish.test.ts` use an **ephemeral dev signer** that
  wraps `node:crypto` ed25519, mirroring `packages/catalog/test/fixtures/catalog-test-signing.ts`
  (`signCatalog` + `TEST_CATALOG_*`). Reuse that fixture's key material; do NOT introduce a new key.

## User value
Closes the catalog supply-chain loop (spec §4 app catalog): publishers can deterministically
assemble + sign a catalog that the on-device verifier already trusts, with a clean seam for the
owner-held production key.

## Non-goals
- NO file/network/clock I/O — `generatedAt` is a caller input, signing is via the injected signer.
  NO embedding or reading of any private key inside the tool.
- Do NOT re-implement validation or canonicalization or verification — consume
  `validateCatalogEntry`, `canonicalizeCatalogBytes`, and round-trip against `verifyCatalog`.
- NO new key material, no changes to `catalog-manifest.ts` / `catalog-entry.ts` / `catalog-canonical.ts`
  public behavior.

## Acceptance
`acceptance_command` passes. `packages/catalog/test/catalog-publish.test.ts` (run with
`node --experimental-strip-types --test`, the established catalog-test pattern) deterministically
covers, with the ephemeral dev signer:
- An assembled + dev-signed catalog **round-trips** through `verifyCatalog(signed, TEST_CATALOG_TRUSTED_KEYS)`
  with `ok === true` and the apps/versions intact.
- An input entry that fails `validateCatalogEntry` (e.g. embedded key material in a ref, bad
  trustTier, missing SBOM) causes `publishCatalog` to return `ok: false` with errors and produces
  no signed manifest.
- The canonical payload bytes are **byte-identical** when the same logical input is supplied with
  reordered object keys (assert equality of `canonicalizeCatalogBytes` over both).
- No production/release key is referenced anywhere in src or test (only the TEST fixture key).
- `npm run typecheck` is clean.

## Security/constraints
- §16 key custody: the **real catalog signing key is owner-held**; this tool is propose-only —
  it emits the canonical signing-input bytes and accepts an injected signer, and only round-trips
  against the dev key in tests. It MUST NOT embed, read, or require a production private key.
- Pure/deterministic, fail-closed on invalid entries; no ambient I/O. No remote imports; lockfile
  mandatory; no package lifecycle scripts; no FFI/native addons.
