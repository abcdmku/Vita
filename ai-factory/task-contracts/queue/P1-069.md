## Objective
Phase-2 Identity (spec §10 "Local owner identity and passkey enrollment"; spec §11 "passkeys as the primary user
authentication method") — a THIN first slice: a LOCAL OWNER IDENTITY whose authenticator is a passkey (WebAuthn
public-key credential), with (a) enrollment of the owner's PUBLIC-key credential on the device and (b) verification of
an owner ASSERTION that authorizes a privileged control action. The private key NEVER touches the device — it lives on
the owner's authenticator; agentd stores ONLY the public credential and verifies signatures. Builds on the first-boot
ownership claim (the identity.attestation cap, P1-024/the rootfs agentd P1-026).

Add a NEW narrow Go capability `owner.identity` under `agent/capabilities/owner/` (modeled on
`agent/capabilities/identity/identity.go` — the same atomic-write store, jsonsafe strict decode, fail-closed validator,
single-commit-point undo, inline-secret rejection), registered in `agent/cmd/agentd/main.go` alongside the other caps.
It exposes exactly three typed operations (a CLOSED set; unknown requests rejected, fail-closed):

1. **Enroll** (`ApplyRequest{Desired: OwnerCredential}`) — persist ONE owner public-key credential:
   `{ credentialId, publicKeyCose, signCount, aaguid?, transports?, rpId, userHandle }`. `publicKeyCose` is the
   COSE_Key PUBLIC key (EC2 P-256 / ES256 OR OKP Ed25519 / EdDSA — the two WebAuthn-mandatory algs the Go stdlib
   covers: `crypto/ecdsa`+`crypto/elliptic.P256()` and `crypto/ed25519`; the COSE_Key public-key map is parsed with a
   minimal hand-rolled CBOR reader — NO new vendored dep). VALIDATE: a real parseable COSE public key of
   a supported alg; `credentialId`/`userHandle` are base64url, bounded; `rpId` a domain-style host (reuse the
   `isDomainHandle` discipline); REJECT any inline PRIVATE-key / secret material (reuse the identity.go
   `containsInlineSecretMaterial` scanner — agentd must NEVER accept or store a private key, §16); reject duplicate
   JSON keys + unknown fields + accessor/exotic shapes. Enrollment is idempotent-replace under undo (single commit point
   = the atomic rename; prior credential restored on Undo). Persist + return the RE-SERIALIZED canonical validated
   struct, never raw input bytes.
2. **Read** (`ReadRequest`) — return `{ exists, credential (public only, NO private material), enrolled: bool }`.
3. **VerifyAssertion** (`VerifyRequest{ Assertion: OwnerAssertion }`) — given an enrolled owner credential, verify a
   WebAuthn-style assertion authorizes a privileged action. `OwnerAssertion = { credentialId, authenticatorData,
   clientDataJSON, signature, action }`. Verify, FAIL-CLOSED, in `webauthn.go`:
   - `credentialId` matches the enrolled credential (else deny — unknown credential);
   - `clientDataJSON` parses to `{ type: "webauthn.get", challenge, origin }`; the `challenge` equals an
     agentd-issued, single-use, unexpired challenge (a `Challenge`/`Consume` pair in owner.go — challenge minted by
     agentd, bound to the requested `action`, consumed on verify so it cannot replay); `type` MUST be `webauthn.get`;
     `origin`/`rpIdHash` (sha256 of `rpId`, the first 32 bytes of `authenticatorData`) MUST match the enrolled `rpId`
     (else deny);
   - the User-Present (UP) flag in `authenticatorData` flags byte MUST be set (physical confirmation, spec §11 "device
     pairing with physical confirmation"); UV honored if present;
   - the signature over `authenticatorData || sha256(clientDataJSON)` verifies against the enrolled COSE public key for
     its alg (ES256: ASN.1-DER ECDSA over the P-256 curve; EdDSA: ed25519.Verify) — else deny;
   - `signCount` monotonic non-regression: if the asserted counter is ≤ the stored counter AND both are non-zero,
     DENY (cloned-authenticator signal); on success advance the stored counter (a small state update under the same
     atomic-write discipline). A zero stored+asserted counter is allowed (authenticators that don't count).
   On success return `{ verified: true, action }`; on ANY failure return a typed deny with a SANITIZED reason (never
   echo key bytes / the challenge) and verified:false. NEVER throw at the trust boundary.

NO real owner secret is committed. Build a TEST owner credential + a matching TEST assertion fixture under
`agent/capabilities/owner/testdata/` generated AT TEST TIME from a freshly-generated TEST key (the test mints the key,
derives the COSE public key, signs a valid assertion over a minted challenge) — so the repo holds NO key material; the
private key exists only in-memory during the test run.

ON-DEVICE (main.ts, the control-plane pattern — agentd composes/acts ONLY from the re-validated typed request over the
AF_UNIX socket; the TS runtime is UNPRIVILEGED and only transports): wire an enrollment of a baked TEST owner credential
(`os/x86_64/ts-overlay/usr/lib/vita/owner/owner-credential.json` — PUBLIC credential only) + a privileged-action
authorization round-trip (mint challenge → present a baked TEST assertion → agentd verifies) + a fail-closed reject
(a tampered/replayed/wrong-credential assertion is DENIED and the privileged action does NOT proceed). The baked
assertion fixture is signed by the SAME test key at IMAGE-BUILD time (a build step that mints the key in-memory, emits
the public credential + a signed assertion, and DISCARDS the private key — never staged, never committed).

MEASURED marker (never synthesized — gate on the REAL agentd verify result, the P1-055 lesson):
`VITA-OWNER: enrolled=OK assertion=verified action=<action> status=OK` emitted ONLY when agentd reports the enrolled
credential present AND the presented assertion verified AND the gated privileged action was thereby authorized.
`VITA-OWNER-REJECT: reason=<sanitized> status=OK` when a forced-invalid assertion (wrong credential / replayed
challenge / bad signature / UP-flag clear / rpId mismatch / counter regression) is DENIED and the action is BLOCKED
(fail-closed). `VITA-OWNER-ERROR: status=FAILSAFE` on setup error (treated as denied — privileged action NOT taken).
Keep ALL prior markers.

## User value
The node has a LOCAL owner whose authority is a passkey it holds — no vendor account, no shared/factory password (spec
§11). Privileged control actions can be gated on a fresh, physically-confirmed owner assertion, so a compromised
unprivileged TS runtime (or a stolen socket handle) cannot authorize an owner-only action without the owner's
authenticator. This is FR-016's "manage local identities, passkeys" foundation and the authorization primitive later
privileged caps build on.

credential, we do NOT verify a packed/tpm/android-key attestation chain — deferred). NO multiple owner credentials /
credential rotation UI (single credential, replace-on-enroll). NO browser/controller UI, NO OIDC federation. NO change
to the transport peer-auth (uid/group gate in `agent/transport/server.go` stays — this is an ORTHOGONAL application-level
owner-assertion check, NOT a replacement). NO real key material in the repo or image. NO RS256/RSA (ES256 + EdDSA only,
stdlib-covered).

## Performance & security constraints
The TS runtime is UNPRIVILEGED; the privileged owner-assertion check lives ONLY in the narrow Go agentd, composing/
acting ONLY from the re-validated typed request (never raw runtime text). FAIL-CLOSED on EVERY invalid/partial/missing
input — no valid owner assertion ⇒ privileged action DENIED. NO private key material EVER accepted, stored, returned,
or committed (signing/recovery/TPM keys are OWNER-HELD, §16; agentd holds only the PUBLIC credential). Challenges are
single-use, expiring, action-bound (replay-resistant); signCount monotonic (clone-resistant); UP-flag required
(physical-presence, §11). Validators are fail-closed and NEVER throw at the trust boundary (cyclic/deeply-nested/
malformed → rejection). Reuse the identity.go inline-secret scanner (the strong `containsInlineSecretMaterial`, not a
weaker copy) + strict jsonsafe decode + the O_EXCL-temp→fsync→rename atomic-write single-commit-point + duplicate-key
rejection + canonical re-serialization. No remote imports; stdlib crypto only (no new vendored dep); offline; lockfiles
mandatory; no package lifecycle scripts. R3 (identity/authorization, a TCB authz primitive) → reviewer gate +
parallel-candidate (two independent worker attempts, judged by rubric).

   test authenticator (the test private key stays in a build-time fixture / never shipped or used by the runtime).
   agentd VERIFIES the pre-signed assertion against the baked public credential; the VITA-OWNER marker is gated on
   agentd's REAL verification of {baked public credential + pre-signed assertion}, NOT on a runtime that self-enrolls and
   self-signs. The boot path MUST actually use `owner-credential.json` (currently it doesn't — part of this blocker).
2. **commit-point regression doesn't test the third-state.** `memoryFileSystem.AtomicWrite`'s

   it proves ordinary rollback, not the mandated "effect happened but Apply reported failure" third-state. FIX: that
   branch must RETURN `errSimulatedWrite` (after the mutation) so the genuine effect-happened-but-failed rollback is

## REVISION 3 (re-review REVISE: replayable fixture challenge — 2026-06-23)
rev2 removed the runtime private key (good) but introduced a REPLAY HOLE: `owner.go Challenge()` sources the challenge
from the FIXTURE `/usr/lib/vita/owner/owner-assertion.json` (the same fixture holding the pre-signed assertion), so any
caller reaching agentd can re-mint that fixed challenge and replay the baked assertion with NO authenticator. That breaks
the single-use, replay-resistant, agentd-ISSUED challenge requirement. (The boot's "challenge_replayed" reject only
catches reusing an already-consumed challenge, not re-minting the fixture one.) Resolve the tension cleanly:
1. **agentd issues a RANDOM, single-use, server-side challenge** per verify request (a fresh nonce, stored once, CONSUMED
   on use). NEVER sourced from a fixture/committed file. A reused or caller-supplied challenge is REJECTED.
2. **A TEST AUTHENTICATOR signs agentd's issued challenge — OFF the unprivileged TS runtime.** Implement the owner
   authenticator as a small SEPARATE signer (a Go test-signer helper / privileged test unit) that holds the TEST private
   key (a build fixture) and signs the random challenge agentd just issued; agentd verifies that signature against the
   baked PUBLIC credential. The TS runtime only RELAYS the {challenge→assertion} round-trip; it NEVER holds the private
   key. (This mirrors the real WebAuthn flow: agentd challenges, an external authenticator signs, agentd verifies.) If a
   full on-device authenticator round-trip is impractical in the smoke boot, scope the ON-DEVICE marker to prove
   {agentd issues a random single-use challenge} + {replay/forged/fixture assertion REJECTED} (the security-critical,
   fail-closed half), and prove the assertion=verified SUCCESS in a Go UNIT test where a test-signer (allowed to hold a
   test key — it is NOT the unprivileged runtime) signs agentd's random challenge.
3. **Fix `--check` nondeterminism:** `os/x86_64/ts-image.mjs` regenerating RANDOM owner fixtures during `--check` mutates
   tracked overlay inputs. The test key + public credential must be FIXED build fixtures (committed public credential;
   the test private key in a build-only fixture), not regenerated each run — `--check` must leave the tree clean.
Keep: no runtime private key, fail-closed, agentd-side verify (challenge/signature/origin/no-replay), measured marker.
Verify: Borg51 boot — `VITA-OWNER: enrolled=OK assertion=verified status=OK` over an agentd-issued RANDOM challenge +
`VITA-OWNER-REJECT` for replay/forged; `--check` clean.
