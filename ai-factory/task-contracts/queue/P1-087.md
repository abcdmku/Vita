## Objective
Phase 5 (spec §21 "User and household roles"; spec §11 "Owner, administrator, member, restricted member, guest, and
service roles"), roles arc slice 2: promote the TWO-role binding shipped by P1-073 (`owner` + `household-member`) to
the **FULL six-role household model** from spec §11 —
`owner`, `administrator`, `member`, `restricted-member`, `guest`, `service` — bound to AUTHENTICATED peer identities,
and have the narrow privileged Go agent (`agentd`) ENFORCE per-capability role grants with a LEAST-PRIVILEGE default.
This is purely an identity/authorization-model widening on top of P1-073's role-scoped files capability: the data
substrate (P1-065 files + P1-073 shared folders) is unchanged; what changes is (a) the closed SET of roles agentd
knows, (b) the principal→role binding keyed off the per-connection authenticated unix-peer identity (SO_PEERCRED,
P1-048 / P1-073), and (c) the per-capability role→access policy the files grant carries. The unprivileged TypeScript
runtime STILL cannot name, assert, or widen its own role — agentd reads the binding from its OWN validated config and
selects the effective access; fail-CLOSED throughout.

Concretely, building strictly on the P1-073 surface (`agent/capabilities/files/shared.go` `Role`/`Principal`/
`EffectiveAccess`/`household-member`-default, `files.go` `Options.Principals` + the `role_forbidden` write gate,
`agent/transport/server.go` per-connection peer→role resolution, `agent/cmd/agentd/main.go` principal/grant wiring,
`sdk/typescript/src/files-grant.ts` the `FilesRole` union):

- **The closed six-role set lives in one canonical place (`agent/identity/roles/roles.go`).** Lift the role type out
  of the files package into a small dedicated `identity/roles` package so roles are a first-class identity concept (not
  a files-only enum) that later capabilities reuse — the files package then IMPORTS `roles.Role`. Define the CLOSED,
  ordered set exactly as spec §11 (no more, no fewer):
  `RoleOwner="owner"`, `RoleAdministrator="administrator"`, `RoleMember="member"`,
  `RoleRestrictedMember="restricted-member"`, `RoleGuest="guest"`, `RoleService="service"`, plus
  `AllRoles() []Role` (length 6, deterministic order) and `Valid(r Role) bool`. P1-073's `household-member` becomes
  `member` (rename, single source); keep a documented note that `member` IS the prior `household-member` so the spec
  §11 vocabulary is authoritative. Add a strict `ParseRole(string) (Role, bool)` that returns `ok=false` for any
  string outside the six (no aliasing, no case-folding, no "" → default at parse time). The DEFAULT role for a
  principal with NO configured binding is the LEAST-PRIVILEGED role — **`guest`** (a stranger, not a household member),
  not `owner`, never owner-by-absence; expose it as `roles.DefaultRole = RoleGuest` with a comment tying it to
  least-privilege. (P1-073 defaulted to `household-member`; the six-role model makes the unconfigured-stranger default
  the strictly-lower `guest` — document this deliberate tightening in the package doc and the contract's Non-goals.)
  A role-ordering/privilege helper is NOT required (access is per-grant, see below) and MUST NOT be used to silently
  grant a higher role's access to a lower one — there is no implicit role hierarchy; every access is explicit per grant.

- **Per-capability role→access grants carry an entry for the SIX roles (`shared.go`, extended, re-validated).** Today
  P1-073's shared grant is `{ name, root, shared?: true, roles?: { owner, "household-member" } }`. Extend the `roles`
  map key space to the six `roles.Role` values: `roles?: { owner?, administrator?, member?, "restricted-member"?,
  guest?, service? }` where each present value is `"read-only" | "read-write"`. A role key that is ABSENT from a
  shared grant's `roles` map means that role has NO access to that grant (→ fail-closed `role_forbidden` for every op
  — this is the least-privilege default, NOT fall-open). Decode STRICTLY via the existing `jsonsafe.DecodeStrict`:
  reject a grant that sets BOTH a flat `access` and `roles`, a `shared` grant with an EMPTY `roles` map, an UNKNOWN
  role key (anything outside the six), a role value that is not one of the two access modes, or duplicate JSON keys —
  fail-closed at `NewHandler`/grant-resolve time (a misconfigured grant must NOT silently fall open). A flat
  (no-`shared`) grant still behaves EXACTLY as P1-065 (the prior boot chain must be byte-for-byte unaffected; absent ≠
  empty). The shared TS types live in `sdk/typescript/src/files-grant.ts` (the single shared source) re-exporting the
  six-value `FilesRole` union from the new `sdk/typescript/src/roles.ts`.

- **Principal → role binding from the AUTHENTICATED per-connection peer (the security core — no new auth path).** The
  files `Options.Principals` and the transport `Config` principals binding (both introduced by P1-073) now bind a peer
  key to one of the SIX `roles.Role` values. The principal key is derived ONLY from agentd-side, per-connection
  authenticated unix-peer identity already proven by `ListenAuthenticatedUnixSocket` / `UnixPeerAuthConfig` /
  SO_PEERCRED (P1-048: `server.go` `Accept`/`readPeerInfo`/`peerAuthorizedForGroup`, `peercred_linux.go`
  `GetsockoptUcred` PID/UID/GID + SO_PEERGROUPS) — REUSE the existing single auth path; do NOT invent a second one and
  do NOT bind off listener-global config (the P1-073 REVISION-2 defect: the role MUST come from THIS connection's peer,
  per-`Accept`, not a once-computed listener principal). The request envelope gains NO `role`/`principal`/`as` field;
  if present it is rejected by the strict decoder (unknown key). A request whose resolved peer has NO configured role
  gets `roles.DefaultRole` (`guest`) — never a household role by absence, never `owner`. The runtime CANNOT assert a
  role: agentd reads the binding from its own validated config keyed off the kernel-provided peer identity, never from
  request text.

- **Per-capability enforcement, least-privilege default (`files.go` write/read gate, reused + widened).** The write
  gate stays exactly P1-073: resolve the request principal's role → `EffectiveAccess(grant, role)`; allow `write` only
  if effective access is `read-write`; allow `list`/`read`/`stat` for any role with ANY (RO or RW) effective access;
  a role with NO entry on a shared grant → `role_forbidden` for EVERY op. With the six-role set, this means: a `guest`
  or `restricted-member` or `service` principal whose role has no `roles` entry on a grant is denied every op
  (`role_forbidden`); a role mapped to `read-only` can read but a `write` is `role_forbidden`. The existing flat-RO
  `runtime-files-ro` grant still rejects `write` with `read_only_grant` (NOT `role_forbidden`) — the P1-065/P1-073
  reject vocabulary is unchanged. Path resolution stays verbatim: `ResolveWithinScope` (traversal-/symlink-safe) and
  the atomic temp+rename write are reused — this slice adds NO new FS primitive and NO new traversal logic. A no-op /
  always-`read-write` / always-allow resolver MUST fail the suite.

- **agentd cannot let the runtime self-assign (encode the invariant).** There is no RPC, config field, or request path
  by which the unprivileged runtime can set, request, escalate, or learn-then-impersonate its own role. agentd's role
  source is exclusively `Config.Principals` (validated at startup) indexed by the authenticated peer identity. Prove in
  tests that a body-supplied `role`/`principal`/`as` is rejected (strict decode) and that two DIFFERENT authenticated
  peers bound to two different roles get two different effective accesses on the SAME grant (the role tracks the peer,
  not the request).

- **Unprivileged on-device wiring + MEASURED marker.** In `main.go`, configure the principal→role bindings and the
  shared-folder grants so the six-role model is PROVEN end-to-end on a single-user smoke boot WITHOUT standing up six
  OS users: bind the runtime's OWN authenticated peer to a privileged role (e.g. `member` or `owner`) for a grant where
  it can write, AND configure at least one grant whose `roles` map FORBIDS a lower role (e.g. `guest`/`restricted-member`
  has NO entry, or is `read-only` where a write is attempted) so a genuine `role_forbidden` denial fires. Because a
  single boot has one runtime peer, the boot proves: (1) the runtime's bound role yields a real write→list→read-back
  (bytes match)→stat round-trip via agentd (the privileged-role success), and (2) an op that the role model FORBIDS
  (the runtime requesting an op on a grant where its effective access is none / read-only-on-write) is REJECTED
  `role_forbidden` — a real measured denial, NEVER synthesized. The full six-role SET being known + enforced is proven
  by the Go suite (all six parse, the closed set rejects a 7th, each role's grant access is enforced); the boot marker
  attests the count + that enforcement is live. Add the thin client surface in `files-client.ts` ONLY if the op set
  changes — it does NOT. Emit in `main.ts`:
  `VITA-ROLES: roles=6 enforced=OK role=<bound-role> grant=<rw-grant> op=write+read+list+stat bytes=<n> roundtrip=OK status=OK`
  (gated on the real write→read-back byte match AND on the role set the agentd build exposes being exactly the six,
  NEVER synthesized) and
  `VITA-ROLES-REJECT: reason=role_forbidden status=OK` (a forbidden-role op is denied);
  `VITA-ROLES-ERROR: status=FAILSAFE` on any inconsistency. Keep ALL prior markers, including the unchanged P1-073
  `VITA-FILES-SHARED:` / `VITA-FILES-SHARED-REJECT:` and the P1-065 `VITA-FILES:` roundtrip + its two
  `VITA-FILES-REJECT:` (path_traversal, read_only_grant).

## User value
The node becomes a real multi-person household product (spec §11): the same node serves an owner, administrators,
ordinary members, restricted members, guests, and machine/service principals — each at a role-appropriate, explicitly
granted access level, enforced by the privileged agent and bound to the kernel-authenticated identity of the
connecting peer. Crucially, authorization is LEAST-PRIVILEGE by default (an unbound stranger is a `guest` with no
household access, never an owner) and the unprivileged runtime can never assert or widen its own role — agentd alone
binds principal→role from its validated config and selects the effective access, fail-closed. This delivers the spec
§21 Phase 5 "User and household roles" deliverable (FR-016 roles/grants) on top of the P1-065/P1-073 files substrate,
and is the role vocabulary every later per-application data/network capability authorizes against.

## Non-goals
NO new roles beyond the spec §11 six (the set is CLOSED — a 7th value is a reject, not an extension point this slice).
NO role HIERARCHY / inheritance / privilege-ordering (access is explicit per grant; `administrator` does NOT implicitly
inherit `member`'s grants — each grant lists the roles it admits). NO role-MANAGEMENT RPC or runtime-mutable roles
(roles are agentd validated config this slice, not a runtime API; that is a later controller/identity slice). NO
passkey/OIDC/device-pairing binding of HUMANS to roles (spec §11 auth is a separate identity slice — this slice binds
the already-authenticated UNIX peer identity to a role, the on-device authorization layer). NO multi-OS-user
provisioning, NO per-user uid/gid ownership split of the data tree (single agentd-owned tree, access decided in
agentd — unchanged from P1-073). NO new file ops, NO directory create/delete/rename/move (still list/read/write/stat,
same op set). NO quotas/encryption, NO controller UI, NO audit-log schema change. NO change to `ResolveWithinScope`,
the atomic-write primitive, the size cap, the SO_PEERCRED auth path, or any P1-065/P1-073 marker. DELIBERATE change
vs P1-073: the unconfigured-principal default tightens from `household-member` to the strictly-lower `guest`
(least-privilege for a stranger) and `household-member` is renamed to the spec-§11 `member` (single source). The
runtime never receives a raw FS path, never an `--allow-read`/`--allow-write` for the data root, and never a way to
name its own role; agentd composes/acts ONLY from the re-validated request + its own validated grants + its own
principal→role binding keyed off the authenticated peer, never from raw runtime text used as a path OR a role.

## Performance & security constraints
- **Unprivileged runtime, agentd-asserted role, authenticated-peer binding (spec §3.4, §7.1, §11):** the runtime gets
  NO raw FS access and NO way to name/request/escalate its own role/principal. agentd binds principal→role from its OWN
  validated config keyed off the per-connection authenticated SO_PEERCRED unix-peer identity (P1-048; the SINGLE auth
  path — no second one), per-`Accept` (never a listener-global principal — the P1-073 REVISION-2 fix), and selects the
  effective access; it acts ONLY from the re-validated request + its own grants + its own binding, NEVER from raw
  runtime text used as a path OR a role.
- **Fail-CLOSED, default-least-privilege:** the role set is a CLOSED six (a 7th value is rejected, not extended);
  misconfigured grant (both flat+roles / empty roles / unknown role key / bad role value / dup keys) rejected at
  startup; a role with NO grant entry → `role_forbidden` for every op; an unbound principal defaults to `guest`
  (strictly least privilege), NEVER owner/member/owner-by-absence. There is NO implicit role hierarchy — no lower role
  silently inherits a higher role's access. A guard over untrusted input MUST NOT throw at the trust boundary (a throw
  is a DoS — return a rejection); prove with a malformed/cyclic regression.
- **No regression of the P1-065/P1-073 floor:** `ResolveWithinScope` (traversal-/symlink-safe), the atomic
  `os.CreateTemp(dir, ".name-*.tmp")` → Sync → Close → Rename single-commit write (mode 0600, no predictable temp), the
  ≤ 8 MiB size cap, strict dup-key-rejecting decode, the `read_only_grant` reject for flat RO grants, and ALL prior
  markers are reused/behave VERBATIM — this slice adds only the six-role vocabulary, the `identity/roles` package, and
  the widened `roles` grant key space.
- **No keys/secrets** — TEST principals/grants only; never commit or generate production key material; signing / TPM /
  recovery / mesh keys remain OWNER-HELD (§16) and are not touched here.
- **No remote imports** in the TS types/client; lockfiles mandatory; no package lifecycle scripts; no FFI/native
  addons. R2 → reviewer gate (`npm run review -- P1-087` must report `VERDICT: approve` before merge, per the standing
  R2/R3/R4 gate).
