## Objective
Implement the **host-side shell backend** that satisfies the `SurfaceShellHostPorts` seam
(`ui_kits/desktop/runtime/host-bridge.ts:81-84`: `registerComponent | previewShell | applyShell |
rollbackShell | currentShell`). Today `ui_kits/desktop/package.ts` mounts these via the bridge
(`package.ts:191,227,231,329`) but **no backend implements them transactionally** — they only
fail-closed through the router (PSD-341) because nothing answers the requests. Back them with the
real **shell config engine** already in the SDK (`sdk/typescript/src/shell/index.ts`) — specifically
the `ManagedShellConfigController` (`shell/index.ts:738`) — so the desktop shell can register its
components and compose the live layout transactionally with rollback + known-good fallback +
FAILSAFE.

- Module: `sdk/typescript/src/desktop-sdk/shell-backend.ts` (a public SDK export — add the
  re-export line to `sdk/typescript/src/desktop-sdk/index.ts`). Test:
  `sdk/typescript/test/ui-kits/shell-backend.test.ts`.
- Expose a `createShellBackend(options?)` factory returning an object whose member functions mirror
  the `SurfaceShellHostPorts` grouping EXACTLY (reuse that exported type from `host-bridge.ts` — do
  NOT redefine it):
  - `registerComponent(definition) -> ShellResult<RegisteredShellComponent>` — registers a shell
    component into a single `ShellComponentRegistry`; a second registration of the same `id` returns
    the engine's `DUPLICATE_COMPONENT` rejection (`shell/index.ts:422-428`), it does not throw.
  - `previewShell(definition) -> ShellPreviewResult` — delegates to the controller's `preview()`
    (`shell/index.ts:757`); MUST be **side-effect-free** (it does not mutate the committed snapshot:
    `currentShell()` returns the same `revision`/`configId` before and after a preview).
  - `applyShell(definition) -> ShellApplyResult` — delegates to `apply()` (`shell/index.ts:778`);
    on success returns `outcome: "committed"` with the composed layout; on plan/compose failure it
    fails closed (`outcome: "fallback"`, or `outcome: "failsafe"` + `status: "FAILSAFE"` for a
    failsafe-class error) and the committed snapshot is left intact.
  - `rollbackShell() -> ShellRollbackResult` — delegates to `rollback()` (`shell/index.ts:834`):
    restores the prior committed layout (`outcome: "rolledBack"`), or `outcome: "fallback"` when
    there is no prior layout.
  - `currentShell() -> ShellManagedSnapshot` — returns the controller's `current()`
    (`shell/index.ts:753`): `{ source: "configured" | "fallback", layout, error? }`.
- Use ONLY public exports from `@vita/desktop-sdk` (the shell engine surface — `ManagedShellConfigController`,
  `ShellComponentRegistry`/`createShellComponentRegistry`, `composeKnownGoodFallbackShell`, and the
  `Shell*Result`/`ShellManagedSnapshot`/`RegisteredShellComponent` types). Import the SDK exactly as
  `ui_kits/desktop/runtime/host-bridge.ts` and `ui_kits/desktop/package.ts` do. No DOM, no I/O, no CEF,
  no platform internals.
- The backend is the real successor to the in-memory shell fake shipped by PSD-341's
  `createInMemorySurfaceBackend()`; it MUST be drop-in for the same `SurfaceShellHostPorts` slot so the
  PSD-341 router can dispatch shell methods to it unchanged.

## User value
Closes the live shell loop: `package.ts` registers the flagship desktop's 8 screens via
`registerComponent` and composes the running layout via `applyShell`, with safe `previewShell`,
`rollbackShell`, and `currentShell` — backed by the transactional engine instead of failing closed
through the bridge. This is what makes the desktop shell a real, reconfigurable layout rather than a
static mock.

## Non-goals
- NO DOM/CSS/CEF/rendering. NO new shell engine — CONSUME `ManagedShellConfigController`; do not
  re-implement the transactional apply/rollback/fallback logic. Do NOT modify `host-bridge.ts`,
  `package.ts`, or `shell/index.ts` (the port shapes and engine are the contracts of record); if a
  shared type is needed, re-export it — do not fork it. NO persistence / controller IPC (the backend
  is in-memory over the engine; persistence is a later slice).

## Acceptance
`acceptance_command` passes. The deterministic test `sdk/typescript/test/ui-kits/shell-backend.test.ts`
MUST cover, against `createShellBackend()` with real (non-trivial) shell component + config definitions:
- **register then apply composes a layout**: after `registerComponent(...)` for the needed
  components, `applyShell(config)` returns a result satisfying `isShellApplyResult` with
  `ok: true` and `outcome: "committed"`, and a well-formed `ShellComposedLayout`.
- **preview is side-effect-free**: `previewShell(config)` returns a result satisfying
  `isShellPreviewResult`; `currentShell()` reports the same `layout.configId`/`layout.revision`
  before and after the preview (no mutation of committed state).
- **rollback restores prior layout**: after two distinct successful `applyShell` calls,
  `rollbackShell()` returns `isShellRollbackResult` with `outcome: "rolledBack"` and `currentShell()`
  reflects the earlier committed layout; calling `rollbackShell()` with no prior layout returns
  `outcome: "fallback"`.
- **currentShell snapshot**: `currentShell()` satisfies `isShellManagedSnapshot` and its
  `source`/`layout` reflect committed state (`"fallback"` on a fresh backend, `"configured"` after a
  successful apply).
- **duplicate component fails closed**: registering the same component `id` twice returns a
  `ShellResult` with `ok: false` and `error.code === "DUPLICATE_COMPONENT"` (does not throw).
- **apply failure -> fallback + FAILSAFE**: an `applyShell` whose config cannot be planned/composed
  returns `ok: false` with `outcome: "fallback"`, and a failsafe-class compose error returns
  `outcome: "failsafe"` with `status: "FAILSAFE"`; in both cases the previously committed snapshot is
  left intact.
- Reuse the host-bridge guard shapes (`isShellApplyResult`/`isShellPreviewResult`/
  `isShellRollbackResult`/`isShellManagedSnapshot`) — if those guards are not public, re-export them
  from the SDK or assert the equivalent discriminated-union shape; do not weaken the check.
typecheck clean. Pure, headless, deterministic (same inputs -> identical results).

## Security/constraints
- Injected ports only (no ambient I/O); capability-mediated, fail-closed, transactional with
  known-good fallback (`composeKnownGoodFallbackShell`, `shell/index.ts:722`) and FAILSAFE status on
  unrecoverable apply/rollback. Pure/deterministic. No remote imports; lockfile mandatory; no package
  lifecycle scripts; no FFI/native addons.
