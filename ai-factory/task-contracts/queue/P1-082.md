## Objective
Phase 2 (spec §21 "TypeScript system control") deliverable **"Controller shell"** + the §15 "Local web controller"
(FR-009 "Manage … from one controller"): give the owner a **local web control surface** that, on the node, (1) shows
**system status**, (2) lets the owner PROPOSE a config plan and see a **preview diff**, and (3) **applies** it over the
EXISTING agentd `/apply` path — with agentd re-validating every plan. The UI is the UNPRIVILEGED proposer; agentd is
the sole privileged mutator. This is the keystone control-surface slice atop the P1-039 on-device APPLY chain.

Scope v1 to EXACTLY: **status view + plan preview + apply**. No auth-bypass, no auth system at all (the local socket +
systemd sandbox are the boundary, exactly as the existing chain — SO_PEERCRED guards the agentd socket per P1-048).
Reuse the already-built pieces — do NOT re-roll: the vendored evaluator (`./vita/evaluate.ts`), the apply orchestrator
(`applyNodeConfig`, `./vita/apply-node-config.ts`), the agent client (`./vita/agent-client.ts` — `getHealth`,
`getOperations`, `getState`), the apply-capable unix transport (`createDenoUnixSocketApplyAgentTransport`), the plan
diff (`./vita/transaction-plan-diff.ts`), and the controller-side `previewPlan` (`controller/plan/src/plan-preview.ts`)
+ `node-overview` (`controller/overview/src/node-overview.ts`) shapes.

Concretely, three layers (thin vertical slice, each tested):

- **Shared, no-I/O shell core (`sdk/typescript/src/controller-shell.ts`).** A PURE request router + HTML/JSON renderer
  with NO I/O of its own — it takes an injected, narrow `ControllerShellAgent` port (a `Pick<AgentClient, "getHealth" |
  "getOperations" | "getState">` for reads, an injected `evaluate` + `diff` for preview, and an injected
  `ApplyNodeTransport`-style apply caller for apply) and a parsed request `{ method, path, body? }`, and returns a typed
  `{ status, contentType, body }`. Routes, CLOSED set (default-deny any other method/path → 404/405, never a throw):
    - `GET /` → an HTML status page (escaped) summarizing node status (health/reachability + hostname + capability/op
      count, from the reads).
    - `GET /api/status` → the same status as JSON.
    - `POST /api/preview` → take an owner-proposed config (untrusted JSON), `evaluate` it, `diff` current→proposed, return
      the preview (added/removed/changed by capability + any evaluator rejections). NO mutation. Fail-closed: a rejected
      eval / malformed body → a typed `{ ok:false, … }` preview, NEVER a 5xx-throw.
    - `POST /api/apply` → re-evaluate the proposed config and relay the plan to agentd via the injected apply caller
      (which posts ONLY `POST /apply`); surface agentd's `committed`/`rejected`/transport outcome. The UI does NOT
      pre-trust the plan; agentd `buildPlan` RE-VALIDATES (the TS plan is untrusted at the boundary, exactly as P1-039).
  All untrusted input (request body, the proposed config, every agentd response) crosses a trust boundary: parse via
  the canonical `safeNormalize` whole-envelope guard; reject duplicate object keys; treat absent ≠ empty; NEVER execute
  methods off untrusted objects; key any record by an untrusted/spec-valid string into a NULL-PROTOTYPE record (never
  `{}[k]=`); HTML-escape every value rendered into the page (no injection). A guard over untrusted input MUST return a
  typed rejection, never throw (a throw at the boundary is a DoS). Same inputs → byte-identical rendered output
  (determinism; no clocks/random in the render).

- **Controller-host parity wrapper (`controller/shell/src/controller-shell.ts`).** A thin wrapper that wires the shared
  core to a real `AgentClient` + `previewPlan`/`node-overview`-style helpers for the controller package (mirrors how
  `controller/apply-node` and `controller/plan` compose the client). It MUST be byte-equivalent in behavior to the
  shared core on the same injected ports (an UPSTREAM-PARITY test, like P1-039's `apply-node` parity), so the on-device
  vendoring below cannot drift from the controller source.

- **On-device wiring (`os/.../ts/vita/controller-shell.ts` + `main.ts`).** Vendor the shared core into the overlay
  (byte-identical except a `// Vendored from …` header + import-path adjustments — the P1-039 vendoring discipline) as
  `os/.../ts/vita/controller-shell.ts`, then in `main.ts`, AFTER the existing `VITA-APPLY` markers (the chain is already
  CONNECT→STATE→APPLY), drive the shell IN-PROCESS against the live agentd over the existing apply transport:
    - render `GET /` and `GET /api/status` from the REAL `/state` reads and assert the page/JSON contain the measured
      status (non-empty hostname + caps>0),
    - `POST /api/preview` a fixed benign proposed config and read the MEASURED diff counts back,
    - `POST /api/apply` a BENIGN-by-construction plan (re-use the P1-039 pattern: `hostname.set` → the CURRENT hostname,
      read first, so apply COMMITS but changes nothing destructive) and read agentd's `committed` outcome back,
    - then drive a DELIBERATELY-INVALID apply (the P1-039 `vita.invalid.capability` forced-reject) through `/api/apply`
      and prove the shell surfaces agentd's `rejected` (fail-closed; the UI cannot force an invalid mutation).
  Markers (MEASURED — gated on the real reads/round-trip, NEVER synthesized):
    `VITA-UI: status=OK route=status hostname=<h> caps=<n> preview=added=<a>,removed=<r>,changed=<c> apply=committed status=OK`
    (split across lines if clearer; keep the leading `VITA-UI:` token grep-able);
    fail-closed reject `VITA-UI-REJECT: route=apply reason=<sanitized markerToken> status=OK`;
    any transport/unexpected error `VITA-UI-ERROR: status=FAILSAFE` (never crash the oneshot; it still exits 0). Keep ALL
    prior markers — the full chain (VITA-TS → EVAL → PREVIEW → EXPLAIN → CONNECT → STATE → APPLY → CAPSULE-* → PDS-* →
    FILES → …) STILL emits on the same boot. No new systemd unit and NO new Deno permission: the shell runs inside the
    EXISTING `vita-ts.service` oneshot under the SAME `AF_UNIX`-only sandbox and socket-scoped `--allow-read/write`; it
    opens NO network listen socket this slice (see Non-goals — the live HTTP listener + ingress are a later, owner-gated
    slice). The load-bearing trust surfaces (status read, preview eval, apply) are the SAME agentd `/state`+`/apply`
    surfaces already proven; this slice adds only the unprivileged render/orchestration layer over them.

## User value
The owner gets the first real **local control surface** for the node: see whether it is healthy and what it is, propose
a configuration change, SEE the diff before committing, and apply it — all on-device, with the unprivileged UI proposing
and the narrow privileged agent validating + applying (or rejecting). This is the Phase-2 "Controller shell" /
"Local web controller" deliverable (§15, FR-009) and the substrate every later controller view (storage, identity, app,
backup, AI — §17.2 Controller UI pod) renders into. It directly demonstrates the Phase-2 exit gates: a TypeScript plan
configures the node through the control surface (no shell access), and an invalid/overprivileged plan is rejected.

## Non-goals
NO live network HTTP listener / no `Deno.serve` / no `--allow-net` / no new listen socket THIS slice — the shell is a
pure render+router exercised in-process; binding a real port + LAN exposure + ingress is the OWNER-GATED networking/
ingress slice (public ingress is §16 owner-gated; the AF_UNIX-only sandbox stays intact). NO authentication / passkey /
session system (owner passkey enrollment is a separate Phase-2 slice; the local socket + systemd sandbox + SO_PEERCRED
are the boundary). NO multi-node / remote-controller view (FR-009 multi-node is later — single local node here). NO new
agentd capability or endpoint (reuse `/state` + `/apply` exactly). NO destructive boot mutation (the on-device apply is
benign-by-construction: `hostname.set` → CURRENT hostname, like P1-039). NO client-side framework / bundler / npm UI deps
(plain string-rendered HTML + JSON; no remote imports, lockfiles mandatory, no lifecycle scripts). NO storage/identity/
backup/app views beyond the status summary (later pod slices). NO auth-bypass of agentd's re-validation — the UI never
pre-trusts a plan.

## Performance & security constraints
- **UNPRIVILEGED runtime, mediated mutation (spec §3.4, §7.1, §8.2):** the TS UI only PROPOSES; agentd (the sole
  privileged mutator) RE-VALIDATES every plan via `buildPlan` and applies/rejects. The UI never pre-trusts a plan and
  never holds privilege; it runs in the existing `vita-ts.service` DynamicUser sandbox (AF_UNIX-only, empty caps,
  NoNewPrivileges) with NO new Deno permission and NO listen socket.
- **Fail-CLOSED at every trust boundary, NEVER throw:** request body, proposed config, and EVERY agentd response are
  untrusted — guard with `safeNormalize` (whole-envelope), reject duplicate object keys, absent ≠ empty, null-prototype
  keying for untrusted-string keys, never execute methods off untrusted objects; a guard returns a typed rejection, never
  throws (a throw at the boundary is a DoS — prove with a malformed/cyclic regression). Default-deny routing.
- **No injection:** every value rendered into HTML is escaped; the page is plain string-rendered (no template engine,
  no client JS that interpolates untrusted data unescaped).
- **Determinism (§8.2):** the render + preview are pure (no clock/random/I/O in the core); same inputs → byte-identical
  output. The apply caller posts ONLY `POST /apply` (the P1-039 narrow surface).
- **No keys/secrets (§16):** no auth/session/key material; signing/recovery/TPM/ingress are OWNER-HELD. No remote
  imports in prod artifacts; lockfiles mandatory; no package lifecycle scripts; no FFI/shell on runtime input.
- R2 (controller surface that crosses to the privileged apply path) → **reviewer gate** (`npm run review -- P1-082`
  must APPROVE) + independent host-verify before merge.

## REVISION 2 (Codex R2 review: REVISE — preview misses removals — 2026-06-24)
`controller-shell.ts readCurrentPlanForDesiredCapabilities` builds the "current" side ONLY from capabilities present in
the PROPOSED plan — so a capability currently configured but OMITTED by the owner's proposal never appears in `removed`.
That breaks the contract's added/removed/changed preview. FIX: read the FULL current node state (ALL currently-configured
capabilities, from agentd /state) and diff the COMPLETE current set against the proposed plan, so omitted-current
capabilities correctly show as `removed` (and added/changed remain correct). Add a test: a proposal that drops a
currently-present capability must show it in `removed`. Verify: node test + Borg51 boot VITA-UI preview shows
added/removed/changed correctly.
