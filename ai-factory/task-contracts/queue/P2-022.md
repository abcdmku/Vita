## Objective
`buildNodeOperationsReport(input)` (controller/report): the operator's single OPERATIONAL-STATUS view that
composes the health summary (`summarizeNodeHealth`, P2-019) and the audit summary (`summarizeAuditLog`,
P2-021) — distinct from the config-state dashboard. Input `{ health: { report, thresholds }, audit:
{ events } }`. Each sub-summary is computed in isolation: a failure in one does NOT discard the other (a
typed per-section error is recorded, the other still renders) — but the OVERALL `verdict` is fail-closed.
`verdict` ("ok"|"attention"|"critical"): **critical** if health is critical OR the audit log is
non-monotonic (tamper/replay) OR either sub-summary failed to validate; **attention** if health is warning
OR there are recent audit failures; else **ok**. Return `{ verdict, health, audit, issues }` where `issues`
is the flat list of human-readable concerns (failed capabilities, over-threshold resources, broken audit
chain, recent failures). Never throw.

## User value
The "is this node operationally healthy and is its history intact" landing view (FR-008/§17) — one verdict
rolling up capability health, resource pressure, and audit-trail integrity, with the concrete issues.

## Non-goals
- No real metric/audit collection, no agent call, no network. Compose the two existing summaries. Do NOT
  modify P2-019 / P2-021 — import them. No config-state diffing (that is the dashboard).

## Dependencies
P2-019 (health monitor), P2-021 (audit viewer), P0-015. Merged.

## Acceptance tests
`acceptance_command` — `operations-report.test.ts`: healthy node + intact monotonic log ⇒ `verdict: ok`,
no issues; a degraded capability ⇒ `attention`; a failed capability ⇒ `critical`; a NON-monotonic audit
log ⇒ `critical` (tamper) with the audit summary still present; a sub-summary that fails to validate ⇒
`critical` + a typed per-section error while the other section still renders; hostile input ⇒ fail-closed
(no throw). Orchestrator also runs `npm run typecheck`.

## Performance & security constraints
Deterministic, no I/O/network. Per-section isolation but fail-closed overall verdict (validation failure or
broken audit chain ⇒ critical, never silently ok). Never throw. Strict TS (no `any`). R2 → reviewer-gated.

## Reviewer revision (round 2 — BLOCKING, from P2-022.review.md)
The TOP-LEVEL input is not fully validated: the custom `snapshotEnvelope` only did prototype/proxy/array
checks and returned the LIVE object, so a top-level input with valid `health`/`audit` PLUS an extra
accessor/symbol/unknown field is accepted. The OUTER envelope is itself a trust boundary. Round 2: run the
WHOLE input through `safeNormalize` (the canonical intrinsic-safe primitive — sdk/typescript/src/safe-
normalize.ts) FIRST, so accessors/symbols/exotic/proxy are rejected at EVERY level including the top level;
then reject UNKNOWN top-level fields (only `health` and `audit` permitted) fail-closed; only then read the
normalized `health`/`audit` and pass them to the sub-summaries. A top-level object carrying an accessor, a
symbol-keyed property, or an unknown field ⇒ fail-closed (no throw). Add the regression with an EXTERNAL
counter incremented inside a top-level accessor (assert it stayed 0 after the call — P2-018) plus an
unknown-top-level-field case. Do not hand-roll the intrinsic checks — use `safeNormalize`.
