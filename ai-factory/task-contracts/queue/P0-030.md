## Objective
SDK type + fail-closed validator for a unified node desired-state document that bundles the per-subsystem
sections an operator authors together. `NodeChangeSet { nodeConfig?: NodeConfig; services?: ServicesConfig;
accounts?: AccountsConfig; capsules?: CapsuleRegistry }` — each section OPTIONAL (absent = "do not manage
this subsystem in this change-set"), but at LEAST ONE section required. `validateNodeChangeSet(input)`:
- `safeNormalize` the WHOLE input first (the OUTER envelope is its own trust boundary — reject accessors/
  exotic/unknown top-level keys); require ≥1 known section present.
- For each PRESENT section, delegate to its existing validator — `validateNodeConfig` (P0-022),
  `validateServicesConfig` (P0-028), `validateAccountsConfig` (P0-029), `validateCapsuleRegistry` (P6-005)
  — and collect that section's typed rejections under its section key. An invalid section ⇒ the whole
  change-set is invalid (fail-closed), with per-section rejections preserved (no partial accept).
- Return `{ ok: true, changeSet, sectionsPresent } | { ok: false, rejections }`. `sectionsPresent` is the
  sorted list of present section keys. Never throw.

## User value
The single validated document an operator authors to describe a whole-node desired state (FR-005/007) — the
input a comprehensive change preview / apply consumes — validated by composing the existing per-subsystem
validators, fail-closed, so a malformed bundle is rejected as a unit.

## Non-goals
- No apply, no diff/preview (that's the controller previews), no I/O/network. Validate + bundle only. Do
  NOT modify any imported model — compose them. New files only.

## Dependencies
P0-022 (node-config), P0-028 (services), P0-029 (accounts), P6-005 (capsule-registry), P0-015 (safeNormalize). All merged.

## Acceptance tests
`acceptance_command` — `node-changeset-model.test.ts`: a change-set with several valid sections validates,
`sectionsPresent` sorted; an empty object (no sections) ⇒ rejection (≥1 required); an unknown top-level key
⇒ rejection; ONE invalid section (e.g. an accounts entry with uid 0) ⇒ whole change-set invalid with that
section's rejection preserved + no partial accept; an accessor/symbol on the envelope ⇒ fail-closed
(external-counter probe stays 0); hostile/partial input fails closed. Orchestrator also runs `npm run typecheck`.

## Performance & security constraints
Pure/deterministic, no I/O. Fail-closed: safeNormalize the OUTER envelope + reject unknown keys; compose the
per-section validators; one bad section fails the whole set; never throw. Strict TS (no `any`). R2 → reviewer-gated.
