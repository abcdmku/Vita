## Objective
Step 4(a) of trusted boot: make the smoke image's UKI **Secure-Boot-signed and firmware-enforced**, and prove
enforcement with an adversarial matrix. Add a `VITA_SECURE_BOOT=1` toggle to `build-and-boot.mjs` (mirrors the
existing `VITA_VERITY`/`VITA_BOOT_DEBUG` env-toggle pattern) that signs the mkosi-built UKI with a TEST `db` key
(`--secure-boot` + `--bootloader=uki`, so the KERNEL inside the UKI is the signed artifact at
`/EFI/BOOT/BOOTX64.EFI`). Enrollment is **offline via `virt-fw-vars`** (set `PK=KEK=db` from `db.crt` into a fresh
OVMF varstore → User Mode = enforcing) — NOT mkosi `--secure-boot-auto-enroll`, which is dead here because
`--bootloader=uki` removes systemd-boot (the agent that does auto-enroll). `bootQemu` selects the `.secboot` OVMF
code, guards against `*.ms`/`*.snakeoil` vars, and falls back KVM→TCG.

## User value
The booted OS is now **tamper-resistant**: the firmware refuses to launch any kernel/UKI not signed by the owner's
key. Foundation for step 4(b) — swapping the TEST key for the owner's real key (held off-host, §16).

## Non-goals
- TEST keys only (throwaway, gitignored under `os/x86_64/.secureboot/`); the owner's REAL key is step 4(b).
- Smoke mode only — full mode keeps its explicit per-slot `sbsign` step (`VITA_SB_KEY`/`VITA_SB_CERT`); do NOT
  enable mkosi `--secure-boot` there (double-sign). No verity coupling (VITA_VERITY unset for the SB demo).
- No production keys / no RAUC / no N-of-M recovery (later).

## Dependencies
P1-026 (agentd in rootfs) merged. Host (Borg51 WSL): mkosi 26, `sbsign`/`sbverify`/`sbattach`/`ukify`/`openssl`,
`virt-fw-vars` (python3-virt-firmware), OVMF `OVMF_CODE_4M.secboot.fd` + blank `OVMF_VARS_4M.fd`, KVM.

## Acceptance tests
`acceptance_command` (`node --check`) is the Windows-runnable syntax gate; the **real** acceptance is the host
matrix `bash tools/wsl-verify.sh secboot` on Borg51, run by the orchestrator (independent verification). VERIFIED
GREEN (HEAD c615995):
```
POS    PASS   db-signed UKI boots to multi-user on enrolled+enforcing OVMF
N1     PASS   unsigned UKI  → rejected   (Access Denied)
N2     PASS   tampered UKI  → rejected   (one byte flipped post-sign)
N3     PASS   wrong-key UKI → rejected   (rogue, non-enrolled key)
CTRLMS PASS   Vita-db-signed UKI → rejected on Microsoft-keyed OVMF (our key ≠ MS-trusted)
RESULT: PASS
```
Each negative has an offline tri-state gate (sbverify: N1 zero-sigs, N2 pass-pre/fail-post-flip, N3 pass-vs-rogue
/fail-vs-db) so a build failure can't masquerade as a reject; negatives PASS only on absence-of-kernel **AND** a
firmware reject witness; enforcement is proven by the POS-boots / negatives-rejected contrast on the SAME enrolled
varstore. Negative boots run in parallel (KVM).
