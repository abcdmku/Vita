## Objective
Phase 3 (spec §21 "Raspberry Pi and storage"), Raspberry Pi arc slice 1: scaffold the **Raspberry Pi 5 (aarch64)
native image build** as an `os/arm64` mkosi profile that MIRRORS the proven `os/x86_64` profile, cross-buildable on the
x86 build host (Borg51). This is the first deliverable of Phase 3 ("Raspberry Pi 5 native image", FR-002) and lays the
arm64 substrate the later A/B/recovery/storage Pi work builds on. The slice is a **deterministic BUILD plan plus
structural verification** — a real on-hardware Pi boot is OUT OF SCOPE this slice (no Pi available; Borg51 is x86) and
is DOCUMENTED as the owner gate (see Non-goals + the spec exit-gate tie-in below).

Concretely:

- **`os/arm64/mkosi.conf` — the aarch64 arch profile (mirrors `os/x86_64/mkosi.conf`).** It `Include=../common/mkosi.conf`
  (the shared immutable-Debian-trixie baseline, exactly as x86 does) and then OVERRIDES the arch-specific bits:
  - `[Distribution] Architecture=arm64` (mkosi's Debian arch token; the x86 profile uses `x86-64`).
  - `[Output] Output=vita-debian-trixie-arm64-root`.
  - `[Content] Packages=` repeats the FULL runtime allowlist the x86 profile carries, with the kernel swapped to
    `linux-image-arm64` (NOT `linux-image-amd64`) and the Pi 5 firmware/boot packages ADDED:
    `raspi-firmware` (Pi bootloader/firmware staging) — and keep `systemd-boot`/`systemd-boot-efi` for the UEFI path
    the Pi 5 supports. Do NOT silently drop `cryptsetup-bin` or any x86 allowlist member; the arm64 set = the x86 set
    with the kernel swapped + Pi firmware added. The package list MUST be asserted in lockstep by the determinism test
    (mirroring `os/x86_64/test/root-determinism.test.ts`), so a future drift fails CI.
  - `[Distribution] Mirror=` inherits the pinned `snapshot.debian.org` snapshot from `os/common/mkosi.conf`
    (`20260613T000000Z`) — same snapshot, byte-reproducible, no new network pin.

- **`os/arm64/build-root.mjs` — the deterministic arm64 root-build PLANNER (mirrors `os/x86_64/build-root.mjs`).**
  A PURE, no-I/O planner (spec §8.2): same inputs → byte-identical plan. It MUST mirror the x86 planner's shape and
  hardening, differing only in arch:
  - `export function planRootBuild(input = DEFAULT_ROOT_BUILD_INPUT)` returning a frozen plan object with
    `target: "arm64"`, `config.architecture: "arm64"`, `config.mkosiArchitecture: "arm64"`,
    `config.output: "vita-debian-trixie-arm64-root"`, the resolved include chain (`os/common/mkosi.conf` →
    `os/arm64/mkosi.conf`) with per-layer sha256 digests, and the arm64 package allowlist.
  - REUSE the shared pins from the x86 module rather than re-declaring divergent values: import `PINNED_MKOSI_IMAGE`,
    `DEFAULT_DEBIAN_SNAPSHOT`, `DEFAULT_SOURCE_DATE_EPOCH` from `../x86_64/build-root.mjs` (single source of truth — the
    snapshot/mkosi-image/epoch are arch-INDEPENDENT and must not fork). Export an arm64
    `DEFAULT_PACKAGE_ALLOWLIST_ARM64` (or equivalent) so the test can assert it.
  - Mirror the x86 input-validation discipline EXACTLY: reject partial inputs (missing `archConfigText` etc.) and
    accessor/getter-bearing inputs (the "must be a data property" guard) — these are TCB-parser hardening rules the
    x86 planner already enforces and the determinism test pins. Do NOT re-roll a looser validator.
  - The emitted builder command stays digest-pinned (`PINNED_MKOSI_IMAGE`), `--pull=never`, `--network none`,
    `SOURCE_DATE_EPOCH`/`TZ=UTC`/`LC_ALL=C.UTF-8` — identical determinism envelope to x86.

- **`os/arm64/agent-image.conf` — the aarch64 agentd build/stage plan (mirrors `os/x86_64/agent-image.conf`).**
  The privileged Go agent must be a NATIVE aarch64 binary on the Pi. Mirror the x86 agent-image plan but set
  `[Build] GoArch=arm64` (CROSS-compiled on the x86 host via `tools/build/go-in-docker.mjs --env GOARCH=arm64
  --env GOOS=linux --env CGO_ENABLED=0` — the `--env` passthrough proven in P1-026 forwards GOARCH into the container).
  Keep `CgoEnabled=0`, `Trimpath=true`, `BuildVcs=false`, `Ldflags=-s -w -buildid=`, `SourceDateEpoch=1781308800` so the
  cross-built agentd is STATICALLY LINKED + STRIPPED + byte-reproducible (the P1-026 properties, now for arm64). The
  install paths/service/tmpfiles mirror x86 verbatim (the overlay layout is arch-independent). This is a CONFIG/PLAN
  artifact only — building the actual aarch64 binary on hardware-real firmware is part of the documented owner gate.

- **`os/arm64/README.md` — record the Pi kernel branch + the owner boot-verify gate (REQUIRED, this is part of the
  exit gate).** Document, explicitly:
  - **The Pi kernel branch: Raspberry Pi DOWNSTREAM 6.12.y** (spec §"Toolchain baselines" table: *"Raspberry Pi kernel
    — Raspberry Pi downstream 6.12.y initially; move to 6.18.y only after hardware qualification"*). State that the
    generic ARM64 certification line is Linux 6.18.y LTS but the Pi 5 image tracks the downstream 6.12.y branch until
    HW qualification — this satisfies the Phase 3 exit gate "Pi kernel branch is explicitly recorded and separately
    certified" (the RECORDING half; separate CERTIFICATION needs the Pi HW = owner gate).
  - **The owner boot-verify gate:** a full QEMU-aarch64 / real-Pi-5 boot-verify is NOT done in this slice (Borg51 is
    x86; no Pi). The available floor here is the deterministic build + structural assertions. The on-hardware
    boot-to-multi-user + `vita-agentd` running marker (the arm64 analogue of the x86 `VITA-TS`/`vita-agentd` serial
    proof) is an OWNER-EXECUTED gate on real Pi 5 hardware (the Pi-firmware path + the Pi downstream kernel cannot be
    faithfully proven on the x86 host). Record this as the FR-002 acceptance step the owner runs.

- **`os/arm64/test/root-determinism.test.ts` + `os/arm64/test/arm64-image.test.ts` — the STRUCTURAL verification
  (the slice's testable floor).** Node-native, `--experimental-strip-types`, no-network, mirroring
  `os/x86_64/test/root-determinism.test.ts`:
  - **Determinism + plan shape:** `planRootBuild()` is deterministic (two calls byte-identical via the serializer);
    the resolved plan carries `architecture: "arm64"`, `mkosiArchitecture: "arm64"`, the pinned snapshot
    (`20260613T000000Z`, EQUAL to the x86 `DEFAULT_DEBIAN_SNAPSHOT` — proving the arch profiles share one pin), the
    digest-pinned `PINNED_MKOSI_IMAGE`, `--network none`/`--pull=never`, and the arm64 package allowlist.
  - **Layout/packages correctness:** the include chain resolves `os/common/mkosi.conf` → `os/arm64/mkosi.conf`; the
    package allowlist (a) contains `linux-image-arm64` and `raspi-firmware`, (b) does NOT contain `linux-image-amd64`,
    (c) is otherwise a SUPERSET of (or equal to, modulo the kernel swap) the x86 runtime allowlist — assert each x86
    non-kernel member is present so nothing was silently dropped.
  - **Vita overlay present (the "is it actually Vita" assertion):** assert the arm64 profile references the SAME Vita
    overlays the x86 image ships — the TS runtime overlay + the agent overlay are staged into the rootfs (the arm64
    `agent-image.conf` parses, sets `GoArch=arm64`, and points at the agent overlay install paths; the arm64 profile
    is wired to carry the `ts-overlay` + `agent-overlay`). The test PROVES the aarch64 image plan includes the Vita
    TS+agent overlay, not a bare Debian rootfs. A bare-Debian arm64 plan (no Vita overlay, no aarch64 agentd) MUST
    fail this suite.
  - **Cross-build envelope:** assert the arm64 `agent-image.conf` plan sets `GoArch=arm64` + `CgoEnabled=0` +
    reproducibility flags (so the agent is cross-built statically — the property that makes the x86-host cross-build
    sound). An `agent-image.conf` that left `GoArch=amd64` MUST fail.

A no-op/placeholder scaffold (empty mkosi.conf, a planner returning a constant, or an x86-arch plan relabeled "arm64")
MUST fail the suite — the tests assert real arch divergence + the Vita overlay + the cross-build envelope.

## User value
Vita ships on TWO certified targets (spec §"Hardware reference profiles": x86-64 PC AND Raspberry Pi 5, 8 GB). This
slice unblocks the Pi 5 line (FR-002, "Boot a signed native image on Raspberry Pi 5") by producing the aarch64 image
build that the later Pi A/B/recovery/NVMe/storage Phase-3 work extends — a buyer can run the same personal node on
affordable, low-power Pi 5 hardware. Scaffolding it cross-buildable on the existing x86 host means the whole arm64
pipeline (rootfs → overlay → agentd) is exercised + structurally verified in CI today, so the only thing left for the
owner's real-Pi boot-verify is the hardware-specific firmware/kernel proof — not the entire image plumbing.

## Performance & security constraints
- **Determinism (spec §8.2):** `planRootBuild` is PURE / no-I/O — same inputs → byte-identical plan. The arch profiles
  SHARE one pinned Debian snapshot, one pinned mkosi image digest, one `SOURCE_DATE_EPOCH`; the arm64 module imports
  them from the x86 module rather than forking them.
- **Reproducible cross-build:** the arm64 agentd plan keeps `CGO_ENABLED=0` + `GOARCH=arm64` + `-trimpath` +
  `-buildid=` + `SOURCE_DATE_EPOCH` so the cross-built binary is statically linked + stripped + byte-reproducible
  (the P1-026 property, now for arm64) — this is what makes the x86-host cross-build sound and the future verity hash
  stable.
- **Security model (encode it):** the on-device TypeScript runtime is UNPRIVILEGED; privileged mutation happens ONLY
  in the narrow Go `agentd` from a RE-VALIDATED manifest (never raw runtime text), fail-CLOSED. This slice ships the
  arm64 BUILD of exactly that architecture — the same `ts-overlay` (unprivileged Deno sandbox) + `agent-overlay`
  (privileged agentd) the x86 image carries; it does NOT widen any privilege. NO real keys/secrets: signing/TPM/
  recovery key material is OWNER-HELD (§16); the arm64 image is UNSIGNED at this slice (signing = a later owner-gated
  Pi slice). TEST fixtures only; never commit/generate production key material.
- **Supply chain:** no remote imports in the planners/tests; lockfiles mandatory; no package lifecycle scripts; no
  FFI/native addons. The Debian mirror stays the pinned snapshot; `--pull=never` + `--network none` in the builder.
- **R3 → reviewer gate:** boot/image/storage is TCB-adjacent (R3). After independent verification, the orchestrator
  runs `npm run review` and merges ONLY on `VERDICT: approve` (the standing R3 gate). Because it is an aarch64 BUILD
  scaffold without a Pi to boot, the owner boot-verify gate is recorded as the residual real-hardware floor.
