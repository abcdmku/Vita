## Objective
`previewCapsuleChange(current, desired)` (controller/capsule): given current + desired `CapsuleRegistry`
(the P6-005 SDK model), validate BOTH via `validateCapsuleRegistry`, then compute a typed, fail-closed
**change diff** — WITHOUT applying anything: capsules `installed` (new id), `removed` (id gone),
`upgraded`/`downgraded` (same id, version changed — surface old→new version), and `stateChanged`
(installed↔disabled), keyed by capsule id. Surface an `integrityChanged` flag when a kept capsule's
integrity changes WITHOUT a version change (a suspicious re-pin). Return `{ valid, diff, integrityChanged,
rejections }`. Fail-closed: invalid either side ⇒ typed rejection, no diff, never a throw.

## User value
The management-plane "what will this capsule change do" view (FR-012/006) — shows installs/removals/
version changes + flags a suspicious same-version integrity change, on validated inputs only.

## Non-goals
- No real capsule install/run, no agent call, no network. Validate + diff only. Do NOT modify the P6-005
  `capsule-registry-model`; import it.

## Dependencies
P6-005 (capsule registry model: validateCapsuleRegistry), P0-015. Merged.

## Acceptance tests
`acceptance_command` — `capsule-preview.test.ts`: identical registries ⇒ empty diff; installed/removed/
upgraded/downgraded/state-changed capsules ⇒ correctly classified; a same-version integrity change ⇒
`integrityChanged` true; invalid current OR desired ⇒ typed rejection (no diff, no throw); hostile input ⇒
fail-closed. Orchestrator also runs `npm run typecheck`.

## Performance & security constraints
Deterministic, no I/O/network. Fail-closed (reuse `validateCapsuleRegistry`; never throw).
`integrityChanged` correctly flags same-version re-pins. Strict TS (no `any`). R2 → reviewer-gated.
