## Objective
Implement the **unified windowed-app model** (spec §6.1: "TSX, web, WASM, and container apps are ONE class of windowed
surface, built on the existing capsule runtimes"). Pure/headless-testable TypeScript that ties the merged shell (PSD-005)
+ WM (PSD-004) to the existing capsule runtimes (ts-service / OCI / WASM, all merged) as windowed surfaces:
- An `AppDescriptor` model: id, title, **surfaceKind** (`"tsx" | "wasm" | "container" | "web"`), the backing runtime
  reference (a capsule for wasm/container; an in-process TSX component for tsx; a webview for web), default window
  hints. One class regardless of backing.
- An `AppHost` lifecycle: **launch(app)** → registers a window/surface with the shell (PSD-005 surface model) placed by
  the WM (PSD-004 intents) and binds it to its runtime via INJECTED ports (the capsule runtime port for wasm/container;
  a render port for tsx; a webview port for web); **stop(app)** → removes the surface + tears down the runtime binding;
  fail-closed if a runtime/port is unavailable. Deterministic, no ambient I/O (all ports injected).
- The **web** surfaceKind is TYPED + lifecycle-wired but its actual rendering is delegated to a `WebviewPort` that is
  STUBBED here (the real web engine is PSD-000/the engine slice) — `launch` of a web app must fail-closed cleanly if no
  webview port is provided, NOT crash; everything else (tsx/wasm/container) works fully against fake runtime ports.

## User value
The app platform the desktop needs: every app — first-party TSX, a WASM capsule, a container app, or (later) a web app —
is launched and managed as one windowed-surface class, on the runtimes the OS already ships. Proves the §6.1 app model.

## Non-goals
- NO GPU/compositor (PSD-002/003) and NO real web engine (PSD-000) — those are other slices. Web rendering is a stubbed
  injected port here. Tests use fake runtime/render/webview ports.
- Do NOT re-implement the capsule runtimes — bind to them via ports/types.

## Dependencies (merged)
- PSD-005 shell surface model + PSD-004 WM (on main). The capsule runtimes (ts/OCI/WASM) + lifecycle (merged) — bind via
  injected ports/types, don't import privileged paths.

## Acceptance
`acceptance_command` passes: launching a tsx/wasm/container app registers a windowed surface (placed via WM intents,
bound to its runtime port) and stop tears it down; a web app fails closed cleanly when no webview port is present; all
deterministic + unit-tested with fake ports (incl. a runtime-unavailable fail-closed case). Headless-verifiable; no boot
marker (pure model). A later slice wires real webview rendering + the compositor.

## Security/constraints
- Apps bind to runtimes ONLY through injected capability ports — no ambient host access; fail-closed on unavailable
  runtime/port. Pure/deterministic; no remote imports; lockfile; no lifecycle scripts.

## Definition of done
- `AppDescriptor` + `AppHost` (launch/stop) unifying tsx/wasm/container/web as one windowed-surface class over the
  merged shell+WM + capsule-runtime ports; web stubbed + fail-closed; comprehensive unit tests incl. fail-closed cases;
  typecheck clean. R2 reviewer gate + my verification (run the suite).

## REVISION 1 (Codex R2 review: REVISE — app-lifecycle fail-closed — 2026-06-25)
Two real consistency bugs in the launch/stop lifecycle:
1. **`stop()` must be fail-closed + consistent (index.ts:312):** it removes the shell surface BEFORE confirming runtime
   teardown; if `#unbindRuntime()` fails (:316), it returns an error with the surface already gone but the runtime
   binding still LIVE and the launch still tracked — an inconsistent leaked state. FIX: make stop deterministic — tear
   down the runtime and remove the surface as an all-or-consistent operation; on a teardown failure, do NOT leave a
   removed-surface + live-runtime + tracked-launch mismatch (surface a FAILSAFE/error with a well-defined end state, no
   leak). Add a regression test where runtime stop fails.
2. **Failed-launch rollback must not leak the runtime (index.ts:251, :269):** `#rollbackRuntime()` discards the
   `#unbindRuntime()` result, so a shell/WM failure can return a failed launch while leaving an UNTRACKED runtime still
   running. FIX: handle the rollback teardown failure explicitly — if the runtime can't be torn down during rollback,
   surface it (fail-closed), never silently leak. Add a test where rollback runtime stop fails.
Verify: `npm run typecheck && node --experimental-strip-types --test sdk/typescript/test/appshell/appshell.test.ts` —
incl. the runtime-stop-fails-on-stop and runtime-stop-fails-on-rollback tests; no leaked/inconsistent state.

## REVISION 2 (Codex R2 re-review: REVISE — make the lifecycle a CONSISTENT transaction over BOTH resources — 2026-06-25)
rev1 fixed the runtime-teardown direction; the SURFACE-teardown direction has the same bug. Solve it comprehensively:
the launch/stop lifecycle owns TWO resources — the shell SURFACE and the runtime BINDING — and must keep them consistent
with the tracked-launch state in EVERY failure path. INVARIANT: at all times, tracked launches and live resources match
(no untracked-but-live surface or runtime; no tracked-but-dead).
- **stop():** tear down surface + runtime. If EITHER fails, do NOT delete `#launches` / update `#windowModel` in a way
  that leaves a live surface or runtime untracked. Either keep the launch tracked so a retry finishes teardown, OR
  record explicit pending-cleanup; return a FAILSAFE/error reflecting the real state. Never delete tracking while a
  resource leaks.
- **failed-launch rollback & `#cleanupFailedLaunch()`:** roll back surface + runtime; if a rollback step fails (surface
  OR runtime), RECORD the leaked resource as pending-cleanup (do not delete the cleanup record before confirming removal
  succeeded). Don't return rollback-failed while silently leaking a surface or runtime.
Tests (all four directions): stop with surface-removal failure; stop with runtime-teardown failure; rollback with
surface-rollback failure; rollback with runtime-rollback failure — each ends in a CONSISTENT, retry-able state (no
untracked live resource). Keep the rev1 tests + the 7 passing.

## REVISION 3 (same blocking 3x — EXACT reorder required — 2026-06-25)
The prior revs did not change the order; do this EXACTLY. The bug is that tracking/state is mutated BEFORE teardown is
confirmed. Invert it:
- **`stop()` (index.ts ~352):** FIRST attempt BOTH teardowns — `removeSurface()` AND the runtime unbind — and capture
  their results. Emit WM close intents / update `#windowModel` / `delete #launches` ONLY IF BOTH succeeded. If EITHER
  fails: do NOT delete `#launches`, do NOT update `#windowModel` to a removed state — keep the launch TRACKED (so a
  retry can finish) or write a `#pendingCleanup` record, and return the error. Tracking is removed ONLY on full success.
- **failed-launch rollback (index.ts ~302) and `#cleanupFailedLaunch()` (~602):** confirm BOTH `#rollbackSurface()` and
  the runtime rollback SUCCEEDED before deleting any cleanup/launch record. If a surface or runtime teardown fails,
  WRITE a `#pendingCleanup` entry (id + which resource leaked) and do NOT delete the record — so a later `stop()`/sweep
  finishes it. Never return success/rollback-failed while a surface or runtime is live but untracked.
Add `#pendingCleanup` (a Map) + a test that after a failed teardown, the resource is in `#pendingCleanup` and a retry
clears it. Tests: stop surface-fail, stop runtime-fail, rollback surface-fail, rollback runtime-fail — all leave a
tracked/pending (never untracked-live) state. Verify the full appshell suite passes.

## REVISION 4 (EXACT fix from exhaustive lifecycle audit — WM-emit ordering in stop() + #cleanupPendingApp() — 2026-06-25)
An exhaustive multi-agent audit (adversarially verified) found EXACTLY 2 remaining violations — both the SAME pattern as
the surface/runtime fixes, but for the THIRD resource (WM close-intent emission), and both about `#windowModel`. Apply
this EXACT fix; do not change anything else:

1. **`stop()` (index.ts ~363-373):** currently emits WM intents, then advances `this.#windowModel = nextWindowModel`
   and `this.#launches.delete(appId)` UNCONDITIONALLY before `if (!emitted.ok) return emitted`. Mirror the LAUNCH path
   (which checks `emitted.ok` before advancing the model). Replace with:
   ```
   const emitted = this.#emitWindowManagerIntents(intents, `/apps/${pathToken(appId)}/wm`);
   if (!emitted.ok) {
     // close intents did not land; window still LIVE on the WM substrate — keep a retry handle, don't advance the model
     this.#rememberPendingCleanup(appId, undefined, launch.surfaceId, launch.windowId, false, true);
     this.#launches.delete(appId);
     return emitted;
   }
   this.#windowModel = nextWindowModel;
   this.#launches.delete(appId);
   ```
2. **`#cleanupPendingApp()` (index.ts ~683-689), the windowOpen branch:** same bug in the RETRY path. Currently emits,
   then `this.#windowModel = nextWindowModel` + `this.#pendingCleanup.delete(cleanup.appId)` UNCONDITIONALLY before the
   `emitted.ok` check. Fix:
   ```
   emitted = this.#emitWindowManagerIntents(intents, `/apps/${pathToken(cleanup.appId)}/wm`);
   if (!emitted.ok) {
     // window still open on the WM — keep the pending entry as a retry handle, don't advance the model
     this.#rememberPendingCleanup(cleanup.appId, undefined, cleanup.surfaceId, cleanup.windowId, false, true);
     return emitted;
   }
   this.#windowModel = nextWindowModel;
   this.#pendingCleanup.delete(cleanup.appId);
   ```
   (Adjust arg names to the real `#rememberPendingCleanup` signature; the intent is: record that the WINDOW-close is the
   outstanding resource so a later stop()/sweep retries it; runtime+surface already torn down on this branch.)

TESTS (add 2; keep the 9 passing): (a) `stop()` where the WM port `setTextureVisibility`/`setFocus` THROWS → assert
`#windowModel` still shows the window OPEN (length unchanged), a pendingCleanup entry exists with windowOpen=true, and a
retry (WM port now succeeds) closes it + clears pendingCleanup; (b) `#cleanupPendingApp()` retry where the WM emit
THROWS → same assertions. INVARIANT: never advance `#windowModel` or drop the retry handle while WM close-intents have
not landed.
Verify: `npm run typecheck && node --experimental-strip-types --test sdk/typescript/test/appshell/appshell.test.ts`.

## REVISION 5 (Codex R2: create-before-throw surface leak — 2026-06-25)
The rev4 WM-emit ordering fix is CONFIRMED correct (windowModel only advances after WM emission succeeds — reviewer
agreed). One remaining blocking case: failed-launch rollback (index.ts:269-276 / #cleanupFailedLaunch :605-619) treats a
thrown `shell.createSurface()` as proof NO surface exists (passes surfaceLive:false into rollback). But createSurface is
SIDE-EFFECTING — it can allocate/register the surface and THEN throw → a live shell surface left unremoved + untracked
(runtime rollback succeeds, no pending cleanup). FIX: treat a createSurface failure as "surface MAY be live" — on the
rollback path attempt removeSurface, and if removal fails record a #pendingCleanup entry for the possibly-live surface;
never assume surfaceLive:false from a throw. Add a regression test: fake ShellSubstratePort.createSurface RECORDS the
surface then throws → assert the surface is removed OR tracked in pendingCleanup (no untracked-live surface). Keep all
existing tests passing.
