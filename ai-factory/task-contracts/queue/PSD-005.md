## Objective
Spec §6.1: the desktop shell is a **composite TSX/CSS layout** the owner customizes by **registering components** and
**editing the desktop's own TSX**. Implement the shell COMPOSITION layer as TypeScript (headless-testable, rendering to
the substrate via injected ports — the actual GPU paint is PSD-002/003 on the VMware target):
- A **component registry**: register a shell component (id, TSX render fn, default placement/role) + resolve a shell
  layout from a composite TSX/CSS definition into a tree of surfaces the WM policy (PSD-004) + compositor place.
- A **declarative shell config** (the owner-editable TSX/CSS layout) evaluated to a placement/surface tree — PURE +
  deterministic (no I/O), so the same shell config → identical layout.
- **Safe live editing (the hard requirement):** shell layout is a managed configuration through the control plane —
  **preview → apply → rollback**. A broken/throwing shell edit MUST NOT brick the GUI or lock the owner out: on apply
  failure or a shell that fails to compose, fall back to a **known-good fallback shell** (a minimal built-in shell that
  always composes) and surface the error — fail-CLOSED to the fallback, never to a black screen.

## User value
The desktop is fully customizable TSX/CSS, safely — the owner can rearrange/extend the shell with confidence that a bad
edit rolls back to a working desktop.

## Non-goals
- NO GPU paint / compositor here (PSD-002/003). The shell composes to a surface/placement tree against injected ports;
  tests use fakes.
- NO panel/launcher/settings apps (PSD-006/007).

## Dependencies
- PSD-001 substrate interface; PSD-004 WM policy (placement of the composed tree). If those aren't merged yet, define
  the minimal port/types here consistent with their contracts and reconcile at merge (keep-both).
- Control plane (preview/apply/rollback) for the managed-shell-config editing — reuse the existing eval→preview→apply
  discipline.

## Acceptance
- `acceptance_command` passes: component registry + composite-TSX→layout is deterministic + unit-tested; the
  rollback/fallback path is tested (a throwing/invalid shell edit → known-good fallback shell composes + error
  surfaced, owner not locked out). Headless-verifiable on Borg51 (pure composition logic). A later integration slice
  paints it on the VMware target.

## Security/constraints
- Shell config editing goes through the control-plane preview/apply/rollback (managed configuration) — fail-closed to
  the known-good fallback. The shell runs as the unprivileged desktop session (no privilege escalation via shell edits).
- Pure/deterministic composition; no remote imports; lockfile; no lifecycle scripts.

## Definition of done
- Component registry + composite-TSX/CSS→layout (deterministic) + preview/apply/**rollback** + known-good **fallback
  shell** (a broken edit can't brick the GUI); comprehensive unit tests incl. the fallback path; typecheck clean. R2
  reviewer gate + my verification (run the unit suite). GPU paint deferred to the VMware integration slice.
