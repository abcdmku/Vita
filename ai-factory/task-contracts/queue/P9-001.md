## Objective
The previously-blocked config→plan evaluator (spec §8.2), now BUILDABLE via the shared capability manifests
(ADR 0007). It turns a node desired-state config into a validated transaction plan, CLOSED + deterministic +
fail-closed, deriving its capability vocabulary + per-capability validation from the manifests (no drift —
the same manifests the Go agent validates against).
- `evaluateNodeConfig(config, registry)`:
  - `registry`: a `CapabilityManifestRegistry` = `ReadonlyMap<string, CapabilityManifest>` (the CLOSED set of
    known capabilities; built from the loaded manifests — currently `{ "timesync": TIMESYNC_MANIFEST }`,
    extensible as caps migrate). The registry IS the closed vocabulary.
  - `config`: the desired state — an object `{ [capabilityName]: request }`. `safeNormalize` it first.
  - For each capability key (process in SORTED order for determinism): if the key is NOT in `registry` ⇒
    typed rejection `UNKNOWN_CAPABILITY` (closed — unknown caps are rejected HERE, not deferred to the
    agent). Else compile + run that capability's manifest validator (`compileCapabilityValidator(registry.
    get(key))`) over the request; on invalid ⇒ collect the per-capability rejections (NO partial plan); on
    valid ⇒ emit a plan operation `{ capability: key, request: <the validated/canonical value> }`.
  - Reject an empty config (≥1 capability required) and a non-object/hostile config (fail-closed via
    safeNormalize). ANY invalid capability ⇒ the WHOLE evaluation fails (no partial plan).
  - Output `{ ok: true, plan: { operations: ReadonlyArray<{capability, request}> } } | { ok: false,
    rejections }`. `operations` are in sorted capability order (deterministic: same input ⇒ byte-identical
    plan). Pure, no I/O, never throws.

## User value
Resolves the §8.2 feasibility wall (the blocked P9-001): a CLOSED, drift-free config→plan evaluator the
controller uses to turn an authored node config into a validated plan BEFORE submitting to the agent — the
core of whole-node apply — with the agent enforcing the IDENTICAL manifest rules (preview == evaluate ==
apply). Supersedes the blocked `ai-factory/task-contracts/blocked/P9-001.md`.

## Non-goals
- No agent submission/HTTP (the controller apply-flow does that), no I/O/network, no operation ORDERING
  semantics beyond deterministic sort (dependency ordering is a later concern). Import the manifest types +
  `compileCapabilityValidator` from `sdk/typescript/src/capability-manifest.ts`; do NOT reimplement validation.

## Dependencies
P9-003 (manifest + loader + `TIMESYNC_MANIFEST`), P9-005 (the validated dialect), P9-006 (conformance —
proves the manifest validation matches the agent). All merged. P0-015 (safeNormalize).

## Acceptance tests
`acceptance_command` — `evaluate.test.ts`: a config `{ timesync: {enabled:true, servers:[...]} }` with a
registry containing timesync ⇒ `ok:true` with one sorted operation carrying the validated request; an
UNKNOWN capability key ⇒ `UNKNOWN_CAPABILITY` rejection (closed, not deferred); an invalid timesync request
⇒ typed rejection with NO plan (no partial); a multi-capability config ⇒ operations in sorted order
(deterministic — assert byte-identical plan across runs); an empty config ⇒ rejection; a hostile/non-object
config ⇒ fail-closed (external-counter accessor probe). Orchestrator runs `npm run typecheck`.

## Performance & security constraints
PURE/deterministic, NO I/O (spec §8.2 — same inputs ⇒ byte-identical plan). CLOSED (unknown caps rejected at
evaluation, not deferred). Fail-closed via safeNormalize + the manifest validators; no partial plan; never
throws. Strict TS (no `any`). R2 → reviewer-gated.
