## Objective
`evaluateNodeConfig(config)` (runtime/evaluator): the spec **§8.2 config evaluation** — a PURE, NO-I/O,
deterministic transformation of a declarative node config (a set of per-capability desired-states keyed by
capability name) into an ordered **plan of operations** (the same op shape the agent /apply consumes:
`{ operations: [{ capability, request }] }`), ready to preview/apply. FIRST read the existing SDK to REUSE
its plan/operation + capability types (`sdk/typescript/src` — plan model, operation, capabilities) rather
than re-inventing them. NEW boundary ⇒ use `safeNormalize` for the untrusted `config`, then evaluate on
the trusted plain value.
- **Deterministic**: same config ⇒ BYTE-IDENTICAL plan; operations ordered by a stable rule (e.g. by
  capability name) so output never depends on input key order or Map iteration.
- **Fail-closed**: an unknown capability key, a malformed per-capability desired-state, or any structure
  that cannot be evaluated ⇒ a typed evaluation rejection (never a throw, never a partial/best-effort plan).
  Reject duplicate capability keys. The capability set is CLOSED (only known capabilities evaluate).

## User value
The deterministic config→plan step the whole control flow rests on (§8.2, FR-005/006): author a config,
evaluate it to a reproducible plan, preview it (P2-008), apply it (P2-013). Reproducible by construction.

## Non-goals
- No real apply, no agent/network/I/O, no per-capability semantic execution. Pure config→plan structure
  evaluation only. Do NOT modify the SDK plan/capability source — import + reuse it.

## Dependencies
P0-015 (safeNormalize), the existing SDK plan/operation/capability types (read `sdk/typescript/src`). Merged.

## Acceptance tests
`acceptance_command` — `evaluate.test.ts`: a valid multi-capability config ⇒ an ordered plan with one
operation per declared capability, byte-deterministic across runs and INDEPENDENT of input key order; an

rejection (no partial plan); duplicate capability keys ⇒ rejected; hostile/partial input ⇒ fail-closed via
safeNormalize (no throw). Orchestrator also runs `npm run typecheck`.

never partial/throw). Stable ordering independent of input order. Strict TS (no `any`). R2 → reviewer-gated.

## Reviewer revision (round 2 — BLOCKING, from P9-001.review.md)
1) **Reuse the SDK's SINGLE source of truth** — do NOT locally redefine the capability vocabulary,
   operation, or plan types. READ `sdk/typescript/src` and import the existing plan/operation/capability
   model; the closed capability set must be the SDK's, so the evaluator can't drift from what `/apply`
   consumes.
2) **No prototype pollution.** Round 1 built canonical objects with `{}` and `output[key] = …`, so an own
   `__proto__`/`constructor`/`prototype` key in a normalized request mutates the prototype (reintroducing
   pollution after safeNormalize) or silently drops fields. Build canonical objects with
   `Object.create(null)` (or reject own `__proto__`/`constructor`/`prototype` data keys); preserve all
   trusted data properties. Add a regression with a `__proto__` request key.
3) **Validate each per-capability desired-state against its real request schema** so the plan is
   `/apply`-ready. `{ "hostname.set": {} }`, `{ "hostname.set": { "bogus": true } }`, or
   `{ "node.config": { "desired": { "mode": "normal" } } }` (missing required fields) must REJECT (no
   partial plan), matching what the Go transport's typed decoders/validators would reject. Reuse the SDK's
   per-capability request schema/validator where it exists; if the SDK does not model a capability's
   request shape, say so in your report rather than accepting "any object". Add request-schema regressions.

## Reviewer revision (round 3 — BLOCKING + SCOPE CORRECTION, from P9-001.review.md round 2)
Root cause: round 2 RE-IMPLEMENTS per-capability request SEMANTICS in TS (`CAPABILITY_EVALUATORS`,
local IPv6/timestamp/etc. checks), which inevitably DRIFTS from the authoritative Go agent validators
(e.g. it accepts `:::/0` and `0001-01-01T00:00:00+00:00` that the agent rejects). That source of truth
lives in the Go agent and cannot be reused from TS — so the evaluator must NOT own per-capability
semantic validation. Re-scope to the correct layering:
- The evaluator is a PURE STRUCTURAL transform: validated config (keyed by capability name) → a
  deterministic `{ operations: [{ capability, request }] }` plan, REUSING the SDK plan/operation types.
- DROP all per-capability semantic request schemas (IPv6/timestamp/hostname/etc.). Each request value is
  passed through as TRUSTED PLAIN DATA after STRUCTURAL checks only (must be a plain object;
  prototype-safe via `Object.create(null)`; dup-key rejected). The **agent's `/apply` Validate is the
  authoritative semantic gate** (and the controller previews it) — document this boundary explicitly in
  the module.
- Capability vocabulary: if `sdk/typescript/src` exposes a canonical capability-name set, import + use it
  as the closed set; if it does NOT (the names are authoritative in the Go agent registry), accept any
  syntactically-valid capability name and DOCUMENT that the agent registry is the authoritative closed
  set (an unknown capability is rejected at /apply). Do not invent a second drifting vocabulary/schema.
- Keep: determinism (sorted, input-order-independent), dup-key rejection, fail-closed on non-object/
  hostile/partial input, no prototype pollution. Update tests to match (drop the per-cap-semantic tests;
  keep structural + determinism + prototype + dup-key + closed/known-vocabulary).
