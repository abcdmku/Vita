## Objective
`evaluateNodeConfig(config)` (runtime/evaluator): the spec **§8.2 config evaluation** — a PURE, NO-I/O,
deterministic transformation of a declarative node config (a set of per-capability desired-states keyed by
capability name) into an ordered **plan of operations** (the same op shape the agent /apply consumes:
`{ operations: [{ capability, request }] }`), ready to preview/apply. FIRST read the existing SDK to REUSE
its plan/operation + capability types (`sdk/typescript/src` — plan model, operation, capabilities) rather
than re-inventing them. NEW boundary ⇒ use `safeNormalize` for the untrusted `config`, then evaluate on
the trusted plain value.
- **Deterministic**: same config ⇒ BYTE-IDENTICAL plan; operations ordered by a stable rule (e.g. by
  capability name) so output never depends on input key order or Map iteration.
- **Fail-closed**: an unknown capability key, a malformed per-capability desired-state, or any structure
  that cannot be evaluated ⇒ a typed evaluation rejection (never a throw, never a partial/best-effort plan).
  Reject duplicate capability keys. The capability set is CLOSED (only known capabilities evaluate).

## User value
The deterministic config→plan step the whole control flow rests on (§8.2, FR-005/006): author a config,
evaluate it to a reproducible plan, preview it (P2-008), apply it (P2-013). Reproducible by construction.

## Non-goals
- No real apply, no agent/network/I/O, no per-capability semantic execution. Pure config→plan structure
  evaluation only. Do NOT modify the SDK plan/capability source — import + reuse it.

## Dependencies
P0-015 (safeNormalize), the existing SDK plan/operation/capability types (read `sdk/typescript/src`). Merged.

## Acceptance tests
`acceptance_command` — `evaluate.test.ts`: a valid multi-capability config ⇒ an ordered plan with one
operation per declared capability, byte-deterministic across runs and INDEPENDENT of input key order; an
unknown capability key ⇒ typed rejection (closed set); a malformed per-capability desired-state ⇒ typed
rejection (no partial plan); duplicate capability keys ⇒ rejected; hostile/partial input ⇒ fail-closed via
safeNormalize (no throw). Orchestrator also runs `npm run typecheck`.

## Performance & security constraints

never partial/throw). Stable ordering independent of input order. Strict TS (no `any`). R2 → reviewer-gated.
