## Objective
Add the FR-018 "install and manage a PDS module" lifecycle as a **capsule-backed managed module** in
a new Go capability package `agent/capabilities/pdsmodule` (Go module `github.com/vita/agent`). The
AT-Proto PDS today exists only as a data plane — `agent/capabilities/pdsrepo` + `agent/capabilities/pdssync`
(VITA-PDS markers) and the TS manifest `protocols/atproto/src/pds-manifest.ts` (`org.atproto.pds`,
`packageClass: "oci-service"`). This slice makes the PDS run as a *managed capsule module* with a real
**install / update / start / stop / remove** lifecycle, instead of ad-hoc on-device test calls.

Concretely the capability MUST:
- Resolve a PDS-module install through the **existing signed capsule path** — reuse the capsule
  registry/runtime primitives in `agent/capabilities/capsule` (`capsule.go`, `lifecycle.go`). Do NOT
  fork or re-implement integrity/scheme checking: reuse `isValidSRI` (delegates to
  `capsulestorage.IsValidIntegrity`) for the `integrity` field and `hasInlineReferenceScheme` /
  `inlineReferenceSchemes` (the `forbiddenSchemePrefix` set in `capsule.go:877`) to reject inline
  reference schemes in the module `ref`.
- Be **deterministic and manifest-driven**: the module descriptor (id `org.atproto.pds`, version,
  `ref`, `integrity`, desired lifecycle state) is the only input; same input → same recorded state and
  transitions, no ambient I/O beyond the injected state root / capsule store (mirror the
  `defaultStateRoot = /var/lib/vita-agent`, `0o600` file / `0o700` dir, `atomicfile` write pattern used
  in `capsule.go`).
- Model the lifecycle states `installed` / `running` / `stopped` / `removed` and the transitions
  install→start (running), start→stop (stopped), stop→start, →update, →remove. Reuse the capsule
  lifecycle op vocabulary (`update`/`restart`/`stop` in `lifecycle.go`) where applicable rather than
  inventing a parallel one.
- **Record transitions to durable state** readable via the existing `/state` surface (the capability
  exposes its current module state the same way other capabilities do, e.g. through `Handle` returning
  a typed response the controller's `/state` read can serialize). Each lifecycle op is **audit-logged**
  (same provenance/audit path the capsule capability already emits to — do not add a new logging sink).
- Reject (fail-closed) a PDS module whose `integrity` is not a valid SRI (unsigned) and one whose `ref`
  contains a forbidden inline-reference scheme, returning a typed `InvalidRequestError`-style rejection,
  with NO state mutation on rejection.

## User value
FR-018 — the owner can install and manage a Personal Data Server as a first-class, signed, audited
module on their node, with a real start/stop/update/remove lifecycle, not just on-device test plumbing.
The PDS becomes a managed capsule like every other app, inheriting the hardened install path.

## Non-goals
- NO new container/microVM runtime, no networking/egress changes, no PDS protocol/federation logic
  (that is `pdsrepo`/`pdssync` and is out of scope) — this is the **module management lifecycle** only.
- Do NOT re-implement integrity or scheme validation; reuse the capsule cap's `isValidSRI` /
  `hasInlineReferenceScheme`. Do NOT alter the TS `pds-manifest.ts` or the capsule package's public
  behavior. No new logging sink, no production keys/secrets handled here.

## Acceptance
`acceptance_command` passes from a clean checkout, offline (`allowed_network: false`). The five
deterministic Go tests in package `agent/capabilities/pdsmodule` cover, with NO wildcard glob:
- `TestPDSModule_InstallResolvesViaSignedCapsulePath` — a PDS module install resolves via the signed
  capsule path (valid SRI integrity + clean `ref`) and lands in `installed` state.
- `TestPDSModule_StartStopTransitionsRecordedAndReadableViaState` — start→running and stop→stopped
  transitions are persisted and read back via the `/state` typed response.
- `TestPDSModule_RejectsUnsignedModule` — an unsigned module (invalid/empty SRI `integrity`) is
  rejected fail-closed with no state mutation.
- `TestPDSModule_RejectsForbiddenSchemeRef` — a module whose `ref` carries a forbidden inline-reference
  scheme is rejected fail-closed.
- `TestPDSModule_LifecycleAuditLogged` — each lifecycle op (install/start/stop/update/remove) emits an
  audit/provenance record.

## Security/constraints
- Capability-mediated, **fail-closed**: reject before any state write. Reuse capsule integrity + forbidden-
  scheme checks (no parallel weaker validator). Deterministic, pure of ambient I/O beyond injected state
  root + capsule store. `0o600`/`0o700` perms, `atomicfile` durable writes, duplicate-JSON-key rejection
  (`jsonsafe.RejectDuplicateObjectKeys`) consistent with the capsule cap. No remote imports; module-pinned
  deps; no FFI; no lifecycle scripts. No production keys/secrets touched.
