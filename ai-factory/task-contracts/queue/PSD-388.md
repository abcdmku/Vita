## Objective
Bind the **live menu bar** in the flagship desktop to a real view-model so it stops being decorative.
Today `ui_kits/desktop/Shell.html` ships a `.v-menubar` whose `.v-menus` block is hard-coded markup
(`<span>File</span><span>Edit</span><span>View</span><span>Go</span><span>Window</span><span>Help</span>`)
with **no `data-vita-*` anchors and no view-model** — it renders in CEF but nothing opens, navigates, or
dispatches. This task adds (a) `data-vita-*` hydration anchors to the menu bar markup and (b) a headless
**menu-bar view-model + screen manifest** (`ScreenModule`, same shape as `ui_kits/desktop/screens/shell.ts`)
that binds the live DOM to the view-model: open/close menus on click, keyboard navigation (arrow keys +
Enter/Escape), and action dispatch through the host bridge (`ui_kits/desktop/runtime/host-bridge.ts`).
- State: ordered top-level menus (id/label), which menu is open (or none), highlighted item index, each
  menu's items (id/label/command/enabled/separator). Actions: `menubar.open(menuId)`, `menubar.close()`,
  `menubar.toggle(menuId)`, `menubar.next()/prev()` (move highlight, wrap), `menubar.openNext()/openPrev()`
  (move across top-level menus while open), `menubar.activate()` (Enter → dispatch highlighted item's
  command through the injected host port), `menubar.escape()` (Escape → close). Deterministic ordering of
  menus and items.
- Anchors use the EXISTING dialect already in `Shell.html` (`data-vita-action`, `data-vita-command`,
  `data-vita-bind-text`, `data-vita-bind-list`, `data-vita-key`, `data-vita-screen`) — do NOT invent a new
  attribute scheme. Wire the menu-bar items as `data-vita-action`/`data-vita-command` entries that the
  binder routes to the screen's `actions` map.
- Put the view-model under `ui_kits/desktop/viewmodels/MenuBar.ts`, the screen manifest under
  `ui_kits/desktop/screens/menu-bar.ts` (register it in the screens manifest the way `shell.ts` is), and
  tests under `sdk/typescript/test/ui-kits/menu-bar-hydration.test.ts`.
- Import the SDK exactly as `ui_kits/desktop/screens/shell.ts` does; consume ONLY public
  `@vita/desktop-sdk` / runtime exports. Dispatch goes through the injected host bridge port, never ambient I/O.

## User value
The menu bar in the CEF desktop becomes functional instead of decorative: a user can click File/Edit/View/…,
arrow-key through items, press Enter to run a command, and Escape to dismiss — the real interaction logic the
CEF-rendered HTML hydrates against. Without it the flagship menu bar does nothing.

## Non-goals
- NO new visual design — `Shell.html` markup/CSS is the design of record; only ADD `data-vita-*` anchors to
  existing menu nodes, do not restyle. NO CEF/native rendering work. NO platform internals. Do NOT re-implement
  the host bridge or SDK ports — consume them. NO context-menu changes (that is `viewmodels/SurfaceMenu.ts` /
  `context-menu.ts`, out of scope here).

## Acceptance
`acceptance_command` passes. The deterministic test `sdk/typescript/test/ui-kits/menu-bar-hydration.test.ts`
covers, against a fake host-bridge port (no real I/O):
- click a top-level menu → it opens (snapshot shows the menu open, others closed);
- arrow-key navigation moves the highlight and wraps; open-next/open-prev moves across top-level menus;
- Enter on a highlighted item → dispatches that item's command through the injected bridge exactly once with
  the expected command id;
- Escape → closes the open menu (highlight cleared);
- inert without a bridge: when no host bridge port is selected, hydration fails closed (the screen is inert /
  activation does not throw and no command is dispatched).
Typecheck clean; pure and headless (no DOM globals required by the view-model logic).

## Security/constraints
- Injected host-bridge port only (no ambient I/O); capability-mediated, fail-closed when the port is absent;
  pure/deterministic snapshots. No remote imports; lockfile mandatory; no package lifecycle scripts;
  no FFI/native addons.
