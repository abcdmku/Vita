## Objective
`resolveInstallPlan(entry, lockfile)` (packages/install) turns a validated catalog entry (P1-003) + its
lockfile into a typed, fail-closed **install plan** — WITHOUT any real install/network/fs:
1. Validate the lockfile against the supply-chain policy (reuse `validateLockfilePolicy`, P4-002) —
   reject if any dep is unpinned, lacks SRI integrity, declares a lifecycle script, or is remote/URL.
2. Resolve the dependency set from the lockfile (the closed, pinned graph) into ordered install steps.
3. Compute the **capability grants**: the plan's granted caps = the entry's REQUESTED caps intersected
   with what the trust-tier (§9.3) allows — reject (do not silently drop) if the entry requests a cap
   outside its tier. Least-privilege; default-deny.
NEW validator ⇒ use `safeNormalize` for the untrusted `entry`/`lockfile` boundary, then operate on the
trusted plain value. Standalone module — import P1-003/P4-002/safeNormalize; no shared-index edits.

## User value
The deterministic, security-checked plan that gates every package install (FR-010): no unpinned deps, no
install scripts, no over-broad capabilities — computed + reviewable before anything is fetched or run.

## Non-goals
- No real fetch/download/extract/run, no network, no Deno execution. Plan resolution + validation only.
  Do NOT modify catalog/lockfile-policy source; import them.

## Dependencies
P1-003 (catalog entry), P4-002 (lockfile policy), P0-015 (safeNormalize), broker capability vocabulary. All merged.

## Acceptance tests
`acceptance_command` — `resolve.test.ts`: a valid entry+pinned-lockfile ⇒ an ordered install plan with
correct least-privilege grants; an unpinned/script-bearing/remote lockfile ⇒ rejected (policy reused); an
entry requesting an out-of-tier capability ⇒ rejected (not dropped); fail-closed on hostile input via
safeNormalize. Orchestrator also runs `npm run typecheck`.

## Reviewer revision (round 2 — BLOCKING, from P3-001.review.md)
1) **Install only the REACHABLE closure, not every lockfile record.** Round 1 visited all records, so a
   policy-valid lockfile carrying an unrelated pinned package would get installed (violates the
   closed-graph / least-supply-chain-surface requirement). Derive the roots from the npm root package
   (`packages[""]` dependencies) AND the JSR `specifiers`, traverse ONLY that dependency closure, and
   either REJECT unreferenced records or exclude them from the plan. The plan must contain exactly the
   closure — no extra packages.
2) **Reject conflicting duplicate records.** Round 1 silently coalesced two entries for the same
   `name@version` (kept the first integrity/source, unioned deps). Reject when duplicates DISAGREE on
   integrity/source/dependencies (a fabricated/under-specified pinned plan); identical duplicates may
   coalesce.
Add regressions: only-reachable-deps-in-plan (unrelated pinned record excluded/rejected); a
duplicate-conflict ⇒ reject; a JSR-specifier success path. (Non-blocking: `policyForTrustTier` should
reference the shared trust-tier policy surface rather than re-embedding it — do it if cheap.)

## Reviewer revision (round 3 — BLOCKING, from P3-001.review.md round 2)
Fail-closed on missing `requestedCapabilities` (AGENTS.md partial-input rule). Round 2 treated an absent
`requestedCapabilities` as "grant EVERY declared capability" via `capabilitiesFromContract(contract)` — a
silent privilege escalation: a verified entry that omits the field would receive all declared data/
ingress/egress grants it never requested. REJECT an entry that omits `requestedCapabilities` (do NOT
synthesize a full request, do NOT default to grant-all). Add a regression: an otherwise-valid entry with
no `requestedCapabilities` ⇒ rejected. (Round-2 closure/duplicate fixes are approved — keep them.)
