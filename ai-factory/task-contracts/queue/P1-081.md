## Objective
Phase-5 "AT Protocol PDS module", next slice atop **P1-067** (the `pds.repo` local repo/records store + commit log).
P1-067 landed CREATE + READ-whole-repo. This slice adds the other two record operations the data product needs:

1. **QUERY / LIST records — by collection, paginated** (a READ-only surface, no mutation). The unprivileged runtime asks
   agentd for "the records in collection `<NSID>`, page-by-page". agentd serves it from its own validated
   `RepoState` (the persisted store), deterministically ordered and bounded — never echoing raw stored bytes.

2. **DELETE a record — tombstone in the commit log, cursor advances** (a privileged mutation, agentd-mediated). The
   record at `(collection, rkey)` is removed from the ACTIVE record set, an append-only **tombstone** log entry
   `{ cursor, op:"delete-record", collection, rkey }` is recorded, and the monotonic commit cursor advances by exactly
   the delete commit — the commit log remains the auditable ordering of every create AND delete, fail-closed.

Both ride the EXISTING `pds.repo` capability and the EXISTING typed Apply (`/apply`) + Read (`/state`) transport — NO
new endpoint, NO new capability. Reuse the P1-067 store, validators, atomic-write/undo single-commit-point, and the
already-present (currently-unused) `recordKeyFromLog` helper in `pdsrepo.go`. Privileged persistent mutation stays
ONLY in the narrow Go agentd acting from the RE-VALIDATED decoded struct (never raw runtime text); the TS runtime only
PROPOSES; fail CLOSED on any invalid/partial/exotic input. Deterministic: same store + same request → byte-identical
result.

Concretely (mirror the P1-067 patterns verbatim where they fit):

- **DELETE op (agentd, `agent/capabilities/pdsrepo/pdsrepo.go`).** Extend the existing typed `ApplyRequest`/
  `DesiredState` decode discipline to carry deletes. Pick ONE of the two shapes below and document it (prefer the
  first — it keeps the create path untouched and the op explicit):
  - a per-record `op` discriminator on the desired records (default `create-record`; `delete-record` for a tombstone),
    OR
  - a sibling `deletes: [{collection, rkey}, …]` array on `DesiredState`.
  Keep the SAME `UnmarshalJSON` fail-closed rules already in `pdsrepo.go`: `jsonsafe.RejectDuplicateObjectKeys`,
  `rejectUnknownFields` (which already rejects `pdssync.IsSecretFieldName` inline-secret names), required-field checks,
  integer-literal cursor (no `.`/`e`/`E`, range `0..pdssync.MaxCursor`), explicit-presence for optional fields. Delete
  semantics, fail-closed:
  - Deleting an EXISTING `(collection, rkey)` removes it from `RepoState.Records`, appends a `delete-record`
    `CommitLogEntry` at the new cursor, and REQUIRES the commit cursor to ADVANCE (`desired.Commit.Cursor >
    state.CommitCursor`) — exactly the create-record cursor-advance/non-regression rule already enforced in
    `applyDesiredState`. The tombstone log entry PERSISTS even though the active record is gone.
  - Deleting a NON-EXISTENT `(collection, rkey)` is fail-closed: either an idempotent no-op converge (cursor must NOT
    advance, like the identical-create no-op) OR a typed rejection — choose, document, and TEST the chosen rule; do NOT
    silently advance the cursor for a delete that changed nothing.
  - A request that both creates and deletes the SAME key, or contains duplicate delete keys, is a conflict → reject.
  - `validateCommitLogEntry` must accept BOTH `create-record` and `delete-record` ops (today it hard-codes
    `createRecordOp`); a stored log with an unknown op still fails closed. The commit-log cursor non-regression /
    "≤ repo cursor" invariants in `validateRepoState` stay intact across deletes.

- **QUERY/LIST op (agentd read surface).** Add a typed query Read alongside the existing whole-repo `ReadRequest`
  (e.g. a `QueryRequest{ Collection string; Cursor *int64-or-pagecursor; Limit int }` routed through the same Read
  path — keep `ReadRequest` working for the P1-067 marker). It returns the records whose `Collection` matches,
  deterministically ordered (the existing `sortRepoState` order: collection then rkey), sliced into a page bounded by a
  fixed `maxPageLimit` constant, with a forward-only page cursor and an `exists`/`total`/`nextCursor` shape so the
  caller can page to completion. Validate `collection` with the SAME `isNSIDLike` used for records (reject malformed),
  clamp/validate `limit` to `1..maxPageLimit` (reject 0/negative/over-cap), and validate the page cursor as a bounded
  integer (reject non-integer / OOR / a cursor past the end). Re-serialize the VALIDATED struct (never raw stored
  bytes — the duplicate-key/last-wins TCB hazard from AGENTS.md §2). Tombstoned (deleted) records do NOT appear in
  query results; they remain only in the commit log.

- **Shared TS model (`sdk/typescript/src/pds-model.ts` + `test/pds-model.test.ts`).** Add the shared, no-I/O validators
  for the new shapes the runtime parses: a `validatePdsQueryResponse` (page of records + `nextCursor`/`total`) and the
  `delete-record` commit-log op, reusing the existing `isReverseDnsNsid` / `isRecordKey` / `isMonotonicCursor` /
  `rejectUnknownFields` / `rejectSecretFieldNames` already in `pds-model.ts` (do NOT fork weaker copies). Keep them pure
  and fail-closed (return a typed validation failure, never throw on untrusted input).

- **On-device wiring (`os/.../ts/vita/pds-repo.ts` + `main.ts`).** AFTER the existing `VITA-PDS-REPO` marker (the
  P1-067 create + read-back), the runtime: (a) issues a QUERY for the test repo's `app.bsky.feed.post` collection via
  `/state`, pages it, and prints `VITA-PDS-QUERY: collection=<nsid> page=<n> records=<m> status=OK` where the counts
  come from agentd's MEASURED response (NEVER synthesized); (b) proposes a DELETE of one fixed test record
  (`app.bsky.feed.post`/`p1-067-post`) at an ADVANCED commit cursor, then READS BACK and prints
  `VITA-PDS-DELETE: removed=<rkey> tombstone cursor=<K> status=OK` where the removal + the new cursor + the
  tombstone-present-in-log are all proven by the READ-BACK (the read-back is the proof); (c) drives a DELIBERATELY
  INVALID request (a delete with a REGRESSED cursor, a delete of a non-existent key that tries to advance the cursor,
  an out-of-range query limit, or a malformed collection) and prints
  `VITA-PDS-DELETE: outcome=rejected reason=<sanitized> status=OK` (and/or `VITA-PDS-QUERY: outcome=rejected …`),
  proving agentd fails closed. Transport/read failure → `VITA-PDS-QUERY-ERROR: status=FAILSAFE` /
  `VITA-PDS-DELETE-ERROR: status=FAILSAFE`. Keep the existing `VITA-PDS-REPO` create/read marker and ALL prior markers
  (the FULL chain still emits on the same boot).

If `pds.repo`'s query/delete shapes are not yet in the on-device evaluator's manifest/capability-manifest dialect, NOTE
that gap in the worker report (a follow-up manifest slice) rather than forcing a divergent manifest — the load-bearing
trust surface this slice is the AGENT validator + the apply/read transport, exactly as P1-067 / P1-042 did.

## User value
Completes the local CRUD surface of the node's AT-Protocol repository (FR-018, "install and manage an AT Protocol PDS
module"): after this slice the node can not only hold records (P1-067) but **enumerate them by collection** and
**delete them with an auditable tombstone** — written through the privileged boundary, surviving reboot, with the
commit log as the tamper-evident order of every create AND delete. Paginated query is what any real client (a feed
viewer, a sync client) needs to read a collection without loading the whole repo; the tombstone-delete is the
foundation for later firehose/MST work where deletes must be ordered events, not silent gaps.

## Performance & security constraints
The TS runtime is UNPRIVILEGED and only PROPOSES; agentd (the sole privileged mutator) RE-VALIDATES from the decoded
typed struct (never raw runtime text), persists the delete transactionally with a single commit point + working undo,
and FAILS CLOSED on any invalid/partial/exotic input. Apply/read surface = EXACTLY the existing `pds.repo` `/apply` +
`/state` (no new endpoint, no new capability). Query is READ-ONLY (no mutation, no cursor advance). Delete is the only
new mutation and obeys the SAME cursor-advance/non-regression + atomic-write/undo invariants as P1-067 create.
Re-serialize the VALIDATED struct on every read/query (never echo raw stored bytes — the duplicate-key/last-wins TCB
hazard). Page limit is a fixed bounded constant (`maxPageLimit`) so a query cannot be coerced into an unbounded
response. A guard over untrusted input MUST NOT throw (a throw at the trust boundary is a DoS — return a typed
rejection); prove with a malformed/cyclic regression on the TS side. No FFI/shell/`os/exec` on runtime-controlled
input. No remote imports in prod artifacts; lockfiles mandatory; no package lifecycle scripts (TS/SDK side). No
keys/secrets — TEST DIDs + SHA-256 hex digests + TEST rkeys only; reject inline-secret-named fields. R3 (privileged
persistent mutation on the TCB path) → two parallel Codex candidates + reviewer gate (`npm run review`) before merge.
