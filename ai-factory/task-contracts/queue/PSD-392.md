## Objective
Bind the existing index dock view-model (`ui_kits/desktop/viewmodels/dock.ts`) to **live window-manager open-window state** so the dock becomes a real multi-app switcher AND launcher. Today `IndexDockModel` tracks running/focused state only from its OWN private `#launches` map (the apps it personally launched via the `launchApp` port) — it never reads the WM `WindowModel`, so it cannot reflect windows opened elsewhere, focus changes made by the stage, or apps with multiple windows. This slice adds a headless, deterministic switcher layer on top of dock entries, driven by the SDK window model.
- New code under `ui_kits/desktop/viewmodels/dock-switcher.ts`; tests under `sdk/typescript/test/ui-kits/DockSwitcher.test.ts`.
- Build ONLY on `@vita/desktop-sdk` public ports + types — read `WindowModel` (`windows[]` with `appId`/`id`/`workspaceId`, `focusStack`) via an injected WM read port, and emit window-manager intents (`focusWindow`) via an injected WM port. NO platform internals, NO DOM/rendering, NO ambient I/O. Import the SDK exactly as `dock.ts` / `stage.ts` already do (`../../../sdk/typescript/src/desktop-sdk/index.ts`), using ONLY public exports.
- Map each pinned dock app (the `IndexDockAppId` set in `dock.ts`) to the set of live WM windows whose `appId` matches. Derive per-entry `running` (≥1 window) and `active` (the entry owning the current focused window per `focusStack`) from the WM model — NOT from a private launch map. Maintain a deterministic, stable ordering of windows per app (sort by `windowId`, mirroring the stage's `compareWindowsByStageKey` ordering) and a per-app cursor for cycling.
- Actions (all pure, returning a frozen result `{ ok, dispatch, state }` in the same shape style as `IndexDockActionResult`):
  - `activate(appId)`: if the app has ≥1 running window → emit a `focusWindow` intent for its **first** window and dispatch `"focusWindow"` (set that app active). If the app has 0 running windows → dispatch `"launch"` carrying the app id/launchable (NO WM intent), so the caller wires it to the existing launch path. Unknown/unpinned app id → fail-closed reject with a stable error code/path (mirror `UNKNOWN_DOCK_APP`).
  - `cycle(appId)`: for an app with multiple windows, advance the per-app cursor and emit a `focusWindow` intent for the next window in deterministic order (wrap around). Single-window app → focuses that one window. Zero-window app → reject (nothing to cycle) with a stable error.
  - `snapshot()`: returns frozen state — per-app `running`/`active`/`windowCount` and the resolved active app id — recomputed from the latest WM read each call (re-read like `StageViewModel.snapshot()` does).
- Fail-closed: if the injected WM read port throws or returns `ok:false`, `snapshot()` falls back to the last-known model and actions reject with a stable `WM_READ_FAILED`-style error; if the WM apply/intent port throws or returns `ok:false`, the action rejects with a stable `WM_INTENT_FAILED`-style error and state is unchanged. Deterministic: same WM model + same action sequence → byte-identical results.

## User value
Makes the dock behave like a real OS dock: clicking a running app focuses its window (and cycles its windows on repeat), clicking a stopped app launches it, and running indicators light up for apps opened anywhere in the WM — not just ones the dock launched. This is the live binding the CEF-rendered dock HTML hydrates against.

## Non-goals
- NO DOM/CSS/rendering/CEF; NO new visual design (the dock HTML is the design of record). NO changes to `dock.ts`'s launch port contract — this layer composes the WM read/intent ports alongside the existing launch path. Do NOT re-implement WM reducers (`focusWindow`, etc.) — consume the SDK exports. No window close/move (that is the stage's job). No pinning/reordering UI.

## Acceptance
`acceptance_command` passes: `npm run typecheck` is clean and the deterministic Node test runner suite at the EXACT path `sdk/typescript/test/ui-kits/DockSwitcher.test.ts` is green against fake/in-memory WM read + intent ports. Tests must cover, at minimum: (1) app with ≥1 window → `activate` marks it active and emits a `focusWindow` intent for the first window; (2) app with 0 windows → `activate` emits a `"launch"` dispatch and NO WM intent; (3) app with multiple windows → repeated `cycle` advances through windows in deterministic order and wraps; (4) running/active indicators in `snapshot()` reflect the injected WM model (windows opened outside the dock count); (5) fail-closed: WM read throw and WM intent reject both produce stable reject results with unchanged state. Pure, headless, no DOM, no network.
