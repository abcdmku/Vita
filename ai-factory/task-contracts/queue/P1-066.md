## Objective
Add a NEW privileged Go capability `backup.archive` (a SECOND capability in the existing `agent/capabilities/backup`
package — leave the merged `backup.policy` capability in `backup.go` UNTOUCHED in behavior) that actually CREATES a
verifiable backup of the node's authoritative persistent data to an INDEPENDENT target, and RESTORES it. This is the
backend half of Phase-5's "Independent attached-disk backup" (spec §10.3) + "Complete node restore" (§21 Phase-5
exit, FR-015). Thin vertical slice: one create + one verify + one restore round-trip, fail-closed, no scheduler/UI/cloud.

Scope of "authoritative data" (the source tree to back up): the persistent agent state root `/var/lib/vita-agent`
— which holds `pds-sync-state.json` (the `pds.sync-state` capability's store) and `backup-policy-desired-state.json`
(the `backup.policy` store) — PLUS the capsule StateDirectory volumes (the per-capsule persistent dirs the capsule
runtime writes under `/var/lib`; the existing capsule `ExecutionManifest.StateDirectory`, `agent/capabilities/capsule/
execute.go:183`). Make the set of backed-up roots an explicit, validated input list (default = the agent state root +
a capsule-volumes root), NOT a hardcoded scatter — so the worker does not hardcode `/var` assumptions that break tests.

The capability exposes a CLOSED typed set of operations via the existing typed-request pattern (see `backup.go`
`ReadRequest`/`ApplyRequest`, `jsonsafe.DecodeStrict`, `RejectDuplicateObjectKeys`):
- **Create** — read the named source roots; produce a single CONTENT-ADDRESSED, integrity-checked backup at an
  INDEPENDENT target directory (a local/attached-volume path supplied as a validated absolute path; NO cloud, NO
  network). The backup is a manifest + content store: every file is hashed (SHA-256), the per-file digest + relative
  path + mode + size recorded in a backup manifest, and the manifest itself carries a top-level digest over its
  canonical serialization (content-addressed: the backup id IS the manifest digest). Write is ATOMIC (the proven
  `os.CreateTemp(dir, ".name-*.tmp")` → write → Sync → Close → `os.Rename` single-commit-point pattern from
  `backup.go:264` / AGENTS.md §2; never a predictable `path+".tmp"`).
- **Verify** — independently re-read a backup at the target, recompute every file digest + the manifest digest, and
  confirm they match the recorded values (detect bit-rot / tamper). Returns ok/which-entry-failed.
- **Restore** — VERIFY FIRST (recompute + match every digest AND the manifest digest); ONLY if verification passes,
  atomically materialize the restored tree into a destination root (staging dir → fsync → rename swap so a crash mid-
  restore never leaves a half-restored authoritative tree; the live tree is replaced as a single commit point, with
  an Undo that restores the prior tree). If verification FAILS, restore REFUSES and mutates nothing (fail-CLOSED).

Survives reboot: the target is a path on the persistent `/var` (verity ro-root + persistent ext4 `/var`, P1-029) or an
attached volume, so a backup created before reboot is restorable after.

Markers (emitted on-device by `main.ts`, MEASURED — never synthesized): on a real create→verify→restore round-trip
against a TEST source tree + TEST target dir under `/var`, emit
`VITA-BACKUP: created=OK restored=OK verified=OK id=<manifestDigestPrefix> files=<n> status=OK`
ONLY when all three really happened and the restored bytes equal the source bytes; plus a fail-closed reject
`VITA-BACKUP-REJECT: reason=<sanitized-step> status=OK` for a forced-invalid case (a backup whose recorded digest does
NOT match its content — restore must REFUSE), and `VITA-BACKUP-ERROR: status=FAILSAFE` on transport/setup failure.
Keep ALL prior markers (the VITA-TS→EVAL→PREVIEW→EXPLAIN→CONNECT→STATE→APPLY→PDS chain) intact.

## User value
The Phase-5 data-product exit-gate spirit (spec §21, FR-015): "Complete node restore succeeds from an independent
backup." The owner can back up the node's authoritative data to an independent attached disk and bring it back, with
integrity guaranteed by content-addressing (a corrupted or tampered backup is detected and refused, not silently
restored). This is the backend that the Restore UI (a later slice) drives.

## Non-goals
- NO cloud / remote / object / SFTP target; NO peer-node backup; NO network at all (§10.3 lists those as later levels).
- NO scheduler / cron execution (the `backup.policy` capability already models schedule/retention; this slice does NOT
  wire a timer — create/verify/restore are explicit operations).
- NO encryption-at-rest of the backup payload, NO recovery-key / TPM use — those are owner-held §16 + a Phase-3 storage
  slice; do NOT generate or commit any key material. (The backup MUST still contain NO plaintext secrets: see security.)
- NO btrfs/LUKS snapshot integration, NO RAUC/OS-image backup, NO migration/x86→arm transform.
- NO controller/web Restore UI (this is the backend only).
- Do NOT change `backup.policy` behavior, the capsule execute path, or any other capability's on-disk format.

## Acceptance tests
`acceptance_command` (go-in-docker, LINUX — the host has no Go on PATH; build/test OFFLINE in the pinned container):
`node tools/build/go-in-docker.mjs --dir agent test ./capabilities/backup/...` and `… vet ./capabilities/backup/...`
must both pass clean. The Go tests MUST prove (using `t.TempDir()` source + target roots, not `/var`):
- **create** produces a content-addressed manifest (backup id == manifest digest) + a content store; every file's
  recorded SHA-256/size/mode matches the source; write is atomic (a pre-planted predictable temp / symlink in the
  target dir does NOT get followed — O_EXCL fresh temp; assert the proven pattern, not `os.WriteFile` to a fixed temp).
- **verify** returns ok for an intact backup AND returns a SPECIFIC failure (which entry) when a stored content byte or
  the manifest digest is mutated on disk (tamper detection).
- **restore** of an intact backup re-materializes a byte-identical tree atomically and returns an `Undo` that restores
  the PRIOR destination tree exactly; restore of a TAMPERED backup REFUSES and leaves the destination UNCHANGED
  (fail-closed — prove the no-mutation partial-failure case: inject a verify failure, assert the live dest tree is
  byte-unchanged and no untracked temp/dir leaks).
- **fail-closed input handling:** a missing-required-field / non-absolute target path / a source-or-target path with
  control chars / a backup payload containing inline secret material (reuse `containsInlineSecretMaterial`) / duplicate
  JSON object keys → REJECT (never throw, never partially honor). Real-op tests that require privileged FS ops under
  go-in-docker may `t.Skip` on EPERM (the AGENTS.md go-in-docker idiom), but the digest/manifest/verify logic tests
  must NOT skip — they run on plain temp dirs.
- The capability is REGISTERED in `registry.go` under a CLOSED name (`backup.archive`); an unknown op is rejected.

Orchestrator host-verify (Borg51 QEMU boot, MEASURED — added by the orchestrator, not the worker): boot the verity
image; the serial shows `VITA-BACKUP: created=OK restored=OK verified=OK id=<digestPrefix> files=<n> status=OK` for a
real round-trip against a TEST source + TEST target dir on persistent `/var`, PLUS `VITA-BACKUP-REJECT: reason=<step>
status=OK` for the forced-tampered case; the prior chain (VITA-TS … VITA-APPLY, VITA-PDS-WRITE) still PASSES. The
marker is gated on the restored bytes ACTUALLY equalling the source bytes (never printed unconditionally).

Do NOT put hidden/rotating evaluation cases here.

## Performance & security constraints
- **Security model (encode it):** the TS runtime is UNPRIVILEGED; ALL privileged FS mutation (reading `/var/lib`,
  writing the target, the restore rename-swap) belongs ONLY to the narrow Go `agent`. agentd acts ONLY from a
  re-validated typed request (validated source-root list, validated absolute target path) — NEVER from raw runtime
  text; unknown/invalid ⇒ fail-CLOSED reject. The capability is a CLOSED typed op set; arbitrary commands rejected.
- **No secrets in plaintext backup metadata:** the backup MANIFEST (paths, digests, sizes, modes, ids) must contain NO
  inline key/secret material — reuse `backup.go`'s `containsInlineSecretMaterial` scanner on every string field that
  enters the manifest, and reject a request that would embed secret material in metadata. (File CONTENT bytes are
  backed up as opaque hashed blobs — they are not metadata; do not scan/transform payload bytes, just hash+store them.)
- **NO real keys / TPM / recovery keys** — owner-held (§16). Use TEST data only; never generate or commit production
  key material. NO encryption this slice (non-goal) — but NO plaintext secrets in the metadata as above.
- **Integrity:** content-addressed (SHA-256); restore VERIFIES before applying; tamper/bit-rot detected and refused.
- **Atomicity / single commit point (R3, AGENTS.md §2):** create and restore each use a fresh O_EXCL temp →
  Sync/Close → Rename as the SINGLE commit point; no fallible step after the irreversible effect; exactly two outcomes
  (success + working Undo, or error with the live tree UNCHANGED) — never mutated-but-reported-failed. Prove it.
- **Fail-closed, never throw at the trust boundary:** validators over the request handle malformed/cyclic/partial
  shapes by REJECTING, not crashing. No remote imports; vendored deps only; offline; no package lifecycle scripts.
- Determinism: the manifest serialization is canonical so the same source tree yields the same content-addressed id.
- R3 (privileged TCB FS mutation of authoritative data) → reviewer gate (`npm run review -- P1-066`) before merge.
