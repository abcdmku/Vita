## Objective
Remove the placeholder value-guard in the desktop host bridge and replace it with a **real structural guard**, so a genuine backend `registerComponent` response is accepted instead of being discarded as malformed.

Today `ui_kits/desktop/runtime/host-bridge.ts:1020` is a hardcoded stub:
```ts
function isRegisteredShellComponent(_value: unknown): _value is RegisteredShellComponent {
  return false;
}
```
This guard is passed at `:232` to `forwardShellResult(request, "registerComponent", [definition], isRegisteredShellComponent)`. Inside `normalizeHostResult` (`:705`) the `valueGuard` is applied to every `ok: true` backend response; because this guard ALWAYS returns `false`, the `ok: true` branch falls into the malformed path and returns `HOST_BRIDGE_MALFORMED_RESPONSE` at `/registerComponent/value`. Net effect: even with a real backend wired, `registerComponent` can NEVER succeed across the bridge.

- Implement a real structural guard mirroring the sibling guards in the same file (`isShellManagedSnapshot` `:1072`, `isTrayItem` `:986`, `isPlacement` `:1159`). A value is a `RegisteredShellComponent` (shape at `sdk/typescript/src/shell/index.ts:132`) when it is a JSON object with `id: string`, `role: string`, and `defaultPlacement` satisfying `isPlacement(...)`. Reuse the existing `jsonObject(...)` and `isPlacement(...)` helpers; do NOT invent a new placement check.
- A well-formed `ok: true` response now normalizes to `{ ok: true, value }`; malformed values (wrong/missing `id`/`role`, non-placement `defaultPlacement`, non-object) still fail closed as `HOST_BRIDGE_MALFORMED_RESPONSE`.
- Change ONLY the guard body. Do NOT alter `forwardShellResult`, `normalizeHostResult`, the wiring at `:232`, or any other guard.
- Put the test under `sdk/typescript/test/ui-kits/host-bridge-register-component.test.ts`. Import the bridge exactly as the existing desktop tests do; drive it through the public `registerComponent` path with a fake backend port (no platform internals, no DOM/CEF).

## User value
Unblocks a real desktop capability: with the placeholder gone, a wired backend can actually register shell components instead of every valid response being rejected as malformed — the bridge now reflects real host behavior.

## Non-goals
- NO DOM/CSS/rendering/CEF. NO platform internals. No new placement/snapshot semantics — reuse `isPlacement`. Do NOT touch other guards, `forwardShellResult`, or `normalizeHostResult`. No backend implementation work beyond the guard.

## Acceptance
`acceptance_command` passes. The new deterministic test, at the EXACT path `sdk/typescript/test/ui-kits/host-bridge-register-component.test.ts`, MUST prove the placeholder is gone and real behavior is present:
- Asserts a backend `ok: true` response carrying a structurally valid `RegisteredShellComponent` (`id`/`role` strings + a valid `defaultPlacement`) now resolves SUCCESSFULLY through `registerComponent` and returns that real value — this case fails against the hardcoded `return false` stub and passes only with the real guard.
- Asserts malformed `ok: true` responses (missing/non-string `id`, missing/non-string `role`, non-placement `defaultPlacement`, non-object value) still fail closed with `HOST_BRIDGE_MALFORMED_RESPONSE` at `/registerComponent/value`.
- No hardcoded sample component is returned by the bridge; the resolved value is exactly the injected backend value. `typecheck` clean.

## Security/constraints
- Injected ports only (no ambient I/O); capability-mediated, fail-closed; pure/deterministic guard. No remote imports; lockfile; no lifecycle scripts.

## Rollback plan
Single-file, single-function change: revert the `isRegisteredShellComponent` body back to `return false` and delete the new test file; no schema, wiring, or data migration involved.

## Definition of done
- `ui_kits/desktop/runtime/host-bridge.ts` `isRegisteredShellComponent` is a real structural guard (no `return false` placeholder) + `sdk/typescript/test/ui-kits/host-bridge-register-component.test.ts`, deterministic, typecheck clean, acceptance green. R1.
