## Objective
Implement node **capability discovery** for the Go agent (spec FR-004 "Discover CPU, RAM, storage,
networking, GPU, NPU, TPM, and virtualization capabilities"; §6, §14). Provide:
1. `agent/hardware/capabilities.go` — a typed, JSON-serializable `Capabilities` struct: CPU (arch,
   cores, model), memory (totalMiB), storage devices (name, sizeMiB, rotational/nvme), networking
   (interfaces: name, kind), TPM (present, version), virtualization (hardware bool), and accelerators
   (mirror the SDK accelerator kinds: nvidia.cuda/intel.npu/amd.npu/amd.rocm/intel.gpu/cpu — discovery
   may return an empty/cpu-only list when none detected). A `Discoverer` interface
   `Discover(ctx) (Capabilities, error)`.
2. `discover_linux.go` (`//go:build linux`) — a real Linux discoverer parsing `/proc/cpuinfo`,
   `/proc/meminfo`, `/sys/block/*`, `/sys/class/net/*`, `/sys/class/tpm*`, and CPU virtualization
   flags. **Read-only**: only reads procfs/sysfs; NO shell, NO `os/exec`, NO writes.
3. `discover_stub.go` (`//go:build !linux`) — a stub returning a typed "unsupported platform" error so
   the package compiles everywhere; the container acceptance exercises the Linux path.
4. Parse helpers must be **pure + table-tested against fixture strings** (sample /proc/cpuinfo,
   /proc/meminfo content) so logic is proven deterministically without depending on the container's
   exact hardware.

## User value
Capability discovery drives placement, certification, and the TypeScript capability snapshot (spec
§6, §8.2, §14). It must be accurate and side-effect-free (read-only).

## Non-goals
- No registration into the privileged capability registry that mutates anything (discovery is
  read-only); wiring it as a read-only capability is fine but optional.
- No GPU/NPU vendor SDKs; detect by PCI/sysfs presence only (best-effort, CPU-always-present).

## Acceptance tests
`acceptance_command` (go test in golang:1.26 — a Linux container, so the linux discoverer compiles and
runs). Also `go vet ./...` clean. Tests must prove:
1. CPU/mem parse helpers produce the expected `Capabilities` fields from fixture `/proc` strings
   (table-driven, deterministic).
2. `Discover` on Linux returns a populated `Capabilities` (arch set, memory > 0, ≥1 CPU) without error

3. Malformed/empty fixture input is handled fail-closed (no panic; returns a typed error or safe
   zero-with-error), never crashes.

## Reviewer revision (round 2 — BLOCKING, from P1-005.review.md)
1. **Accelerator entries must be SDK §14.1-valid or not emitted.** Do NOT put `nvidia.cuda`/`intel.npu`/
   `amd.npu`/`amd.rocm` into the typed `accelerators []AcceleratorCapability` list without their
   required fields (`memoryGB`/`compute`/`generation`) — that yields a snapshot the TS validator
   rejects. Fix: the typed `accelerators` list contains ONLY entries with all required fields populated
   from sysfs (CPU is always valid; include a GPU/NPU only if you can fill its required fields).
   Detected-but-undetailed PCI devices go in a SEPARATE optional `detectedDevices` list (e.g.
   `{ class, vendorID, deviceID }`) that does NOT masquerade as the §14.1 union. Add fixture tests for
   each emitted accelerator kind (or proving GPU/NPU kinds are omitted unless valid).
2. **No arbitrary-read surface (R3 TCB).** Don't expose caller-injectable arbitrary path fields on the
   production discoverer — a constructor must read FIXED `/proc` and `/sys` roots. Make any root
   override unexported / test-only (e.g. an unexported field set by a test helper), so production
   callers cannot turn discovery into an arbitrary-file-read primitive. Constrain reads to the
   documented procfs/sysfs subtrees.
