## Objective
`previewServicesChange(current, desired)` (controller/services): given current + desired `ServicesConfig`
(the P0-028 SDK model), validate BOTH via `validateServicesConfig`, then compute a typed, fail-closed
**change diff** WITHOUT applying: services `enabled` (newly present+enabled OR flipped false→true),
`disabled` (flipped true→false), `added` (name new to desired), `removed` (name gone from desired), keyed
by service name. Surface `newlyEnabledCount` (how many services this change turns ON — a privilege-relevant
signal the operator should see). Return `{ valid, diff, newlyEnabledCount, rejections }`. Fail-closed:
invalid either side ⇒ typed rejection, no diff, never a throw.

## User value
The management-plane "what will this services change do" view (FR-007/006) — shows which services get
enabled/disabled/added/removed and how many are newly turned ON, on validated inputs only.

## Non-goals
- No real systemctl, no agent call, no network. Validate + diff only. Do NOT modify the P0-028
  `services-model`; import it.

## Dependencies
P0-028 (services model: validateServicesConfig), P0-015. Merged.

## Acceptance tests
`acceptance_command` — `services-preview.test.ts`: identical configs ⇒ empty diff, `newlyEnabledCount` 0;
enabled/disabled/added/removed services ⇒ correctly classified; a service flipped false→true ⇒ counted in
`newlyEnabledCount`; invalid current OR desired ⇒ typed rejection (no diff, no throw); hostile input ⇒
fail-closed (external-counter accessor probe). Orchestrator also runs `npm run typecheck`.

## Performance & security constraints
Deterministic, no I/O/network. Fail-closed (reuse `validateServicesConfig`; never throw).
`newlyEnabledCount` correct. Strict TS (no `any`). R2 → reviewer-gated.
