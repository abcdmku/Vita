## Objective
**Storage durability, slice — finish the spec Phase-3 "TPM key sealing on x86" + "Recovery-key flow" deliverables (spec
§21 Phase 3, §10.2 "TPM-assisted unlock on supported systems" + "Offline recovery key", §11/§10.4 FR-015).** P1-068
landed the LUKS2 data-volume mechanism end-to-end with the unlock-key resolver's two privileged sources — **TPM-sealed
slot** and **N-of-M recovery key** — left as inert `# OWNER WIRES §16` STUBS
(`os/x86_64/verity-overlay/usr/lib/vita/luks/vita-data-unlock.sh`, `unsupported_tpm()` / `unsupported_recovery()`; only
the build-only TEST keyfile actually unlocks). This slice **implements both sources for real, on a TEST TPM**, exactly as
Secure Boot proved enforcement with a TEST db key (`tools/secureboot-test-keys.sh`) and dm-verity proved root integrity
on a TEST cert: prove the MECHANISM with throwaway TEST material, keep the seam for the owner's real §16 secrets.

Concretely:
1. **TPM-sealed auto-unlock (real, swtpm-backed).** Enroll a LUKS2 keyslot on the `vita-data` container that is sealed to
   the TPM so a *trusted boot* unseals it with no human input. Use `systemd-cryptenroll --tpm2-device=auto` (present on
   the build host) against a software TPM (swtpm, attached to the QEMU guest as `tpm-tis`/`tpm-crb`; the host has
   `qemu-system-x86_64 -device tpm-tis`). Bind the seal to a documented, STABLE PCR policy that does NOT change across
   ordinary reboots of the same image (choose + DOCUMENT the PCR set; e.g. firmware/bootloader/kernel-measuring PCRs —
   justify the choice and why a benign reboot still unseals while a changed boot would not). The TPM enrollment is added
   to the LUKS image **at build time, behind the existing `VITA_LUKS=1` gate** (extend the `build-and-boot.mjs`
   post-format step that already does `luksFormat`/`luksOpen` — see `luksFormatDataPartition()`): after the TEST keyfile
   slot exists, also `systemd-cryptenroll` a TPM2 slot (against the build-time swtpm state that the QEMU boot then
   re-presents) and the recovery slot (step 2). Replace `unsupported_tpm()` in `vita-data-unlock.sh` with a real TPM
   unseal path (`systemd-cryptsetup`/`cryptsetup open --token-only` / `--tpm2-device`, or a `systemd-cryptenroll`-managed
   token); it must FAIL CLOSED (no plaintext fallback) if the TPM is absent, the policy does not satisfy, or the slot is
   missing — falling through to the recovery source, never to plaintext.
2. **N-of-M offline recovery flow (real).** Implement the owner-recovery path that recovers the volume when the TPM/sealed
   state is lost. M offline recovery **shares** are generated as TEST material (gen-once, gitignored — mirror
   `tools/luks-test-keys.sh`); presenting **any threshold-of-M** shares reconstructs the recovery passphrase that opens a
   dedicated LUKS recovery keyslot. The combine/validate logic lives in the agent (`agent/capabilities/storage/recovery.go`)
   as a pure, fail-closed N-of-M validator+combiner that mirrors the SDK quorum semantics already proven in P0-021
   (`sdk/typescript/src/recovery-key.ts`: threshold ≤ shares, distinct presented shares satisfy the quorum, below-quorum
   REJECTS, secrets-as-references at the model boundary). The on-device `recovery-unlock.sh` calls into the agent
   combiner (or a vendored equivalent) ONLY from re-validated inputs (never raw runtime text), reconstructs the recovery
   passphrase, and `cryptsetup luksOpen`s the recovery slot. **Fewer than threshold shares MUST FAIL CLOSED** (no unlock,
   no plaintext). NO real recovery secret is generated, escrowed, or shipped — TEST shares only; the owner provisions the
   real N-of-M material (§16). Replace `unsupported_recovery()` in `vita-data-unlock.sh` with this real path.
3. **Resolver order + fail-closed (unchanged contract from P1-068).** `vita-data-unlock.sh` resolves in the documented
   order **TPM-sealed → recovery → TEST keyfile** (the TEST keyfile source stays BUILD-ONLY under `VITA_LUKS=1`, absent
   from a release image). The resolver remains CLOSED: if no source yields a valid key, the unlock FAILS and `/var` does
   NOT mount on a plaintext fallback (the P1-068 `var.mount` `Requires=`/`BindsTo=`/`What=/dev/mapper/vita-data` hard
   dependency is preserved — never weaken it to a soft `Wants=`/by-label fallback).
4. **MEASURED marker (the P1-055/P1-068 lesson — never synthesized).** Replace P1-068's `tpm=stub recovery=stub` marker
   with one emitted ONLY after REAL on-device checks: (a) **sealed=OK** — on a good boot the mapper opened via the TPM
   token (the unlock log shows the TPM2 source resolved + opened, NOT the TEST keyfile fallback); (b) **recovery=OK** — a
   threshold set of TEST recovery shares opens the recovery slot (exercised on-device on a SECOND boot path or by the
   marker driver presenting the shares; MEASURED by a real `luksOpen` of the recovery slot, not asserted); (c)
   **wrong-key=fail-closed** — a below-threshold/wrong share set is REALLY refused by `cryptsetup` and `/var` does NOT
   mount plaintext. Marker:
   `VITA-TPM-SEAL: sealed=OK recovery=OK wrong-key=fail-closed status=OK`;
   fail path `VITA-TPM-SEAL-ERROR: reason=<specific step+errno> status=FAILSAFE`. Keep the P1-068 `VITA-LUKS:` marker AND
   all prior markers; `VITA-LUKS` may now read `tpm=OK recovery=OK` (the stubs are gone).

This is the MECHANISM only, on TEST TPM + TEST shares. **The real TPM provisioning + the real N-of-M recovery secrets are
OWNER-HELD (spec §16); NEVER generate, escrow, or commit production key material.**

## User value
The node auto-unlocks its encrypted authoritative data on a *trusted* boot with no human present (TPM-sealed, spec §10.2
"TPM-assisted unlock on supported systems"), AND the owner can still recover that data after catastrophic TPM/state loss
via an offline N-of-M recovery key (spec §10.2 "Offline recovery key", §10.4/FR-015 recovery flow) — while a tampered or
untrusted boot, or a below-quorum recovery attempt, fails CLOSED and discloses nothing (spec §16 "Vendor cannot decrypt
local disks"). Landing both sources for real (on TEST material) completes the encryption-unlock story P1-068 stubbed and
clears two of the Phase-3 deliverables, leaving only the owner's real-secret provisioning.

## Non-goals
NO real TPM provisioning and NO real recovery-secret generation/escrow — those are owner-held §16 secrets (TEST swtpm +
TEST shares only; nothing production generated or committed). NO Shamir-secret-sharing *cryptographic* hardening claim
beyond a correct, fail-closed N-of-M combine on TEST material (the owner's real scheme may differ; the seam + the
quorum semantics are what this slice fixes). NO TPM PCR-policy *rotation*/re-seal-after-update UX, NO key-rotation/
`luksAddKey` operator UX, NO `luksKillSlot` lifecycle (later slices). NO Btrfs/snapshots/quotas (separate Phase-3 slices).
NO ARM/Pi TPM (x86_64 only; the Pi flow is separate). NO change to the dm-verity RO root or the Secure Boot chain beyond
reading PCRs for the seal policy. NO controller/UI for recovery (the agent validator + on-device flow only). The plain
smoke image and non-LUKS verity image stay byte-compatible (everything gated behind `VITA_LUKS=1`).

## Performance & security constraints
TPM-sealed source is the unattended default; recovery is the owner's break-glass; the TEST keyfile is BUILD-ONLY
(`VITA_LUKS=1`, never in a release image). FAIL-CLOSED everywhere: a missing/wrong-policy TPM, a below-quorum recovery
attempt, or any source failure → `/var` does NOT mount on a plaintext fallback; the marker is MEASURED, never
synthesized; specific step+errno on failure. The unlock service + the agent combiner are the only privileged actors; they
compose every `cryptsetup`/`systemd-cryptenroll` invocation from FIXED, code-controlled args + the resolved key/passphrase
— NEVER from raw runtime-supplied text (the security model: the unprivileged TS runtime never performs privileged
mutation; privileged mutation is only the narrow Go agent acting on a re-validated manifest/input). Secrets-as-references
at the model boundary (§13.1): the agent combiner rejects structures embedding literal share/key material. TEST TPM
(swtpm) + TEST shares are THROWAWAY, host-local, gitignored, NEVER shipped, EXCLUDED from reproducibility (spec §16:
signing/TPM/recovery secrets unavailable to dev agents — TEST material only). LUKS2 only. No remote imports; lockfiles
mandatory; no package lifecycle scripts; no FFI/native addons in TS; no network. R3 (boot/storage/identity — privileged
TCB) → **reviewer gate** (`npm run review -- P1-089`) + independent orchestrator host-verify before merge.

## REVISION 2 (Codex R3 review: REVISE — 5 blocking incl. a security hole — 2026-06-24)

   image and each share carries the FULL recovery passphrase, so the recovery slot is unlockable from material BAKED into
   the root. FORBIDDEN: offline recovery shares are HOST-LOCAL / owner-presented at recovery time, NEVER shipped in the

   unrelated swtpm.

   absent on the host. Use swtpm so the seal/unlock is genuinely proven.
4. **agent/on-device parity.** The on-device recovery combiner uses a separate, WEAKER shell ref-validator than
   `agent/capabilities/storage/recovery.go`. Use the Go combiner/validator (or an equivalent that matches it exactly) so
   secrets-as-references validation is identical on both paths.
5. **tpmseal verify-mode must require the FULL prior chain.** wsl-verify `tpmseal` mode PASSes on just seal+luks markers;
   it MUST also require the TS/EVAL/APPLY/CAPSULE/NET/... chain still passes on the same boot.
Keep: TEST keys/swtpm only, no real secrets, owner wires real (section 16). Verify: QEMU+swtpm boot — TPM-sealed
auto-unlock on good boot, recovery via host-presented shares (NOT baked), wrong/absent fails closed, prior chain still
