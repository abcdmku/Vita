## Objective
Implement the agent's **transactional apply engine** (spec §8.2 steps 8–9 "applied transactionally
through the Go agent … rolled back if health checks fail"; FR-007 "Apply plans transactionally and
roll back failed changes"). This is the privileged core that turns a validated desired-state plan into
host changes safely. Provide (`agent/transaction/engine.go`):
- A typed `Plan` = ordered `[]Operation`, where each `Operation` names a **transactional capability**
  and carries a typed request. A `TxCapability` interface extends the base capability with
  `Apply(ctx, req) (Undo, error)` returning a **compensating `Undo`** action, and the engine collects
  Undos.
- `Apply(ctx, reg *capabilities.Registry, plan Plan, health HealthCheck) Result`:
  1. **Atomic precondition check** — verify EVERY operation's capability is registered AND transactional
     BEFORE applying anything; if any is unknown/non-transactional, reject the whole plan (apply
     nothing). Fail-closed.
  2. Apply operations in order, recording each successful `Undo`.
  3. On ANY apply error OR a failing post-apply `health` check, **roll back**: invoke the recorded
     Undos in REVERSE order; report which rolled back (and any rollback errors).
  4. Return a typed `Result` (applied ops, committed|rolledBack, errors). Deterministic, no partial
     commit left behind.
- NO shell / `os/exec` / arbitrary command. Undo is a typed compensating action, not a command string.

## User value
Transactional apply with rollback is what makes TypeScript-declared changes safe to apply to a real
host (spec §3.3, §8.2, §16 reliability — "automatic rollback after failed … health check"). It is the
heart of the privileged agent.

## Non-goals
- No real host operations (capabilities are provided/mocked by the caller/tests); this is the ENGINE.
- No persistence/journal to disk yet; no concurrency across plans.

## Dependencies

## Acceptance tests
`acceptance_command` (go test in golang:1.26) + `go vet` clean. Tests must prove:
1. A plan whose ops all succeed and whose health check passes **commits** (all applied, no rollback).
2. A plan where the Nth op fails **rolls back** ops 1..N-1 in reverse order (assert Undo call order),
   leaving nothing committed.
3. A plan that applies but then **fails the post-apply health check** rolls back everything.
4. **Atomic precondition:** a plan referencing an unknown/non-transactional capability applies NOTHING
   and returns a typed rejection (fail-closed).
5. A rollback whose Undo itself errors is reported (not swallowed, no panic).

## Performance & security constraints
TCB component. NO shell/`os/exec`/arbitrary surface. Fail-closed precondition; no partial commit
without rollback. `go vet` clean. Deterministic (no real time/IO in the engine; health check is an
injected func). R3 → reviewer-gated, extra scrutiny on rollback correctness + no-partial-commit.
