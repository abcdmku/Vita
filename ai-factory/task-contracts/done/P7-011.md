## Objective
A NEW end-to-end LIFECYCLE scenario test `agent/transport/lifecycle_scenario_test.go` that exercises the
ASSEMBLED agent (the wired handler with multiple capabilities + the audit store) through a realistic
multi-step SEQUENCE — proving the subsystems work TOGETHER, beyond the existing per-feature unit tests. Build
the handler via the existing test helpers (injected facades for ≥3 representative capabilities + a real
in-memory `auditlog.Store`). Then drive, asserting after EACH step:
1. `GET /operations` lists the registered ops; `GET /state` reflects the initial (absent/default) state.
2. `POST /apply` a valid plan to capability A ⇒ committed; `GET /read/A` returns the new config (canonical);
   `GET /state` now includes A's config; `GET /audit` has exactly ONE committed event for A (sequence 1).
3. `POST /apply` to capability B ⇒ committed; `/state` includes both A and B; `/audit` has TWO events
   (sequences 1,2, strictly monotonic, correct capabilities/outcomes), order stable.
4. A `POST /apply` that ROLLS BACK (a later-op/health failure) ⇒ the response reflects rolled_back, the live
   state of the targeted capability is UNCHANGED (no third state), and `/audit` records a rolled_back event.
5. A pre-transaction-REJECTED `POST /apply` (fails Validate) ⇒ 4xx, NO state change, and (per P7-006) NO new
   audit event (rejected-before-transaction is not recorded).
Assert the audit trail is strictly monotonic across the whole scenario and `/state` is byte-stable.

## User value
Confidence that the assembled control-plane agent behaves correctly as a SYSTEM (FR-004/008/§17) —
apply→read→state→audit cohere across capabilities, provenance accumulates monotonically, and rollback/
rejection leave no untracked state — not just that each piece passes in isolation.
