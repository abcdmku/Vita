## Objective
A transactional capability `agent/capabilities/identity/` that stores the node's **identity attestation**
— its DID, handle, and a signing-key REFERENCE (the proof) — to a FIXED agent state path, applied
atomically with rollback. Same proven pattern as nodeconfig (P1-007): `Handle` reads the current
attestation; `Apply` validates a desired attestation and writes it via a single atomic commit point
(temp + rename — nothing fallible after the rename), returning an `Undo` that restores the prior bytes.
Integrate with the transaction engine (commit + rollback proven). Injected FS facade for tests.
- **Validate** the DID (`did:plc:`/`did:web:` well-formed) and handle (domain-style label), mirroring the
  P5-001 SDK rules. Reject malformed fail-closed.
- **Secrets-as-references (§13.1)**: the attestation references the signing key by id/handle — REJECT any
  attestation that embeds literal key material (PEM/seed/private-key/long blobs).
- No `os/exec`, no network, no DID resolution. Fixed state path (never request-supplied).

## User value
The node's persisted, transactionally-managed identity (FR-016) — the on-host half of the identity model
(P5-001) that the PDS/controller will read. Proves the capability pattern generalizes to identity.

## Non-goals
- No real crypto/DID resolution/network/PDS. No `cmd/agentd/main.go` edits (registration is a follow-up).
  Store + validate the attestation only.

## Dependencies
P1-006 (engine), P1-007 (atomic-file capability pattern), P5-001 (identity syntax rules). All merged.

## Acceptance tests
`acceptance_command` (go test in golang:1.26) + orchestrator `go vet`. Cover: Handle reads current;
Apply writes + restoring Undo; transaction commit; transaction rollback (later op fails ⇒ prior
attestation restored); malformed DID/handle rejected without writing; embedded key material rejected
(§13.1); atomic-write-failure leaves the live file unchanged (single commit point). Injected FS; no real
disk mutation.
