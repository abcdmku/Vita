## Objective
Give the agent a **local control surface** the controller can call (spec §7 controller↔agent, §8.2
apply path, FR-008 status). An `http.Handler` (`agent/transport/server.go`) exposing:
- `GET /healthz` — read-only status (from P1-004 status).
- `GET /capabilities` — discovered node capabilities (from P1-005), read-only.
- `POST /apply` — accept a typed plan (JSON body), **validate it fail-closed**, run it through the
  transaction engine (P1-006), and return a typed result (committed | rolled-back + errors). Wire
  `cmd/agentd/main.go` to serve this handler bound to **loopback only** (127.0.0.1 or a unix socket) —
  NEVER a public interface (spec §12.1 default-deny inbound).

**Trust boundary — full fail-closed + intrinsic-safe (per AGENTS.md), because /apply takes untrusted
JSON:**
- Decode the body into typed Go structs with a strict decoder (reject unknown fields:
  `Decoder.DisallowUnknownFields`); reject malformed/oversized/exotic bodies with a typed 4xx error,
  never a panic. Bound the request body size.
- The plan's operations may only name registered transactional capabilities and carry typed requests;
  the engine's atomic precondition already rejects unknown ones — surface that as a clean 4xx, apply
  nothing. Request data NEVER becomes a file path or command.
- No `os/exec`/shell anywhere. No auth yet (loopback trust); document that as a known gap.

## User value
This is how a declared plan actually reaches the host: controller → loopback → agent validate → apply
→ rollback-on-failure (spec §8.2, FR-007). Read endpoints give the UniFi-style status (FR-008).

## Non-goals
- No real network/TLS/auth/identity; loopback only. No RPC/protobuf (typed JSON for now).
- No new capabilities; uses the registry + engine + discovery already built.

## Reviewer revision (round 2 — BLOCKING, from P1-008.review.md)
**Reject INCOMPLETE typed requests at the boundary, before any transaction work.** Strict JSON decode
(DisallowUnknownFields) is not enough: `{"desired":{"mode":"normal"}}` decodes with `remoteAccess == ""`
and currently reaches `transaction.Apply`, failing INSIDE the op — so an incomplete request returns a
rolled-back result instead of a clean 4xx, and a valid op preceding an incomplete one gets
applied-then-rolled-back. That violates the AGENTS.md fail-closed rule (partial/incomplete input must be
rejected, not partially honored). Fix:
- Give each capability's request type a `Validate() error` (for nodeconfig: require a non-empty, valid
  `mode` AND `remoteAccess` — surface the validation that currently lives inside `Apply`). Adding this
  small method in `agent/capabilities/nodeconfig/` is in-scope.
- In the transport `/apply` handler, after decoding, run a PRE-TRANSACTION validation pass over ALL ops:
  if ANY op's typed request is incomplete/invalid, return a typed **4xx and apply NOTHING** — do not call
  `transaction.Apply` at all. Only fully-valid plans proceed to the engine.
- Regression tests: (a) `{"desired":{"mode":"normal"}}` (missing `remoteAccess`) ⇒ 4xx, nothing applied;
  (b) a VALID op followed by an INCOMPLETE op ⇒ 4xx, nothing applied (the valid op must NOT be
  applied-then-rolled-back). Keep the existing loopback/no-exec/strict-decode behavior (reviewer approved).
