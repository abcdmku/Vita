## Objective
A transactional capability `agent/capabilities/pdssync/` that stores the node's **PDS sync state** (the
on-host counterpart to the SDK P5-003 PDS model) to a FIXED agent state path, applied atomically with
rollback — the proven nodeconfig (P1-007) pattern. A typed `SyncState` = repo DID + cursor (monotonic)
+ repo head CID. `Handle` reads current; `Apply` validates a desired sync state and writes via a single
atomic commit point (temp + rename — nothing fallible after the rename), returning a restoring `Undo`;
commit + rollback proven through the engine. Implements `Validate()` for the transport gate. Injected FS
facade for tests.
- **Validate fail-closed** (mirror P5-003 §): repo DID (did:plc/did:web) well-formed; cursor a
  non-negative monotonic value; head CID a well-formed CIDv1; reject a cursor that REGRESSES below the
  current stored cursor (monotonic invariant — sync state never goes backwards). Absent required field ⇒
  reject (not defaulted). No `os/exec`, no network, no real PDS sync.

## User value
The on-host PDS sync checkpoint (FR-018) the agent persists transactionally — repo head + monotonic
cursor, so a crash/rollback never loses or regresses sync position. Real repo sync is a later contract.

## Non-goals
- No real PDS/network/repo sync, no MST/merkle, no crypto. Store + validate the sync state only. No
  `os/exec`. No `cmd/agentd/main.go` edits (wiring is a follow-up).

## Reviewer revision (round 2 — BLOCKING, from P5-004.review.md)
1) **Duplicate-JSON-key TCB hazard** (now an AGENTS.md rule): stored JSON is decoded last-wins and
   `Handle` returns the raw bytes, so `{"repo":"-----BEGIN PRIVATE KEY-----","repo":"did:plc:..."}`
   validates on the clean last value but smuggles the PEM in the raw bytes. REJECT requests with
   duplicate object keys before decoding, AND persist + return the RE-SERIALIZED canonical form of the
   VALIDATED struct, never the raw input. Add regressions (duplicate key ⇒ reject; PEM-via-duplicate-repo
   not present in stored/returned bytes).
2) **Monotonic check has a read-validate-write race.** Two concurrent `Apply` calls can both validate
   against cursor `100` then write `200` then `150`, regressing the live cursor. Serialize the
   read-validate-write (a `sync.Mutex` guarding `Apply`, or an atomic compare-and-replace facade) so the
   monotonic check holds against the CURRENT committed state at write time. Add a concurrency regression:
   two interleaved applies never leave a regressed stored cursor.
(Also fix the misleading `tryErrorAfterCommit` test so it actually exercises the post-commit class.)

## Reviewer revision (round 3 — BLOCKING, from P5-004.review.md round 2)
(Round-2 dup-key + concurrent-cursor fixes are approved — keep them.)
1) **Undo must restore the EXACT original prior file bytes, not a canonicalized form.** Round 2
   canonicalizes the prior snapshot before storing it in the undo record, so rolling back a valid-but-
   non-canonical prior file restores reserialized bytes — violating the R3 rule that an error path leaves
   the live system byte-for-byte unchanged. Read the prior bytes AS-IS, parse a COPY for the cursor/
   validation checks, but store the ORIGINAL prior bytes in the Undo. (Only the NEW desired state being
   written is canonicalized.) Add a regression: a non-canonical valid prior + a later op failure ⇒ the
   live file is restored to the EXACT original bytes.
2) **Reject non-canonical base32 in CIDv1** (mirror P5-003). Round 2's base32 decode ignores non-zero
   unused trailing bits, so non-canonical CID strings (e.g. `…sidfwz`/`…sidfw2`/`…sidfw3` vs the canonical
   `…sidfwy`) decode to the same bytes and pass `isCIDV1Bytes`, accepting malformed CIDs that P5-003
   rejects. Use the SDK's explicit base32 decoder / trailing-bit check; reject any non-canonical encoding.
   Add a regression for a trailing-bit CID variant.
