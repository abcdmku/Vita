## Objective
A pure, standalone SDK type model + fail-closed validator for backup/restore and recovery-key
enrollment (spec §10.3/§10.4, §11, FR-015). `backup-model.ts` exports the types (`BackupPolicy`,
`BackupTarget`, `RestorePlan`, `RecoveryKeyEnrollment`, `RecoveryKeyRef`, etc.) and validators
(`validateBackupPolicy`, `validateRecoveryKeyEnrollment`) that fail-close on untrusted input. NEW
validator ⇒ use `safeNormalize` for the boundary, then validate structure on the trusted plain value.
**Secrets-as-references only** (spec §13.1): recovery keys/material are referenced by id/handle, never
embedded literally — reject any enrollment that inlines key material. Standalone module — no shared
barrel/index edits.

## User value
The typed contract for the recovery-key + backup flows the storage/identity layers will implement
(FR-015). Encodes the secrets-as-references invariant at the SDK boundary.

## Non-goals
- No crypto, no real key generation/storage, no agent code. Types + pure validators only. No shared-index edits.

## Dependencies
P0-015 (`safeNormalize`) — merged.

## Acceptance tests
`acceptance_command` — `backup-model.test.ts` covers: valid backup policy + recovery-key enrollment

## Reviewer revision (round 2 — BLOCKING, from P0-020.review.md)
§13.1 secrets-as-references must validate the reference VALUES, not just reject forbidden field NAMES.
`recoveryKeyRef.handle`/`recoveryKeyRef.id` (and EVERY `*Ref` field, e.g. `credentialRef`) must be
rejected if they embed literal key material — detect PEM blocks (`-----BEGIN`), private-key/seed-phrase
patterns, and long base64/hex blobs over a length bound — and must match an opaque reference syntax
(id/handle shape), not raw secret bytes. Add regression tests that embed real-looking key material
inside `recoveryKeyRef.handle`/`id` (and another `*Ref`) and assert rejection. Also tighten
`validateRequiredDateTime` to a real ISO-8601 check (not any `Date.parse`-able string) and drop the
unused `PlainJsonObject` import.
