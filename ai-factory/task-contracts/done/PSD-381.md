## Objective
Wire the EXISTING `LockAuthPort` (`ui_kits/desktop/viewmodels/Lock.ts:63`) to the agent's
owner-passkey capability (`agent/capabilities/owner/webauthn.go`, op `webauthn.get`) through the
SDK host, so the flagship desktop's Lock screen can authenticate the local owner against a real
agentd assertion instead of an injected stub.
- Extend the public `DesktopHost` surface (`sdk/typescript/src/desktop-sdk/ui-package.ts:123`)
  with `authenticateOwner(request): DesktopMaybePromise<DesktopHostResult<OwnerAuthSession>>`,
  gated on a NEW `"owner.auth"` member of `DesktopCapability`
  (`sdk/typescript/src/desktop-sdk/ui-package.ts:25`). Plain-JSON in/out, fail-closed.
- The host-proxy impl in `sdk/typescript/src/desktop-sdk/loader.ts` MUST check the grant with the
  existing `hasDesktopCapabilityGrant(manifest, "owner.auth", …)` pattern and, when present, call
  an injected agentd transport double for `webauthn.get`, then map the agent's reply to an
  `OwnerAuthSession`. Missing grant → `hostReject("MISSING_CAPABILITY", …)` (the established
  fail-closed path), NOT a throw.
- Add a thin adapter that satisfies `LockAuthPort` by delegating `authenticate(request)` to
  `host.authenticateOwner(...)` and normalizing the result to a `LockAuthSession`
  (`ui_kits/desktop/viewmodels/Lock.ts:49`) on success / a `LockViewModelError`-shaped reject on
  failure.
- Request/assertion shapes MIRROR `webauthn.go`: the challenge carries `clientDataJSON`
  (`{ type: "webauthn.get", challenge, origin }`), `authenticatorData`, and `signature` (the exact
  trio `verifyWebAuthnAssertion` consumes at `webauthn.go:103`). Do NOT verify signatures in TS —
  the SDK only marshals the request and trusts agentd's verdict (fail-closed on a non-ok verdict).
- Export the new types (`OwnerAuthSession`, request type, the adapter factory) from
  `sdk/typescript/src/desktop-sdk/index.ts`. Consume ONLY public SDK exports + the existing
  Lock view-model port types.

## User value
The desktop Lock screen authenticates the LOCAL owner with a real passkey assertion verified by
agentd, closing the gap between the headless Lock view-model and the on-device owner identity —
the privileged-action gate the OS already enforces server-side (P1-069 / webauthn.go).

## Non-goals
- NO DOM/CSS/rendering/CEF. NO crypto/signature verification in TS (agentd owns that). NO new
  WebAuthn algorithms, NO credential ENROLLMENT (assertion/get only). NO real socket/network I/O
  in this slice — the agentd transport is an injected dependency; tests use a stub transport
  double. Do NOT re-implement the Go capability or the Lock view-model — bind to them.

## Acceptance
`acceptance_command` passes. Deterministic unit tests in
`sdk/typescript/test/ui-kits/owner-auth-port.test.ts` cover, against a stub agentd transport
double, all four cases:
1. **accept** — transport returns an ok `webauthn.get` verdict → `authenticateOwner` resolves
   `{ ok: true, value: OwnerAuthSession }`; the adapter yields a valid `LockAuthSession`.
2. **reject** — transport returns a deny verdict → `{ ok: false, error }`, no session leaked.
3. **malformed-fail-closed** — transport returns a non-plain-JSON / missing-field reply →
   fail-closed reject (no throw, no partial session).
4. **missing-grant** — manifest lacks the `owner.auth` grant → `hostReject("MISSING_CAPABILITY", …)`
   WITHOUT ever invoking the transport (assert the stub was not called).
Typecheck clean; pure and headless (no ambient I/O, transport injected).

## Security/constraints
- Injected ports only (no ambient I/O); capability-mediated on `owner.auth`, fail-closed on every
  edge (missing grant, malformed reply, deny verdict). Plain-JSON request/response — no functions,
  no prototypes, no non-finite numbers crossing the boundary. The SDK never holds or verifies key
  material; it forwards `clientDataJSON`/`authenticatorData`/`signature` and trusts agentd's
  verdict. No remote imports; lockfile mandatory; no package lifecycle scripts; no FFI/native.

## Rollback plan
Single-branch (`task/PSD-381`); revert the merge commit. The new `"owner.auth"` capability and
`authenticateOwner` are additive (optional/new members), so reverting restores the prior
`DesktopHost` surface with no consumer breakage.

## Reviewer revision (round 3)

Codex R2 review: earlier findings fixed. Two NEW BLOCKING auth issues in sdk/typescript/src/desktop-sdk/ui-package.ts; keep the rest, add tests:
1. (~:285, :304) The submitted credential JSON carries a 'user' and the adapter prefers parsed.value.user for the authenticated OwnerAuthSession. That lets UNTRUSTED lock input choose the session user. agentd verifies the ASSERTION, not that user object. The authenticated session's user MUST come from the TRUSTED Lock/host context only - never from the untrusted submitted credential. Drop parsed.value.user; source the user from trusted host context. Add a test: a forged 'user' in the submitted credential is ignored.
2. (~:234-239) The adapter assumes host.authenticateOwner returned a well-formed LockViewModelError-shaped failure before reading result.error.code/path. A MALFORMED or throwing host result must be caught and normalized fail-closed to a LockViewModelError (never throw, never a non-shaped reject). Add a test for a malformed/throwing host result -> fail-closed normalized error.
