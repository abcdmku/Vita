## Objective
Build the WRAPPER that turns the (separately imported) flagship desktop design at `ui_kits/desktop/index.html` into a
real, swappable **`DesktopUiPackage`** on the merged `@vita/desktop-sdk` (PSD-021) — the first concrete consumer of the
SDK, proving the boundary. Pure, deterministic, headless TypeScript over the SDK's injected `DesktopHost` (tests use a
fake host); NO platform internals, NO web engine here.
- A `ui_kits/desktop/package.ts` implementing `DesktopUiPackage` from `@vita/desktop-sdk`: a manifest (`id`
  "vita.desktop.flagship", `version`, `sdkVersion` from the SDK, `entry: "index.html"`, declared capability grants it
  needs — apps.launch, notifications, etc.) + `mount(host: DesktopHost): DesktopUiInstance` that registers the desktop's
  root surface/shell against the host (pointing at the `index.html` entry the SDK/engine renders) and `unmount()` that
  tears it down cleanly. Use ONLY the SDK's public surface.
- A `ui_kits/desktop/index.html` PLACEHOLDER (a minimal valid desktop shell page) — the IMPORTED design replaces this
  file's content later; the wrapper + manifest must work regardless of the page's specifics. Do NOT fabricate the final
  design; keep the placeholder minimal + clearly marked.
- Validation: the package loads through the SDK loader against a fake host (mount → instance, unmount → clean), declares
  a compatible `sdkVersion`, and fails closed if a required grant is missing.

## User value
The flagship desktop UI becomes a swappable package built on the SDK — exactly the owner's 3-layer model. This wrapper is
the seam the imported `ui_kits/desktop/index.html` design drops into and the SDK loads/swaps.

## REVISION 1 (Codex R1: re-mountable + fail-closed mount — 2026-06-25)
Two lifecycle findings on the swappable-package contract:
1. **Re-mountable (package.ts:63):** `host.registerComponent` returning `DUPLICATE_COMPONENT` is treated as a hard
   failure, but components survive `unmount()` (the SDK host has no unregister API), so re-mounting the SAME package on
   the SAME host fails. FIX: treat `DUPLICATE_COMPONENT` as IDEMPOTENT success (the component is already registered —
   fine on remount/reload). Add a remount-after-unmount regression (mount → unmount → mount again succeeds).
2. **Fail-closed mount (package.ts:110-118):** `mount()` launches the desktop app BEFORE later fallible ops
   (notification/tray registration); if one throws, `mount()` throws WITHOUT returning an instance, so the loader cannot
   call `unmount()` and the launched app leaks. FIX: make `mount()` fail-closed — if ANY step after launch fails, roll
   back everything done so far (stop the launched app + undo the shell/registrations) before throwing; never leave a
   launched app with no returned instance. Add a post-launch-partial-failure regression (a later registration throws →
   the app is stopped, no leak).
Keep all existing tests. Verify: npm run typecheck && node --experimental-strip-types --test sdk/typescript/test/ui-kits/*.test.ts

## REVISION 2 (Codex R1: single shell-rollback semantics — 2026-06-25)
`cleanupLaunchedDesktop()` (package.ts:216) calls `host.rollbackShell()` then rethrows, but the SDK LOADER ALSO calls
`rollbackShell()` after a mount failure. With the real `ManagedShellConfigController` (rollback = toggle current↔previous),
the DOUBLE rollback corrupts history (can restore the FAILED shell; a later fallback unmount brings it back). FIX:
in `mount()`'s catch path, roll back ONLY the launched APP (stop it) + undo non-shell registrations — do NOT call
`rollbackShell()`; let the LOADER perform the single shell rollback. Prove single-rollback semantics: test against the
real `ManagedShellConfigController` (or an equivalent that models the toggle/history), asserting that after a post-launch
mount failure + loader rollback, the active shell is the PRIOR good one (not the failed desktop) and the app is stopped.
Keep all existing tests. Verify: npm run typecheck && node --experimental-strip-types --test sdk/typescript/test/ui-kits/*.test.ts
