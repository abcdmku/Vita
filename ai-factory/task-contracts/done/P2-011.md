## Objective
`previewStorageChange(current, desired)` (controller/storage): given the current + desired `StorageLayout`
(the P0-019 SDK model), validate BOTH via `validateStorageLayout`, then compute a typed, fail-closed
**change diff** — WITHOUT applying anything: per-subvolume `added` / `removed` / `modified`
(role/path/appId/quota changes), keyed by the subvolume role+path. Return `{ valid, diff, rejections }`.
Fail-closed: if either layout fails validation, return a typed rejection (no diff, never a throw).

## User value
The management-plane "what will this storage change do" view (FR-014/006) — shows exactly which
subvolumes are added/removed/modified before any host apply, on validated inputs only.

## Non-goals
- No real Btrfs/disk apply, no agent call, no network. Validate + diff only. Do NOT modify the P0-019
  `storage-model`; import it.

## Dependencies
P0-019 (storage model: validateStorageLayout), P0-015 (safeNormalize, via the model). Merged.

## Acceptance tests
`acceptance_command` — `storage-preview.test.ts`: identical layouts ⇒ empty diff; an added/removed/
modified subvolume ⇒ correctly classified in the diff; an invalid current OR desired layout ⇒ typed
rejection (no diff, no throw); hostile input ⇒ fail-closed. Orchestrator also runs `npm run typecheck`.

## Performance & security constraints
Deterministic, no I/O/network. Fail-closed (reuse `validateStorageLayout`; never throw). Strict TS
(no `any`). R2 → reviewer-gated.
