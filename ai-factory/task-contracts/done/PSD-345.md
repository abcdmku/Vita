## Objective
Build the missing desktop **settings store + backend** that backs the three `DesktopHost` settings ports
(`readSetting` / `previewSetting` / `applySetting`) defined in
`sdk/typescript/src/desktop-sdk/ui-package.ts:135-137`. Today the host bridge
(`ui_kits/desktop/runtime/host-bridge.ts`) only *forwards* these methods to an external transport, and the
Settings view-model (`ui_kits/desktop/viewmodels/Settings.ts`) consumes them — but **no backend implements
them**, so toggles never persist. This contract builds that backend on the SDK side ("sdk-ts").
- A deterministic settings **model**: a typed key→value document over the real desktop setting keys —
  `appearance.theme` (light|dark|graphite), `appearance.accent` (blue|teal|violet|orange|green),
  `appearance.layout` (comfortable|compact|floating|tiling), `settings.activeSection`, plus
  `a11y.*`, `wallpaper.*`, and `keyboard.*` keys (reuse the option/enum sets in
  `ui_kits/desktop/viewmodels/Settings.ts` — do not redefine the enums divergently). Unknown keys
  fail closed.
- A **preview→apply transaction**: `previewSetting(req)` returns
  `DesktopSettingsPreview {revision, diff}` (`ui-package.ts:107-110`) computed against current state
  WITHOUT mutating; `applySetting(req)` commits and returns `DesktopSettingsApply {revision, applied}`
  (`ui-package.ts:112-115`). `revision` is **deterministic** — a content hash of the canonicalized
  (sorted-key) document, identical inputs → byte-identical revision.
- **Persistence to `/var`** via the atomic-file pattern (write temp + fsync + atomic rename; no partial
  files on crash). I/O goes through an **injected** filesystem port (no ambient `node:fs` import in the
  store module) so the unit test drives an in-memory fake. The on-device wiring (real `/var` path) is a
  thin adapter, not part of this slice's tested surface.
- **Grant-gated**: reads require `settings.read`, writes require `settings.write`
  (the grants already declared in `desktopUiPackageManifest`, `package.ts:141-145`, and enforced via
  `hasDesktopCapabilityGrant`). Missing grant → fail-closed `DesktopHostResult` error, never a throw.
- The store's `readSetting`/`previewSetting`/`applySetting` must satisfy the existing host-bridge guards
  `isDesktopSettingsPreview` / `isDesktopSettingsApply` (`host-bridge.ts:807-821`) so it can be wired
  behind the bridge transport unchanged.
- Put the code under `sdk/typescript/src/desktop-settings-store.ts` and tests under
  `sdk/typescript/test/ui-kits/desktop-settings-store.test.ts`. Import desktop types only from the
  public `sdk/typescript/src/desktop-sdk/index.ts` barrel (as `Settings.ts` / `host-bridge.ts` do).

## User value
Makes Settings toggles actually **persist across reboot**: the Appearance/theme/accent/layout/a11y/
wallpaper/keyboard choices a user makes in the flagship desktop survive a restart, with a safe
preview-before-commit transaction and crash-safe storage. This is the backend the existing Settings
view-model has been calling into a void for.

## Non-goals
- NO DOM/CSS/rendering/CEF, no view-model changes (Settings.ts already consumes the ports — don't
  rewrite it). NO new visual design. Do not implement the real `/var` mount wiring or boot-time
  hydration here (separate slice) — the FS port is injected and faked in tests. Do not redefine the
  setting enums in a way that diverges from `viewmodels/Settings.ts`. Do not widen capability grants or
  touch protected-policy files.

## Acceptance
`acceptance_command` passes. Deterministic unit tests in
`sdk/typescript/test/ui-kits/desktop-settings-store.test.ts` cover, against fake ports (no ambient I/O):
- `readSetting` returns the current persisted value for a known key, and fails closed for an unknown key
  and when the `settings.read` grant is absent.
- `previewSetting` yields `{revision, diff}` reflecting the requested change and does **not** mutate
  store state (a subsequent `readSetting` still returns the old value); passes
  `isDesktopSettingsPreview`.
- `applySetting` commits the change, a subsequent `readSetting` reflects it, the returned `applied`
  matches the request, and it passes `isDesktopSettingsApply`; fails closed without `settings.write`.
- Reloading a fresh store from the persisted file restores prior state (round-trip through the atomic
  FS fake; verify a partial/temp file is never observed as the committed document).
- `revision` is deterministic: identical document content → identical revision; a changed value →
  a different revision.
Typecheck clean under `tsconfig.base.json`; pure/deterministic (no `Date.now()`/`Math.random()` in the
revision or diff path).

## Security/constraints
- Injected ports only (FS + grant check) — no ambient I/O, no `node:fs` import in the store module;
  capability-mediated, fail-closed on missing grant or malformed input. Atomic, crash-safe persistence
  (temp+rename, no partial commit). Deterministic revision (content hash, sorted keys). No remote
  imports; lockfile mandatory; no package lifecycle scripts; no FFI/native addons.
