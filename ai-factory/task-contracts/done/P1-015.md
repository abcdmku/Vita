## Objective
Expose the agent's **registered operation names** so the controller can discover what it can apply
(FR-004 discover, FR-006 plan-building). Add a read-only `GET /operations` to the transport returning
`{"operations": [<registry.Names()>]}` (sorted). This fixes the gap found while integrating P1-013:
`GET /capabilities` reports HARDWARE discovery (P1-005), which is a DIFFERENT concept from the registered
transactional operations; the controller needs both. Keep `/capabilities` exactly as-is (hardware).
- Loopback-only, read-only; non-GET ⇒ 405; the handler reads names from the same `*capabilities.Registry`
  the transport already holds. No new capabilities, no /apply changes.

## User value
The controller can enumerate applicable operations (node.config, time.set, hostname.set, …) to build
plans (FR-006) — currently impossible (hardware /capabilities ≠ operations). Closes a real integration gap.

## Non-goals
- Do NOT change `/capabilities` (hardware) or `/apply`. No controller-client wiring here (P2-006
  `getOperations` is a separate follow-up). No new capabilities.

## Dependencies
P1-008 (transport), P1-013 (populated registry). Both merged.

## Acceptance tests

`{operations:[…]}`; an empty registry returns `{operations:[]}` (not null); non-GET ⇒ 405; `/capabilities`
still returns the hardware shape (unchanged). httptest, no real socket.
