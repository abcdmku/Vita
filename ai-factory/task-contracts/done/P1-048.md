## Objective
The filed ADR-0008/0009 hardening: now that `capsule.execute` lets the channel SPAWN workloads, harden the agentd
unix socket with PEER-CREDENTIAL authentication. agentd's unix listener must verify the connecting peer is authorized
(a member of the `vita-agent` group — the same identity the socket FS-perms gate) BEFORE serving any request, and
REJECT (close + audit) others. This is defense-in-depth beyond the socket's `0660 group=vita-agent` perms (so a perms
misconfig or a same-group-but-wrong-process can't silently get through), per ADR-0008's noted future hardening.

Concretely:
- On each accepted unix connection, read the peer credentials. Note the TS runtime is a **DynamicUser** whose
  *primary* gid is transient (NOT vita-agent — that's a SUPPLEMENTARY group). So `SO_PEERCRED`'s gid alone is
  insufficient: verify the peer is a MEMBER of the `vita-agent` group via **`SO_PEERGROUPS`** (Linux ≥4.13) OR a
  `/proc/<peer-pid>/status` `Groups:` read as fallback. Accept iff the peer is in `vita-agent`; else close the
  connection + audit `peer_unauthorized`. TCP (loopback dev) path unaffected (or also gated — keep existing behavior).
- Confirm the legitimate vita-ts runtime (SupplementaryGroups=vita-agent) STILL connects (no regression) and an
  unauthorized local peer (not in the group) is REJECTED.
- TS side: `main.ts`'s `VITA-CONNECT` is unchanged in shape; optionally annotate `auth=peercred` once it connects
  through the authenticated path. Keep all markers.

## User value
The privileged agent's control channel — which can now spawn workloads + mutate the host — only serves the intended
unprivileged runtime, verified by kernel-provided peer credentials, not just filesystem permissions. Closes the
ADR-0008 "unauthenticated channel" gap that `capsule.execute` made higher-impact.

## Non-goals
NO token/mTLS auth (peer-cred is the on-device single-tenant control). NO change to the request semantics. Don't
break the legitimate runtime's connection. NO change to the TCP-dev path's existing behavior beyond what's needed.

## Acceptance tests
`acceptance_command` — Go tests: a connection whose peer IS in `vita-agent` is SERVED; a peer NOT in the group is
REJECTED (connection closed, audit `peer_unauthorized`, no request served); the group-membership check uses
SO_PEERGROUPS (or the /proc fallback) — NOT just SO_PEERCRED's primary gid (a DynamicUser-like primary-gid peer in
the supplementary group is ACCEPTED). vet/build clean; existing transport tests green. Orchestrator host-verifies:
boot, the vita-ts runtime still reaches agentd (`VITA-CONNECT … healthz=OK`) through the authenticated path (no
regression); the full chain still PASS.

## Performance & security constraints
Peer-cred auth checked BEFORE serving; unauthorized → closed + audited (fail-closed). Must not break the legitimate
DynamicUser runtime (verify via supplementary-group membership, not primary gid). No keys. R3 (privileged-daemon
access control) → parallel-candidate + reviewer gate.
