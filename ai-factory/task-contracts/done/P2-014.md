## Objective
`previewBackupChange(current, desired)` (controller/backup): given current + desired `BackupPolicy`
(the P0-020 SDK model), validate BOTH via `validateBackupPolicy`, then compute a typed, fail-closed
**change diff** — WITHOUT applying anything: schedule change, retention change (count/maxAge), targets
added/removed, and a `weakensRetention` flag when the desired policy SHORTENS retention (lower count or
shorter max age) vs current — so the operator sees a reduction in backup coverage. Return
`{ valid, diff, weakensRetention, rejections }`. Fail-closed: invalid either side ⇒ typed rejection, no
diff, never a throw. §13.1: never surface recovery-key material (reference only).

## User value
The management-plane "what will this backup-policy change do, and does it reduce coverage" view
(FR-015/006) — on validated inputs only, before any host apply.

## Non-goals
- No real backup apply/run, no agent call, no network, no crypto. Validate + diff only. Do NOT modify the
  P0-020 `backup-model`; import it.

## Dependencies
P0-020 (backup model: validateBackupPolicy/validateRecoveryKeyEnrollment), P0-015. Merged.

## Acceptance tests
`acceptance_command` — `backup-preview.test.ts`: identical policies ⇒ empty diff, weakensRetention false;
shorter retention (lower count or maxAge) ⇒ weakensRetention true; added/removed targets + schedule change
classified; invalid current OR desired ⇒ typed rejection (no diff, no throw); hostile input ⇒ fail-closed;
no recovery-key material in the preview output (§13.1). Orchestrator also runs `npm run typecheck`.

## Performance & security constraints
Deterministic, no I/O/network. Fail-closed (reuse `validateBackupPolicy`; never throw). §13.1 (no key
material in output). `weakensRetention` correctly flags coverage reductions. Strict TS (no `any`).
R2 → reviewer-gated.
