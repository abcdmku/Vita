## Objective
Migrate the `pdssync` capability (op `pdssync.*` — verify the exact `Name`) end-to-end — the FINAL of 13 caps.
The REAL entrypoint `transport.DecodeJSONRequest[pdssync.ApplyRequest]`+`Validate()` is the ORACLE. Read
`agent/capabilities/pdssync/pdssync.go` and match `SyncState.Validate`/`validateRepoHead`(CID)/`decodeMultibase`/
`requiredCursorField`/the repo-DID validation EXACTLY (AGENTS.md manifest≡agent + the 9 traps).
- **`schema/capabilities/pdssync.json` = the full request** `{ desired: { object: { repo: didPlcOrWeb; cursor:
  integer (float64-Trunc, 0..maxCursor); repoHead: cidV1Multibase } } }` (READ the SyncState shape + which
  fields are required).
- **REUSE `didPlcOrWeb`** (P9-019 — `repo` is a DID; pdssync uses the SAME didPlcIdentifierPattern
  `^[a-z2-7]{24}$` + didWebPathSegmentPattern; confirm identical to identity's, maxDIDLength 2048, and reuse).
- **`cursor` — float64-Trunc integer mode (NEW per-field option; this cap is the ONE exception to trap 9).**
  The agent `requiredCursorField` (pdssync.go:~542) decodes the JSON number as a FLOAT64 and rejects only
  `IsInf||IsNaN||Trunc(value)!=value||value<0||value>maxCursor(9007199254740991=2^53-1)`. So it ACCEPTS
  integer-valued floats/exponents `1000.0`/`1e3` (Trunc==value) and rejects `1000.5`. This DIFFERS from
  accounts/network (Go-`int` decode, trap 9 rejects `1000.0`). The manifest's integer for `cursor` must MATCH
  THIS: add an opt-in flag (e.g. `acceptIntegerValuedFloat: true`) that accepts integer-valued float/exponent
  tokens (Trunc==value) within `[0, 2^53-1]` and rejects fractional/Inf/NaN/negative/over. Do NOT apply the
  strict trap-9 reject to `cursor` (that would be STRICTER ⇒ manifest≢agent). Default stays strict for all
  other fields/caps.
- **`cidV1Multibase` (NEW format — the heaviest; structured, NO regex engine; ground-truth cross-check):**
  match `validateRepoHead`/`decodeMultibase` EXACTLY: multibase prefix handling + base32-lower alphabet
  `abcdefghijklmnopqrstuvwxyz234567` (pdssync.go:420) and base58btc alphabet (`:421`) decode, the CIDv1
  (`cidVersion=1`) structural checks (version/codec/multihash/digest-length per the agent), maxCIDLength 512,
  trim/control as the agent does. Replicate the EXACT decode/validation; pin with a FROZEN corpus.
- **RUNTIME-EXCLUDED:** the cursor NON-REGRESSION check (`desired.Cursor < priorState.Cursor` ⇒ reject,
  pdssync.go:~251) compares to STORED state — it is RUNTIME/stateful and MUST stay OUT of the manifest (trap
  6); the manifest validates cursor as a standalone 0..maxCursor value. The conformance tests `Validate()`,
  not the apply-time regression.
- **secretKeyNameDenylist** — READ pdssync.go: if it rejects object KEYS whose normalized name is a secret
  token, model that (a key-name screen, distinct from value screening); if it does NOT, do not add it (match
  the agent). DisallowUnknownFields is already handled by jsonsafe.
- **Conformance ≡ agent** `schema/capabilities/conformance/pdssync.json` (≥ 26 full-request vectors) via BOTH
  the manifest AND `DecodeJSONRequest[pdssync.ApplyRequest]`+`Validate()` (dual-oracle, copy
  network_conformance_test.go — NOT self-referential). Cover: valid did:plc/did:web repo + valid base32/base58
  CID; bad repo; bad CID (wrong multibase, bad alphabet char, wrong version/length, >512); cursor 0/max/-1/
  over-max/`1000.0`(ACCEPT)/`1e3`(ACCEPT)/`1000.5`(reject)/Inf-as-string; each field absent; dup JSON key;
  unknown field. The REAL entrypoint is the oracle.
- **Register** pdssync (regenerate; orchestrator updates the registry test) + evaluator coverage. Agent UNCHANGED.

full-request `conformance/pdssync.json` is already a genuine dual oracle (good — keep it). BUT
`schema/capabilities/formats/pdssync-formats-conformance.json` + `pdssync_conformance_test.go`'s
`TestPDSSyncFormatConformanceCorpus` validate the cidV1Multibase format vectors ONLY through
`Validate(manifest,…)`/`normalizeStringFormat(…)` — i.e. the manifest's OWN CID decoder, NOT `pdssync.go`. That
is manifest≡manifest, structurally blind to manifest≢agent drift (trap 8), and it leaves the codec/hash/
digest-length edge cases UNVALIDATED against the real agent. (The independent probe read the CID port
byte-for-byte and it IS faithful — so this is a TEST-INTEGRITY fix, not a known code divergence; lock the
parity in so it cannot regress.) **FIX:** make EVERY cidV1Multibase edge case run through the REAL agent —
either (a, preferred) FOLD the format vectors (base32-lower/upper-B/base58btc accept; bad multibase prefix;
non-canonical base32 trailing bits; wrong version; nonzero-codec; digest-length 0/1/128/129; total-length
mismatch; >512 byte; control/trim) into `conformance/pdssync.json` as full `{repo,cursor,repoHead:<cid>}`
requests (the dual oracle then runs each through `transport.DecodeJSONRequest[pdssync.ApplyRequest]+Validate()`
AND the manifest, asserting agreement), OR (b) change the format test to vendor a copy of `pdssync.go`'s
`decodeMultibase`/`isCIDV1Bytes` as the ORACLE (like P9-015's services-regex vendoring) and assert the
manifest's CID decoder ≡ that oracle on every vector. No assertion may compare the manifest against its OWN
copy. Keep everything else from round 1 (it is correct).
