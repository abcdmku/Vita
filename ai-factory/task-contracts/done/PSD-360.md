## Objective
Author **ADR-0016** (`architecture/adr/0016-first-party-app-packages.md`, status **Proposed**) that records the
architecture decision (per the owner): the desktop's apps (Files, Terminal, Settings, Browser, Mail, Text-Editor,
Activity-Monitor) are **NOT baked into the desktop shell** — each is a **separable FIRST-PARTY PACKAGE**, mirroring the
swappable Desktop UI package pattern (`sdk/typescript/src/desktop-sdk/ui-package.ts` `DesktopUiPackageManifest`/
`DesktopUiPackage`, and the flagship `ui_kits/desktop/package.ts`). It is a decision record, not code. It MUST decide and
record:
- **(a) The `AppPackageManifest` shape** — mirror `DesktopUiPackageManifest` (`ui-package.ts:43-49`) for an APP:
  `id` / `version` / `sdkVersion` (`DesktopSdkCompatibility`) / `entry` (the CEF-rendered web-app HTML/CSS/TS bundle
  entry, like `DESKTOP_UI_ENTRY`) + a declared **`capabilityGrants: readonly DesktopCapabilityGrant[]`**
  (`ui-package.ts:36-39`, the same `DesktopCapability` union at `ui-package.ts:25-34`). Decide where it lives
  (`sdk/typescript/src/desktop-sdk/app-package.ts`, exported from `sdk/typescript/src/desktop-sdk/index.ts`) and the
  `AppPackage` interface every first-party app implements (`{ manifest; entry/descriptor }`, analogous to
  `DesktopUiPackage.mount`).
- **(b) The app loader / host / window lifecycle** — apps are launched via the EXISTING `DesktopHost.launchApp(app)` /
  `stopApp(appId)` seam (`ui-package.ts:130-131`, returning `DesktopAppLaunch`/`DesktopAppStop` with
  `surfaceId`/`windowId`/`textureId`/`intents`), each app a `WebAppDescriptor` (`appshell/index.ts:85` — `surfaceKind:"web"`,
  `WebviewRuntimeRef` `{ url, partition }`) windowed by the WM on the compositor multi-surface stacking seam
  (**PSD-304**, `raise_surface`/`set_z`/per-surface placement) and host-backend-wired per **ADR-0015** (PSD-340 — the host
  proxy routes `launchApp`->capsule.execute / `stopApp`->capsule.stop, with capability enforcement at the host proxy).
- **(c) Install / list / launch flow** — apps install via the EXISTING separable-package/capsule mechanism (the same path
  proven for the desktop package in **PSD-001** `packageClass`/`capsule.fetch`->install transaction->launch/stop), are
  LISTED by an app registry (a pure registry/loader view-model, PSD-361), and LAUNCHED by the dock/launcher
  (`emitLauncherIntent`, `ui-package.ts:138`; the dock view-model `ui_kits/desktop/viewmodels/dock.ts`) + windowed by the
  WM. Users can build/ship/swap apps too (third-party apps implement the same `AppPackageManifest`).
- **(d) Capability enforcement is at the host (single choke point), fail-closed** — consistent with ADR-0015: no backend
  trusts the renderer; each `launchApp`/`requestFile`/`readSetting`/... is checked against the app package's
  `capabilityGrants` at the host proxy and fails closed if the grant is absent. Apps are OFFLINE
  (`allowed_network:false`) and capability-gated.
- **The slice DAG** — enumerate the follow-on implementation slices and their dependency edges so the build fans out: the
  app-package SDK foundation + registry/loader view-model (PSD-361, depends on this ADR + ADR-0015), then ONE slice per
  first-party app (PSD-362..PSD-368: Files, Terminal, Settings, Browser, Mail, Text-Editor, Activity-Monitor), each
  `depends_on` PSD-361 (+ PSD-340/PSD-304 for the launch/window seam).

Put the ADR at `architecture/adr/0016-first-party-app-packages.md`. Cross-link ADR-0013 (`0013-desktop-hydration.md`),
ADR-0014 (`0014-cef-live-render.md`), and ADR-0015 (`0015-desktop-host-bridge.md`, authored by PSD-340). Add a small
deterministic guard test at `sdk/typescript/test/ui-kits/adr-0016.test.ts` that asserts the ADR exists and contains the
required sections (so an empty branch fails).

## User value
Fixes the product framing as a load-bearing decision: every follow-on worker knows apps are swappable first-party
packages (not shell built-ins), what the `AppPackageManifest` is, how an app is loaded/hosted/windowed (DesktopHost +
PSD-304 + ADR-0015), how it installs/lists/launches (PSD-001 + dock/launcher + registry), and where capability
enforcement sits — turning "the desktop has apps" into a buildable, fan-outable plan with one slice per app.

## Non-goals
- NO implementation of the SDK foundation, registry, or any app — this is a decision record only.
- Do NOT modify `ui-package.ts`, `appshell/index.ts`, `host-bridge.ts`, `package.ts`, or any runtime/SDK source.
- Do NOT change the `DesktopCapability` union, the `DesktopHost` seam, or the `WebAppDescriptor` shape; the ADR documents
  them, not edits.
- No new visual design; no DOM/CSS/CEF code.
