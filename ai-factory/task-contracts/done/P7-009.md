## Objective
A transactional capability `agent/capabilities/accounts/` that stores the node's managed local-accounts
config to a FIXED agent state path, applied atomically with rollback — the proven nodeconfig (P1-007)
pattern, with the SAME security gates as the P0-029 SDK model (`sdk/typescript/src/accounts-model.ts` — read
it for the exact rules; the agent is the authoritative enforcer). Typed `Account { name; uid; primaryGroup;
groups; shell; enabled *bool }`, `Config { accounts *[]Account }`. `Handle` reads current; `Apply` validates
a desired config and writes via a SINGLE atomic commit point (the proven `os.CreateTemp`+O_EXCL → write →
Sync → Close → Rename pattern — NOT a predictable temp name), returning a restoring `Undo`; commit + rollback
proven (inject a failure at AND after the effect — assert no third state). Implements `Validate()` with
duplicate-JSON-key rejection + canonical persisted bytes.
- **Security gates (fail-closed, mirror P0-029)**: `name` POSIX `^[a-z_][a-z0-9_-]{0,31}$`; `uid` integer,
  **REJECT uid 0 and uid < 1000**, ≤ 60000; `primaryGroup`/`groups` valid group names, deduped, **REJECT
  membership in `root`/`sudo`/`wheel`/`admin`**; `shell` from the closed allowlist `{ /bin/bash, /bin/sh,
  /usr/bin/bash, /usr/bin/zsh, /usr/sbin/nologin, /bin/false }`; `enabled` *bool EXPLICIT presence (absent ⇒
  reject); reject duplicate `name` AND duplicate `uid`; `accounts` pointer slice (absent ⇒ reject; explicit
  empty `[]` ⇒ accept); reject unknown JSON keys; §13.1 inline-key-material rejection. NO password/secret
  fields. No `os/exec`, no real `useradd`/`/etc/passwd` — stores the DESIRED config; real apply is later.

## User value
The security-gated managed-accounts state the node enforces (FR-007) — privilege-escalation guards (no
root/uid<1000, no privileged-group membership, allowlisted shells) enforced in the TCB before any account
is provisioned. Real useradd apply is a later host contract.
