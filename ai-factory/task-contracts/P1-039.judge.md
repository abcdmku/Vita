## WINNER: B  (`task/P1-039B`)
## VERDICT (winner B): approve

Both candidates are correct, secure, fail-closed, and pass 6/6 acceptance tests. The decision is narrow.
B wins because it is the **minimal, exactly-to-spec** mutation-boundary widening (smaller surface to
misread) AND it adds a real defense-in-depth edge A lacks (serial-marker sanitization). A is also
mergeable and is *more* restrictive on the read path, but that extra restriction is beyond-spec and
introduces a server-route coupling that B avoids. For an R3 write-boundary, "smaller and exactly what
was asked" beats "stricter but coupled."

## Per-axis findings

### 1. Apply-transport narrowness (decisive) — both PASS the hard requirement; tie on write surface
The hard requirement is: write surface == **exactly POST /apply**, no general write. Both meet it.

- **A** (`unix-socket-transport.ts` +61): refactors to a shared `createTransport(options, allowApply)`
  and adds `createDenoUnixSocketApplyAgentTransport`. In apply mode `isAllowedRequest` allowlists an
  EXACT GET set (`/audit /capabilities /healthz /operations /read /state` + `/read/<cap>`) **and** POST
  `/apply`; rejects query strings on all paths; rejects unknown GET paths. Write surface = only POST
  `/apply`. ✅ Tighter on reads.
- **B** (`unix-socket-transport.ts` +33): standalone `createDenoUnixSocketApplyAgentTransport` that
  keeps the read-only transport's existing read behavior (any GET — which is exactly what S2 shipped:
  the read-only default only rejects non-GET) and adds POST `/apply` via `isApplyPost` (rejects query
  strings on `/apply`). Write surface = only POST `/apply`. ✅ Exactly the contract wording: "allow
  EXACTLY POST /apply (plus the existing GETs)".

Assessment: neither broadens the write surface beyond `/apply` (the load-bearing requirement). A is
*stricter* on reads, but the contract's "the existing GETs" = the read-only transport's existing
surface, which is any-GET; so **B is precisely spec, A is beyond-spec**. A's GET allowlist couples the
TS transport to agentd's route table — if agentd adds a GET endpoint, A's apply transport silently
blocks it (latent drift bug); B has no such coupling. B is also +28 lines smaller and a self-contained
function (no shared-flag refactor of the read-only path), so it is *clearer and harder to misuse* for
the thing that matters here (the write gate). Tie on the security floor; edge to B on
clarity/spec-fidelity, edge to A on read strictness. Net: roughly even, slight B.

### 2. agentd re-validation NOT bypassed — both PASS
Confirmed against `agent/transport/server.go`: `handleApply` (L521) requires POST, decodes the body,
then `buildPlan` (L672) re-validates EVERY operation (`operations` required; per-op capability lookup
`h.registry.Lookup`, transactional-capability check, registered decoder, typed `Validate()`), and only
then `transaction.Apply`. Neither candidate fabricates a result locally; both just POST the plan and
surface agentd's actual response. The forced-invalid plan (`vita.invalid.capability`) is rejected by
`buildPlan`'s `unknown_capability` path server-side — proving the runtime cannot force a mutation. ✅✅

### 3. Benign-by-construction + markers — both PASS
- Both read the CURRENT hostname first (`state.state.hostname`) and apply `hostname.set → desired =
  currentHostname` — a no-op-equivalent commit. **Apply is only attempted inside `if (state.ok)`**; on a
  failed state read both emit `VITA-APPLY-ERROR: status=FAILSAFE` and never apply. No destructive op.
- Committed marker: both emit `VITA-APPLY: outcome=committed applied=N rolledBack=0 audit=recorded
  status=OK` (audit=recorded unless `auditUnrecorded`). ✅
- Forced-reject: both emit `VITA-APPLY: outcome=rejected reason=<code> status=OK`. ✅ (fail-closed proof)
- Transport/unexpected error: both emit `VITA-APPLY-ERROR: status=FAILSAFE`, never throw out of the
  oneshot. ✅
- **Difference (B better):** B sanitizes the rejected `reason` through `markerToken()`
  (`replace(/[^A-Za-z0-9_.-]+/gu,"_")`) before interpolating it into the serial marker (main.ts L395).
  A interpolates `rejected.reason` RAW (main.ts L291). Today agentd's error codes are clean constants,
  so A is safe in practice — but at an R3 "response-is-untrusted" boundary, a code containing a
  space/newline would split/forge the marker line that the orchestrator's host-verify parses. B defends
  at the marker layer; A relies on agentd codes always being clean. Concrete edge to B. (PORT to A.)

### 4. Vendoring fidelity — both PASS, byte-identical
`apply-node-config.ts` (497 lines) in A and B are **byte-identical to each other**, and differ from
upstream `controller/apply-node/src/apply-node-config.ts` by exactly: the `// Vendored from …` header +
three import-path adjustments (`./evaluate.ts`, `./safe-normalize.ts`). No logic fork. ✅✅ (Both even
ship a test that re-derives this diff and asserts body-identity — test 3.)

### 5. Test quality — both 6/6 PASS; coverage essentially equal, A slightly broader on read-surface
Both: POST-body shape, committed-parse, **upstream parity on a shared mock**, **vendored-body-identical
guard**, rejected-fail-closed, transport-error, and the narrow-surface guard.
- **A narrow-surface test** (L135): asserts allowed GET `/operations`, GET `/read/hostname.set`, POST

  `/apply` (wrong method on apply path), GET `/not-found` (unknown path), GET `/operations?x=1` (query

- **B narrow-surface test**: asserts allowed GET `/healthz` + POST `/apply` (payload-verified); rejects

Both honest (no weakened/oracle-free asserts). A tests a couple more read-path negatives, consistent
with A's stricter design; B's negatives are exactly the ones that matter for its design (write to
wrong path, query smuggling). Slight edge to A on raw breadth; not decisive.

## Why B over A
1. **Exactly-to-spec, minimal surface.** B widens precisely "POST /apply on top of the existing GETs"
   — the contract's literal requirement — in a self-contained +33-line function. A re-architects the
   read-only path into a shared `allowApply` flag (+61) and adds a GET allowlist that is *beyond spec*
   and **couples the unprivileged transport to agentd's route table** (a new agentd GET endpoint would
   be silently blocked client-side). For the write boundary, smaller + decoupled + literal-spec is the
   lower-risk guard.
2. **Marker sanitization (real defense-in-depth at an R3 boundary).** B runs the agentd-supplied reject
   reason through `markerToken()` before it reaches the serial marker the orchestrator parses; A emits
   it raw. Right instinct for "the response is untrusted."
3. **Reuse over re-implementation.** B's forced-reject path reuses the already-vendored
   `createAgentClient().apply()` + `isAgentClientError`/`AgentClientError.agentError` rather than
   hand-rolling JSON extraction (A adds `readAgentErrorCode`/`readApplyErrorCode`/`readOutcome` helpers
   that duplicate parsing the vendored client already does correctly).

A is fully mergeable and slightly stronger on read-path strictness + test breadth; if read-surface
allowlisting is later judged desirable it can be lifted from A. But for THIS slice, B is the cleaner,
exactly-scoped, better-hardened mutation boundary.
